# Конституция разработки

> **Статус:** принято  
> **Область:** все новые сервисы, контракты и спецификации этого репозитория  
> **Связанные документы:** [AGENTS.md](../AGENTS.md), [System Design](../system-design/README.md)

Эта конституция фиксирует технические принципы, которые применяются к каждой
новой спецификации. Она не заменяет конкретный контракт функции: детали API,
таблиц, лимитов и бизнес-правил по-прежнему определяются в `spec.md` и
`plan.md` конкретной функции.

## 1. Технологическая основа

- Backend пишется на **Eclipse Temurin JDK 25.0.5 LTS**, **Spring Boot 4.1.2**
  и Maven Wrapper.
- Мобильное приложение будет отдельным Flutter-клиентом; оно не содержит
  серверных бизнес-правил и не является владельцем данных.
- Внешний API использует REST/HTTP. gRPC применяется только для согласованных
  внутренних синхронных вызовов с явным Protobuf-контрактом.
- Kafka передаёт сохранённые бизнес-события. RabbitMQ применяется только для
  согласованных фоновых задач, в первую очередь обработки видео. Видеофайлы
  хранятся в S3-совместимом хранилище, а не в брокерах.

## 2. Владение данными и PostgreSQL

- Каждый сервис — единственный владелец своих данных и своей логической базы
  PostgreSQL. Другие сервисы не читают и не изменяют его таблицы напрямую.
- Локальная PostgreSQL устанавливается и запускается вне Docker. Docker Compose
  не должен создавать контейнер PostgreSQL.
- Локальные базы именуются `fitness_<service>`, например первая база Identity
  будет называться `fitness_identity`. Базу создаём только вместе с первым
  сервисом-владельцем, его миграциями и отдельной учётной записью; сейчас
  создавать пустую общую базу не нужно.
- Изменение схемы выполняется только версионируемыми миграциями **Liquibase**.
  Ручное изменение схемы локальной, тестовой или рабочей базы не является
  заменой migration changeset.
- Секреты подключения не коммитятся. В репозитории допускается только
  `.env.example` без настоящих паролей.

## 3. Сообщения, сбои и согласованность

- Kafka для локальной разработки запускается через Docker Compose в режиме
  **KRaft**, без ZooKeeper. Один локальный контейнер нужен для разработки и не
  доказывает отказоустойчивость production-кластера.
- Состояние сервиса и исходящее событие фиксируются локально через outbox.
  Получатель защищается inbox и идемпотентной бизнес-операцией: события могут
  прийти повторно.
- Между базами разных сервисов нет общей транзакции. Нельзя удерживать
  транзакцию PostgreSQL во время сетевого вызова.
- Для временных ошибок определяются таймаут, ограниченные повторы и способ
  восстановления. Повреждённое или невалидное сообщение не повторяется
  бесконечно.

## 4. Безопасность и качество

- Сервер проверяет входные данные и права доступа; клиенту нельзя доверять в
  денежных, видео- и административных операциях.
- Пароли, токены, ключи идемпотентности и персональные данные не попадают в
  логи, события или ответы об ошибках.
- Критичные правила, ошибки, права и конкурирующие запросы покрываются
  автоматическими тестами. Для поведения PostgreSQL используются
  интеграционные тесты с настоящим PostgreSQL.
- Контракты REST, gRPC и событий имеют владельца, версию, примеры, ошибки,
  авторизацию и правила повторной доставки до реализации.

## 5. Порядок работы

1. Сначала описать результат и границы функции в `spec.md`.
2. Затем спланировать данные, контракты, риски и проверку в `plan.md`.
3. Разбить реализацию на проверяемые задачи в `tasks.md`.
4. Выполнять одну связанную задачу в новой пронумерованной ветке и завершать её
   Pull Request после успешных проверок.
5. После завершения сверить критерии готовности спецификации с фактическим
   результатом, а не только с написанным кодом.
