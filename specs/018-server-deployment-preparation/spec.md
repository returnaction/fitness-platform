## Цель

Подготовить воспроизводимую dev-выкладку fitness-platform на одном
VPS: Java-сервисы запускаются в Docker Compose, PostgreSQL 17 работает в
Ubuntu, а GitHub Actions доставляет версии сервисов из GHCR после merge в
`main`.

## Границы

### Входит в эту спецификацию

- Версионирование выпускаемых сервисов и `grpc-contracts` в monorepo.
- Dockerfile, серверный `compose.yaml`, dev-конфигурация и шаблоны окружения
  для всех текущих сервисов; первый Compose-набор: Gateway, Identity, Accounts
  и Coins.
- Генерация и подключение server-only mTLS/JWT-материалов.
- GitHub Actions → private GHCR → SSH-доставка на VPS.
- Чистая Ubuntu 24.04, Docker, PostgreSQL 17, UFW, SSH, DBeaver SSH-туннель.
- Подготовка баз, ролей и первого поэтапного запуска.

### Не входит в эту спецификацию

- Kubernetes, отказоустойчивость, бэкапы, отдельный мониторинг и уведомления.
- Kafka и Redis до появления фактической потребности.
- HTTPS, домен и внешний reverse proxy: dev-клиент использует HTTP gateway на
  IP и порту `8088`.
- Перенос PostgreSQL на другой сервер, PostgreSQL TLS и доступ будущих
  участников команды.
- Выкладка, миграция пользовательской БД, push, merge или deploy без
  отдельного явного разрешения пользователя.

## Пользователи и права

| Роль | Что может делать |
| --- | --- |
| Владелец | Администрировать VPS и управлять доступом к среде. |
| Администратор PostgreSQL | Управлять сервисными базами через защищённое подключение. |
| GitHub Actions | По отдельному SSH-ключу доставлять Compose и выпускать одобренную версию сервиса. |
| Будущий ограниченный пользователь | Не определён в этой спецификации; не получает `sudo` или Docker. |

## Сценарии

### Сценарий: выпуск новой версии одного сервиса

**Дано:** у сервиса увеличена собственная версия в `pom.xml`, тесты и сборка
успешны.
**Когда:** изменение merge-ится в `main`.
**Тогда:** GitHub Actions публикует exact-version image в private GHCR, копирует
`compose.yaml` на VPS и обновляет только этот сервис; остальные контейнеры не
перезапускаются.

### Сценарий: подготовка базы нового сервиса

**Дано:** сервису требуется собственное постоянное хранилище.
**Когда:** владелец создаёт роль, базу и права через DBeaver SSH-туннель по
  [инструкции подготовки БД](../../docs/database-setup.md), затем сохраняет
  настройки подключения вне репозитория.
**Тогда:** первая выкладка сервиса применяет Liquibase-миграции и создаёт
таблицы; другие сервисы не получают доступ к этой БД.

### Ошибки и граничные случаи

| Условие | Ожидаемое поведение |
| --- | --- |
| Тест или сборка выпускаемого сервиса не прошли | Image не публикуется, VPS не меняется. |
| Health-check новой версии не прошёл | Выкладка отмечается ошибочной; автоматического отката нет, причина разбирается по SSH и Docker-логам. |
| Liquibase не применил миграцию | Сервис не запускается; БД, роль и секрет не удаляются автоматически. |
| У сервиса нет БД | Подготовка роли и базы не требуется. |

## Правила

- Только сервис с увеличенной собственной версией выпускается из `main`.
- `latest` не используется: Compose ссылается на точный image tag.
- Изменение Compose-конфигурации сервиса требует повышения версии этого
  сервиса.
- Docker images, Git и GitHub Actions не содержат runtime-паролей, JWT- или
  mTLS-приватных ключей.
- В интернет опубликован только gateway `8088`; PostgreSQL и внутренние
  сервисы закрыты.

## Критерии готовности

- [ ] Первый набор сервисов имеет независимые версии и воспроизводимые images.
- [ ] Server Compose не содержит секретов, публикует только gateway и задаёт
  health-check, restart и log rotation.
- [ ] CI выпускает только сервис с увеличенной версией после его успешных
  проверок.
- [ ] Ubuntu VPS подготовлен согласно согласованной схеме без лишних runtime.
- [ ] PostgreSQL доступен владельцу через DBeaver SSH-туннель и сервисам только
  через внутренний путь Docker.
- [ ] Первый запуск Accounts → Coins → Identity → Gateway подтверждён
  health-check, Liquibase и ручной проверкой с телефона.

## Открытые вопросы

- Точные лимиты Docker/JVM RAM определить по первому реальному запуску.
- Время и формат последующей ротации mTLS-сертификатов после 90 дней.
