## Подготовка физического телефона

Пользователь подключает Android-телефон по USB, включает USB-отладку и разрешает
подключение компьютера. Исполнитель проверяет устройство через adb/Flutter,
фиксирует модель, Android, версию приложения и проверяемую ревизию, собирает и
устанавливает APK. Настроить доступ к существующему локальному Gateway по
инструкции apps/mobile/README.md; проверить серверную доступность.
Использовать согласованный тестовый аккаунт, не изменять реальные данные без
согласования. Не записывать пароль, токены и персональные значения в логи отчёта.

Если управление экраном инструментами недоступно, пользователь выполняет точные
шаги на телефоне, исполнитель сверяет наблюдаемый результат и безопасные логи.
Отмечать, какие действия и наблюдения выполнены пользователем. Не утверждать
визуальную или автоматическую проверку без фактического наблюдения.

## Обязательные сценарии

Составные пункты остаются открытыми до проверки всех их частей; частичные результаты ниже.

- [ ] Вход/регистрация: You are signed in, панель, недоступные Home/Challenges,
  доступный Profile; первый GET, все поля кроме version, Not set.
- [ ] Изменение каждого поля, Public/Private, выбор timezone, выбор/очистка даты,
  очистка необязательных полей; правильная клавиатура, прокрутка, отсутствие
  обрезанного текста и перекрытия Save клавиатурой на подключённом телефоне.
- [ ] Save с изменениями: один PUT, новая версия/данные; Save без изменений:
  отсутствие PUT. Уход без Save: предыдущие значения без подтверждения.
- [x] Перезапуск: локальный профиль без GET; жест вниз: GET и обновление данных.
- [ ] Невалидные поля и занятый ник: понятные ошибки без потери формы.
- [ ] Конфликт версии: изменить тот же тестовый профиль другим клиентом через
  существующий API, получить 409 со старой формы, проверить Reload и его отказ.
- [ ] Потеря сети при первом GET и ручном обновлении: Retry, сохранение старых данных.
- [ ] Потеря ответа PUT: проверить перечитывание, отсутствие слепого повтора PUT,
  совпадающий результат и неопределённость при отличающихся данных/ошибке GET.
- [ ] Уход во время PUT: навигация доступна, повторное редактирование запрещено,
  успех обновляет копию без принудительного перехода, ошибка уведомляет.
- [ ] Завершение приложения во время PUT: при следующем открытии проверка GET,
  отсутствие автоматического повторного PUT.
- [ ] Истёкшая сессия: штатный refresh; окончательный отказ возвращает на вход
  и удаляет профиль/черновик.
- [ ] Выход на этом/всех устройствах, отмена и существующее подтверждение;
  выход во время PUT, игнорирование позднего ответа, очистка локальной копии.
- [ ] Вход другим тестовым пользователем не показывает данные предыдущего.

Для воспроизведения сетевых сбоев допускается тестовая подмена транспорта или
локальный тестовый proxy без изменений production-бэкенда. Отдельно указывать,
что проверено на реальном сервере, что с внедрённым сбоем и что только unit-тестом.
Не подменять обязательную проверку на устройстве результатом автоматических тестов.
Если сценарий пока невозможно воспроизвести, оставить его открытым и описать причину.

## Обнаруженный сбой регистрации — T008

Пользователь дважды сообщил об общей ошибке `Request could not be completed.
Please try again.` после регистрации разных тестовых аккаунтов. Проверка локальной
Identity БД в read-only режиме показала для обоих ACTIVE/COMPLETED, готовые профиль
и кошелёк. У второй операции между created_at и updated_at около 5.93 s.
В Identity зафиксирован AsyncRequestNotUsableException при записи ответа.

В конфигурации Gateway общий deadline 3 s, локальное ожидание регистрации Identity
12 s. Это указывает на несогласованные таймауты как вероятную причину; HTTP-статус
именно телефонного ответа пока не перехвачен. Общий текст UI скрывает код ошибки.
Регистрацию нельзя считать успешно проверенной. Необходимое изменение серверного
ожидания/deadline следует отдельно обсудить; бэкенд и его настройки не менялись.

## Самостоятельная проверка через ADB — продолжение T008

Устройство SM-S938B / Android 16, та же USB-сборка. До этого пользователь сообщил,
что обычное сохранение и возврат без Save работают; это пользовательское наблюдение,
без независимого подтверждения количества PUT.

Исполнитель самостоятельно управлял телефоном через ADB, считывал UI hierarchy
и просматривал снимки экрана. Временный loopback observer передавал запросы
в настоящий Gateway и записывал только HTTP method/path/status, без тел и заголовков.

- PASS: просмотр профиля; все семь полей видны, version отсутствует. Home/Challenges
  не имеют доступного действия в UI hierarchy. Сохранённые значения здесь не публикуются.
- PASS: открыть Edit и Save без изменений — возврат к исходному профилю, observer
  не зарегистрировал GET/PUT. UI labels до и после совпали.
- PASS: изменение имени только в черновике и уход стрелкой назад — исходный профиль,
  без PUT; UI labels совпали. На просмотренном снимке Save виден над клавиатурой.
- PASS: обновление жестом — один GET /api/v1/accounts/me, реальный ответ 200.
- PASS: force-stop и запуск процесса — POST /api/v1/auth/refresh 200; после открытия
  Profile локальные данные восстановлены, дополнительного GET профиля нет.
- PASS: временная переадресация USB на неработающий порт и жест обновления —
  сообщение Could not update profile, прежние данные остаются видны. Это внедрённый
  сбой соединения, не настоящий отказ Gateway. Первый GET без кэша ещё не проверен.
- Обычный adb reverse на 8088 восстановлен; observer остановлен. Повторный жест
  обновления выполнен после восстановления связи.

Технические артефакты UI/снимки и журнал observer находятся только в игнорируемой
apps/mobile/build/t008; не включать их в коммит. T008 остаётся открытой: нужны
остальные сценарии формы, конфликтов, неопределённого PUT, выхода и смены аккаунта.
