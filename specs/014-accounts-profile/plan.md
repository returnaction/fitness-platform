Использовать существующий стек и Maven Wrapper по [конституции](../constitution.md) и [стандартам](../../docs/engineering-standards.md), без произвольного обновления зависимостей.

- [Gateway OpenAPI](../../contracts/openapi/gateway-v1.yaml) и [Identity OpenAPI](../../contracts/openapi/identity-auth-v1.yaml) — источник существующих ссылок и формата ошибок, не источник новых предположений о настройках runtime.

## Риски и проверки до реализации

Проверить фактическую поддержку Jackson 3 required/null/coercion, способ получения UPDATE RETURNING через текущий persistence-стек и реальные границы Spring-транзакции. Избежать self-invocation, из-за которого объявленная @Transactional граница может не действовать. Не добавлять абстракции сверх необходимых для задачи.

SQL-таймауты и предел ожидания блокировки выбирать после сверки действующего бюджета Gateway; не копировать устаревшие числа из проектных контрактов. Существующие PostgreSQL-тесты могут быть пропущены без Docker: успешный Maven не заменяет свидетельство их выполнения.

Подробные согласованные шаги и критерии ниже; T001–T004 разрешены и завершены 2026-11-13; следующие шаги ожидают отдельных команд.

Передавать в Accounts исходные HTTP-метод, путь, Authorization: Bearer, тело PUT и общий X-Request-Id. Gateway всегда создаёт свой UUID, игнорируя клиентский X-Request-Id, даже корректный; Accounts сохраняет полученный от Gateway ID в ответе. Поля профиля в Gateway не проверять.
Передавать телефону статус и тело ответа Accounts, включая единый формат ошибок и Cache-Control: no-store. Сбои соединения, проверки сессии и таймауты обрабатывать существующими механизмами Gateway.

## 3. ACCOUNTS-SERVICE

### 3.1. Проверить существующую основу
Сверить user_profiles, entity, репозиторий, миграции и создание профиля при регистрации. Не создавать профиль заново при GET или PUT. Не дублировать существующие столбцы и ограничения.
Необходимые поля и уникальный индекс lower(nickname) уже предусмотрены в схеме проекта; фактическое состояние целевой базы проверить отдельно. Миграции пользовательской БД без разрешения не запускать.

### 3.2. Добавить единый формат ошибок
Использовать существующий контракт Identity/Gateway:
error.code, error.message, error.details, error.requestId.
details — список объектов {field, code}; если деталей нет — []. Тексты ошибок полей выбирает и переводит мобильное приложение по кодам; отдельные сообщения в details не передавать. Общий error.message сохранить по существующему контракту. Стабильные коды деталей: required — обязательное значение отсутствует/null; invalid_length — недопустимая длина; invalid_format — недопустимые символы/формат; invalid_value — недопустимое значение; out_of_range — выход за допустимый диапазон. Отсутствующее поле JSON по-прежнему относится к 400 invalid_request, а не к валидации значения. Сохранять общий X-Request-Id.
Добавить ApiErrorResponse и ApiExceptionHandler с @RestControllerAdvice для ошибок контроллера, валидации и сервиса.
Ошибки фильтра и Spring Security обрабатывать отдельно, но возвращать в том же формате: @RestControllerAdvice не перехватывает их автоматически.
Не возвращать клиенту SQL, stack trace, токены и внутренние подробности ошибок.

### 3.3. Создать DTO и настроить разбор JSON
UpdateProfileRequest — Java record для PUT.
ProfileResponse — ответ GET и успешного PUT.
Оба содержат: nickname, firstName, lastName, bio, dateOfBirth, timezone, visibility, version. Явно обеспечить camelCase в JSON DTO и ошибок (включая requestId); в Accounts используются стандартные имена Java DTO без snake_case-переименования.
Для GET request DTO не нужен. Entity напрямую клиенту не возвращать. user_id и public_profile_id в DTO этого сценария не включать.

Все поля PUT обязательны к присутствию: использовать @JsonProperty(required = true) на компонентах record и проверить поведение на используемой конфигурации Jackson.
Явный null разрешён только для firstName, lastName, bio, dateOfBirth.
Version в request DTO — Long, чтобы не подменять отсутствующее значение нулём. Visibility в DTO — ProfileVisibility: JSON-строки PUBLIC и PRIVATE сразу десериализуются в enum и сериализуются обратно такими же строками. Неизвестная строка, неправильный регистр или неверный JSON-тип — 400 invalid_request; явный null проверяется валидатором и даёт 422 validation_error. Не преобразовывать неизвестное enum-значение в null и не принимать числовые ordinal-значения.
Запретить неизвестные поля через FAIL_ON_UNKNOWN_PROPERTIES. Одна @JsonIgnoreProperties(ignoreUnknown = false) не гарантирует строгий разбор.
Некорректный JSON, отсутствующее поле, неизвестное поле или ошибка преобразования типа — 400 invalid_request. Ручной разбор JSON не нужен. На фактическом ObjectMapper проекта (Jackson 3) проверить required, явный null и строгие типы: число вместо строки и дробная version не должны автоматически преобразовываться в допустимые значения. Одного FAIL_ON_UNKNOWN_PROPERTIES для этого недостаточно.
Значения, которые нужно проверять после нормализации, не валидировать преждевременно через @Valid на входе контроллера.

### 3.4. Добавить фильтр пользователя и SecurityContext
Фильтр пользовательского контекста применяется только к GET и PUT /api/v1/accounts/me. Для management и остальных запросов этот фильтр пропускается; доступ к ним определяют отдельные правила SecurityConfiguration. Фильтр подключается только внутри цепочки Spring Security, без повторной регистрации как обычного servlet-фильтра.
Перед контроллером фильтр получает Bearer-токен, извлекает sub как UUID пользователя и роли.
Отсутствующий Bearer, повреждённый токен или отсутствующий/некорректный UUID — 401 invalid_access_token. Некорректный используемый контекст отклонять.
В SecurityContext поместить UUID в principal, известные роли — в authorities как ROLE_<role>. Неизвестные роли прав не дают; отсутствующие или пустые роли не мешают работе со своим профилем. USER автоматически не назначать. Известные коды ролей: USER, MODERATOR, ADMIN, SUPER_ADMIN. Не импортировать entity Identity в Accounts ради этих кодов. Отличать отсутствующий/пустой список ролей от повреждённой структуры claims; повреждённый используемый контекст отклонять.
Контекст изолирован между запросами и очищается после успеха и ошибок.

Accounts в этой схеме доверяет проверке Gateway и повторно не проверяет подпись токена. Для текущего локального HTTP это принятое допущение: личность HTTP caller технически не подтверждается. Не объявлять это защитой серверного развёртывания. Существующий gRPC mTLS сохранить; Docker в этот этап не входит.

### 3.5. Настроить SecurityConfiguration
Подключить фильтр перед проверкой доступа. Требовать authenticated() точно для:
GET /api/v1/accounts/me
PUT /api/v1/accounts/me
Сохранить отдельные правила management. Остальные запросы оставить закрытыми.
Само authenticated() не проверяет токен: оно требует установленного аутентифицированного пользователя в контексте.

### 3.6. Реализовать чтение своего профиля
Контроллер получает UUID из SecurityContext и передаёт его сервису. Сервис через репозиторий читает user_profiles по user_id и формирует ProfileResponse.
Успех — 200 OK. Если профиль отсутствует — 503 profile_unavailable, проблему фиксировать, профиль автоматически не создавать.

### 3.7. Реализовать нормализацию и ProfileUpdateValidator
PUT принимает Content-Type: application/json. Неподдерживаемый Content-Type — 415 unsupported_media_type; пустое тело — 400 invalid_request. Query-параметры GET и PUT не поддерживаются: существующий Gateway отклоняет запросы с query string.
Контроллер PUT получает UUID из SecurityContext и UpdateProfileRequest из тела запроса, затем передаёт их сервису. Владелец не определяется полем из тела запроса.
Сервис до транзакции применяет strip() к nickname, firstName, lastName, bio; внутренние пробелы сохраняются. Пустые firstName, lastName и bio преобразуются в null.
Затем вызывает ProfileUpdateValidator. Валидатор не обращается в БД и собирает все обнаруженные нарушения значений в список {field, code}. Непустой список — 422 validation_error с деталями, без сохранения.

Правила нормализованных значений:
- nickname: не null и не пустой; 3–30 символов, латинские буквы, цифры, _ и -.
- firstName, lastName: null или строка до 100 символов; если заполнена, должна содержать хотя бы одну букву. Разрешены буквы разных языков и относящиеся к ним знаки (в том числе ударения), внутренние обычные пробелы, дефис, обычный апостроф U+0027 и типографский U+2019. Цифры, emoji, табуляции и переносы строк запрещены. Внутренние пробелы сохраняются.
- bio: null или обычный текст до 500 символов, в соответствии с существующим ограничением PostgreSQL VARCHAR(500). Разрешены emoji и переносы строк; HTML и Markdown не интерпретируются как разметка. Серверную проверку длины согласовать с ограничением БД, не вводить другой лимит из-за UTF-16 в Java. Ограничения длины имён также согласовать с существующими VARCHAR(100).
- dateOfBirth: null или дата YYYY-MM-DD; от текущей даты UTC минус 150 лет до текущей даты UTC включительно. В Java LocalDate, в PostgreSQL DATE, без преобразования часового пояса даты рождения.
- timezone: обязательный существующий часовой пояс IANA.
- visibility: уже разобранный enum PUBLIC или PRIVATE; валидатор проверяет, что значение не null. Неизвестные enum-значения отклоняются при десериализации с 400.
- version: не null, положительное целое число.

Недопустимые для хранения текстовые значения, включая U+0000 (JSON-escape \u0000), отклонять до обращения к БД с 422 validation_error и деталью invalid_format для соответствующего поля. Это не должно превращаться в техническую ошибку 503. Обычные emoji и переносы в bio разрешены.
Проверки значений выполнять после strip(). Ошибки разбора JSON возникают раньше и не обязаны собираться в общий список нарушений валидатора. Для типизированных DTO значения, которые невозможно преобразовать в выбранный тип, относятся к 400; остальные нарушения правил — к 422.

### 3.8. Реализовать сохранение с проверкой версии
Нормализация и валидация выполняются вне транзакции. После успешной валидации открыть короткую транзакцию, охватывающую UPDATE и при необходимости проверку наличия профиля. Репозиторий выполняет один UPDATE всех изменяемых полей с условием:
WHERE user_id = :userId AND version = :expectedVersion
При успехе увеличить version на один, обновить updated_at и получить обновлённую строку через RETURNING.
Версию увеличивать и при сохранении прежних значений. Частичное сохранение запрещено. Сетевых вызовов внутри транзакции нет.

Если UPDATE не изменил строку, проверить наличие профиля: существует — 409 profile_version_conflict; отсутствует — 503 profile_unavailable.
Уникальность ника обеспечивает существующий индекс user_profiles_nickname_unique на lower(nickname). Нарушение именно этого индекса — 409 nickname_already_taken; транзакция откатывается. Не переводить все ошибки целостности в ошибку занятого ника. Перевод нарушения уникальности в HTTP-ошибку выполняется после отката транзакции; не продолжать SQL-запросы внутри провалившейся транзакции. Ограничить время выполнения SQL и ожидания блокировок, согласовав таймауты с бюджетом запроса Gateway. Таймаут Gateway сам по себе не гарантирует остановку SQL или откат; проверить это поведение отдельно.
Свой текущий ник, включая изменение регистра, разрешён. Ник можно менять сколько угодно, без периода ожидания. После успешной смены старый ник сразу доступен другим пользователям; резервирование и история ников в этап не входят. Прежние ограничения символов nickname сохраняются: латиница, цифры, _ и -. Предварительный SELECT для проверки занятости не нужен.
Дополнительный ручной lock, повышение уровня изоляции и INSERT ON CONFLICT для этой операции не нужны. Использовать READ COMMITTED и атомарный UPDATE по версии.
Ключ идемпотентности не нужен. Повтор успешного запроса со старой версией может вернуть 409.

### 3.9. Вернуть результат
После успешного завершения транзакции вернуть 200 OK и ProfileResponse с сохранёнными значениями и новой версией.
Ответы GET и PUT возвращать с Cache-Control: no-store. Возвращать все восемь полей ProfileResponse; необязательные пустые значения передавать как явный null, не исключать их при сериализации.

## 4. ОШИБКИ И HTTP-СТАТУСЫ

- 400 invalid_request — некорректный JSON, пустое тело PUT, отсутствие поля, неизвестное поле, неизвестное enum-значение, ошибка преобразования типа или неподдерживаемые query-параметры.
- 401 invalid_access_token — ошибка аутентификации; истечение токена и недействительную сессию проверяет Gateway.
- 415 unsupported_media_type — неподдерживаемый Content-Type PUT.
- 422 validation_error — нарушение правил значений, с деталями по полям.
- 409 nickname_already_taken — ник занят другим пользователем.
- 409 profile_version_conflict — устаревшая версия профиля.
- 503 profile_unavailable — профиль отсутствует или временно недоступна его база.
- 500 internal_error — непредвиденная ошибка.

Существующие ошибки Gateway и стандартные ошибки HTTP сохраняются; этот список не заменяет общий контракт проекта.
Телефон обрабатывает ошибки по code, а не по message. При техническом сбое результат сохранения может быть неизвестен клиенту; нельзя обещать, что любой ответ 5xx означает отсутствие изменений.

## 5. ПОВЕДЕНИЕ МОБИЛЬНОГО ПРИЛОЖЕНИЯ (ТРЕБОВАНИЯ НА БУДУЩЕЕ, БЕЗ РЕАЛИЗАЦИИ В ЭТОМ ЭТАПЕ)

Первое открытие Account — GET и сохранение профиля в памяти приложения. Переключение между экранами не вызывает повторный запрос. Жест «потянуть вниз» выполняет новый GET. После перезапуска приложения первое открытие снова выполняет GET.
При открытии редактирования форма заполнена текущими данными. null показывается пустым полем. При сохранении телефон отправляет все поля и версию, соответствующую данным формы; пустые необязательные поля отправляет как null.
Пока PUT выполняется, повторное нажатие «Сохранить» отключено. При успехе данные в памяти заменяются ответом PUT.
При ошибке обновления сохраняются прежние данные. При конфликте телефон перечитывает и показывает актуальный профиль, отдельно сохраняя несохранённый черновик. Пользователь переносит нужные изменения в актуальную форму и повторно нажимает «Сохранить». Автоматическое объединение, подстановка новой версии и перезапись старой формой запрещены.
При обрыве связи телефон перечитывает профиль для выяснения текущего состояния.
При выходе или смене аккаунта профиль в памяти очищается; поздние ответы запросов прежнего аккаунта игнорируются.
Cache-Control: no-store запрещает HTTP-кэширование и не мешает хранению профиля в памяти приложения.

## 6. ПРОВЕРКИ И КРИТЕРИИ ЗАВЕРШЕНИЯ

Gateway: маршруты GET/PUT, проверка JWT и CheckSession, отсутствие пересылки при отказе, сохранение Bearer, тела PUT, request_id, статусов и no-store; ошибки соединения и таймауты.
Accounts: единый формат ошибок, стабильные коды деталей без текстов полей, очистка и изоляция SecurityContext, UUID и роли, фильтр только на GET/PUT /me, отсутствие двойной регистрации фильтра, доступность предусмотренных management-операций без пользовательского Bearer, запрет остальных маршрутов, доступ только к своему профилю.
DTO: обязательное присутствие всех полей, допустимый null, неизвестные поля, неверные типы без автоматического преобразования, enum visibility (включая неизвестное значение, число и null), camelCase, все поля ответа с явным null, нормализация до проверки длины. HTTP: Content-Type, пустое тело и запрет query-параметров.
Валидатор: границы длины и даты, допустимые символы, имена с апострофами и знаками ударения, отказ для имени из одних дефисов, emoji и переносы в bio, согласованность длины с БД, timezone, visibility, version, сбор нескольких нарушений, отклонение U+0000 до обращения к БД.
PostgreSQL: GET после PUT, очистка полей, свой ник и смена регистра, конфликт ника без учёта регистра, конкурентное занятие одного ника, два UPDATE с одной версией, rollback без частичных изменений, отсутствие профиля и ошибки базы, ограничение ожидания блокировок и поведения при таймаутах.
Сквозной сценарий: вход через Gateway → GET своего профиля → PUT → повторный GET; отсутствие регрессии создания профиля при регистрации.
Использовать существующий механизм PostgreSQL-интеграционных тестов, включая Testcontainers. Некоторые существующие тесты пропускаются без Docker: явно фиксировать skips и не считать успешный Maven доказательством выполненных проверок БД. Testcontainers для тестов не означает добавление PostgreSQL в пользовательский Docker Compose или подготовку серверного развёртывания. Проверка работы на телефоне не является условием завершения серверного этапа; сценарии проверить через API.
