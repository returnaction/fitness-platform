## Цель

После регистрации и входа пользователь мобильного приложения получает свой уже созданный профиль и может сохранить изменения его данных. Два телефона не должны незаметно перезаписывать изменения друг друга.

## Границы

Входит только серверная работа: OpenAPI, Gateway, Accounts, документация и тесты. Внешние операции — `GET /api/v1/accounts/me` и `PUT /api/v1/accounts/me`. Accounts владеет профилем; Identity сохраняет владение учётной записью, паролем и сессиями.

Не входят: реализация мобильного приложения, просмотр чужих профилей, публичные ссылки, аватары, изменение пароля/email, предварительная проверка доступности ника, история/резервирование ников, новые события/брокеры, развёртывание Docker и защита сервера. Content-Encoding остаётся отложенной работой Spec 013. Visibility в этом этапе только сохраняется.

[Spec 013](../013-pending/spec.md) завершена в согласованном локальном объёме; её разрешения на реализацию и коммиты не переносятся. Пользователь разрешил T001–T003, включая проверки Gateway и подготовку HTTP Accounts, без коммита. Эти задачи завершены; T004–T010 ожидают отдельных команд.

Для настройки Gateway используются `UpstreamId.ACCOUNT`, ключ
`gateway.upstreams.services.ACCOUNT` и переменная `ACCOUNT_HTTP_BASE_URL`.
Эти имена согласованы пользователем 2026-11-13; название сервиса Accounts
и пути `/api/v1/accounts/me` сохраняются.

## Пользователи и права

Обе операции требуют проверенного Gateway access-токена и активной сессии (CheckSession в Identity по существующему gRPC mTLS). Gateway пересылает исходный Bearer, метод, путь и тело. Gateway всегда генерирует собственный UUID request_id, игнорируя клиентский X-Request-Id даже при корректном UUID. Accounts получает этот ID от Gateway и сохраняет его в ответе; тот же ID возвращается клиенту в X-Request-Id и error.requestId.

Accounts использует UUID из sub как владельца: `principal = UUID`, известные роли — в authorities. Поддерживаемые коды: USER, MODERATOR, ADMIN, SUPER_ADMIN; отображение ROLE_<role>. Неизвестные строки не дают прав, отсутствующий/пустой список не означает USER и не мешает работе со своим профилем. Повреждённый используемый контекст отклоняется. user_id из тела или клиентского заголовка не используется.

Фильтр применяется только к точным GET/PUT `/api/v1/accounts/me`, подключается один раз внутри Spring Security. Для этих операций требуется authenticated(); существующие management-правила сохраняются, остальные запросы закрыты. Контекст изолирован и очищается после успеха и ошибок.

**Локальное допущение:** Accounts разбирает Bearer без повторной проверки подписи и доверяет Gateway. Личность HTTP caller технически не подтверждается; прямой локальный запрос с подделанными claims этим подходом не исключается. Это не доказательство серверной безопасности. gRPC mTLS сохраняется.

## API и данные

GET и успешный PUT возвращают `200 OK`, `Cache-Control: no-store`, общий `X-Request-Id` и все восемь полей ProfileResponse. Необязательные значения возвращаются явным null, а не исключаются. user_id, public_profile_id, служебные даты и entity не выдаются в этом DTO.

PUT — полная форма из восьми полей. Все поля обязаны присутствовать, даже nullable. При открытии редактирования телефон использует ранее полученные значения и соответствующую version. PUT принимает application/json. Query-параметры не поддерживаются.

| Поле | Правило после нормализации |
| --- | --- |
| nickname | Не null/пустой, 3–30 ASCII-символов: латинские буквы, цифры, `_`, `-`; уникален без учёта регистра. |
| firstName, lastName | Null или до 100 символов каждый, хотя бы одна буква. Буквы разных языков и относящиеся к ним знаки, внутренние обычные пробелы, дефис, апострофы U+0027 и U+2019. Без цифр, emoji, табуляций и переносов строк. |
| bio | Null или обычный текст до 500 символов по ограничению PostgreSQL VARCHAR(500). Emoji и переносы разрешены; HTML/Markdown не интерпретируются. |
| dateOfBirth | Null или YYYY-MM-DD: от текущей даты UTC минус 150 лет до текущей даты UTC включительно. Java LocalDate / PostgreSQL DATE, без смещения по timezone пользователя. |
| timezone | Не null, существующий часовой пояс IANA. |
| visibility | Enum PRIVATE / PUBLIC, не null. |
| version | Положительное целое, DTO Long; обязательное ненулевое значение. |

Перед валидацией применить strip() к nickname, firstName, lastName, bio; внутренние пробелы сохраняются. Пустые необязательные строки превращаются в null. Длину имён и bio проверять согласно существующим VARCHAR(100/500), а не вводить меньший лимит из-за UTF-16 Java. Недопустимый для хранения U+0000 отклонять до БД с 422/invalid_format.

Ник можно менять сколько угодно. Свой текущий ник и изменение его регистра разрешены. После успешной смены старый ник сразу доступен другим пользователям.

### Разбор и валидация

UpdateProfileRequest — record; обязательное присутствие через @JsonProperty(required = true), строгие неизвестные поля и типы. На фактическом Jackson проверить, что число не превращается в строку, дробная version в Long, а число в ordinal enum. Ручной разбор JSON не требуется.

Visibility сразу десериализуется в ProfileVisibility: неизвестная строка/регистр/тип → 400; явный null → 422. Дата, которую невозможно преобразовать в LocalDate, → 400; корректная дата вне диапазона → 422.

ProfileUpdateValidator проверяет нормализованные значения без обращения в БД и собирает все обнаруженные нарушения значений. Ошибки разбора тела возникают раньше и не обязаны собираться вместе с ними. Не выполнять проверки длины/содержимого через ранний @Valid до strip().

## Сценарии

### Чтение

**Дано:** профиль создан при регистрации. **Когда:** разрешён GET. **Тогда:** Accounts читает его по UUID из контекста и возвращает данные. Отсутствующий профиль не создаётся: 503 profile_unavailable и безопасная фиксация проблемы.

### Сохранение

**Дано:** клиент получил профиль версии N. **Когда:** PUT содержит все допустимые поля и version N. **Тогда:** атомарно обновляются поля, updated_at и version до N+1; после commit возвращается сохранённый профиль. Даже неизменившиеся значения увеличивают версию.

### Два телефона

**Дано:** два запроса используют версию N. **Когда:** первый сохранён. **Тогда:** второй не перезаписывает данные и получает 409 profile_version_conflict. Нельзя автоматически подменять ожидаемую версию и повторять сохранение.

### Занятый ник

Регистронезависимая уникальность обеспечивается существующим индексом user_profiles_nickname_unique на lower(nickname). Конфликт с другим владельцем → откат всего UPDATE и 409 nickname_already_taken. Предварительный SELECT не обеспечивает корректность и для сохранения не нужен.

### Потерянный ответ

Ключ идемпотентности не нужен. После успешного commit ответ может потеряться; повтор со старой версией возвращает конфликт. Клиент перечитывает профиль. Техническая ошибка/таймаут не доказывают, что данные не сохранены.

## Ошибки

Использовать существующий формат Identity/Gateway: error.code, error.message, error.details, error.requestId. details — объекты field/code, без текстов по полям; при отсутствии деталей []. Общий message сохраняется, локализованные тексты телефон выбирает по кодам.

| HTTP / code | Причина |
| --- | --- |
| 400 invalid_request | Некорректный JSON, пустое тело PUT, отсутствующее/неизвестное поле, неизвестный enum, неверный тип, query string. |
| 401 invalid_access_token | Отказ аутентификации; JWT/сессию проверяет Gateway, структуру используемого контекста — Accounts. |
| 415 unsupported_media_type | Неподдерживаемый Content-Type PUT; это не изменение отложенного Content-Encoding. |
| 422 validation_error | Разобранные значения нарушают правила; все обнаруженные детали валидатора. |
| 409 nickname_already_taken | Нарушен именно индекс уникальности ника. |
| 409 profile_version_conflict | Профиль существует, но версия устарела. |
| 503 profile_unavailable | Профиль отсутствует или недоступна его база. |
| 500 internal_error | Непредвиденный сбой. |

Стабильные коды деталей: required (обязательное значение null/пусто), invalid_length, invalid_format, invalid_value, out_of_range. Отсутствующее поле JSON относится к 400, а не required в 422. Существующие транспортные и стандартные ошибки Gateway сохраняются.

## Транзакции и конфиденциальность

Нормализация/валидация вне транзакции. Короткая транзакция READ COMMITTED: UPDATE всех изменяемых полей WHERE user_id = :userId AND version = :expectedVersion, version + 1, updated_at, RETURNING. Если строк нет — уточнить наличие профиля. Сетевых вызовов внутри нет, частичного сохранения нет. Дополнительный ручной lock, повышение изоляции, INSERT ON CONFLICT не требуются.

После нарушения уникальности выполнить rollback до формирования ошибки; не продолжать запросы в провалившейся транзакции. Ограничить SQL и ожидание блокировок с учётом бюджета Gateway, проверить фактическое поведение таймаутов. Таймаут HTTP не равнозначен отмене SQL.

Не логировать токены, профиль/персональные данные, SQL-параметры и секреты. Ошибки не раскрывают stack trace и внутренние подробности. Единственное определение таблицы остаётся у [Accounts](../../system-design/services/accounts/32-accounts-profile.md); новые таблицы не нужны по текущей схеме.

## Мобильное поведение — справочно, не реализация этапа

Первое открытие → GET и память приложения; переход между экранами без GET; pull-to-refresh → GET. После PUT память обновляется ответом. Перезапуск требует нового чтения; выход/смена аккаунта очищает память, поздние ответы прежнего аккаунта игнорируются.

Форма заполнена полученными значениями, null отображается пустым полем. Во время PUT кнопка сохранения отключена. Ошибка обновления не стирает данные. При конфликте показывается актуальный профиль и отдельно сохраняется черновик: пользователь переносит нужные изменения вручную. Автоматическое объединение/перезапись запрещены. no-store не мешает памяти приложения.

## Критерии готовности

- [ ] OpenAPI Accounts и Gateway согласованы, ссылки валидны, примеры соответствуют DTO.
- [ ] Gateway применяет JWT/CheckSession, корректно пересылает запросы и ответы.
- [ ] Accounts устанавливает и очищает контекст, запрещает чужой профиль и непредусмотренные пути.
- [ ] GET/PUT, null, строгий JSON, enum, нормализация и все правила полей проверены.
- [ ] PostgreSQL подтверждает уникальность, конфликт версий, rollback и ограничение ожидания.
- [ ] Ошибки/заголовки соответствуют общему контракту, результат неизвестен при потерянном ответе.
- [ ] Существующее создание профиля при регистрации и auth-пути не сломаны.
- [ ] Проверки Maven Wrapper, форматирования и анализа выполнены; пропуски явно записаны.
- [ ] Связанные документы актуализированы; состояние не объявлено серверной защитой или готовым мобильным приложением.
