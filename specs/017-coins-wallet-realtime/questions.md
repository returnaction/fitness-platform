# Решения Spec 017

- Пользователь выбрал обновление баланса через HTTP GET. Постоянный канал
  обновлений в эту спецификацию не входит.
- Coins — источник истины для `availableBalance` и `lockedBalance`; ответ
  повторной операции является историческим снимком и не заменяет запрос
  актуального баланса.
- GET получает только баланс владельца: Gateway проверяет JWT и сессию,
  затем пересылает `Authorization`; Coins по образцу Accounts извлекает claims
  и `sub` без повторной валидации JWT или сессии.
- Балансы документируются как JSON `integer` формата `int64`; это соответствует
  `BIGINT` в Coins и передаётся вызывающей стороне обычным JSON-числом.
- Все ответы имеют `Cache-Control: no-store`. Ошибки используют локальный
  `ApiErrorResponse` и `ApiExceptionHandler`: 401 `invalid_access_token`, 500
  `wallet_invariant_violation`, 503 `coins_unavailable`, 500 `internal_error`.
- Owner-контракт — `contracts/openapi/coins-wallet-v1.yaml`; Gateway ссылается
  на него через `$ref`, не дублирует схемы и документирует 503
  `coins_unavailable` как публичный ответ маршрута.
- Порядок реализации: контракт, затем Gateway с mock upstream, затем Coins и
  только после этого сквозная проверка Gateway → Coins.
- Реализация Spec 017 завершена; пользователь разрешил ревью и исправления
  в существующей ветке. Проверки и ограничения записаны в
  [verification.md](verification.md). Commit, push, merge и deploy в рамках
  этого обновления документов не выполняются.

## Отложено: длительная недоступность БД

- Затрагивает T004.9, T005.4 и итоговую проверку T006.
- Подтверждено: после обрыва существующего соединения Gateway возвращает
  503 coins_unavailable; после восстановления БД — 200.
- Пользователь удалил явные connection-timeout=3000 и validation-timeout=1000
  и попросил отложить настройку таймаутов. Они не восстановлены.
- Не подтверждено: ответ при длительном ожидании нового соединения с БД
  успевает прийти до дедлайна Gateway 7s.
- Варианты: отдельно измерить текущую конфигурацию и согласовать таймауты
  либо оставить вопрос открытым до следующей разрешённой проверки.
- Рекомендация: перед окончательным закрытием проверки отказов выполнить
  сценарий длительной недоступности и принять решение по результату.
  Пока этот сценарий не считать пройденным.
