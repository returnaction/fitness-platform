# План реализации: мобильный Flutter-клиент и аутентификация

> **Спецификация:** [spec.md](spec.md)  
> **Статус:** implemented
> **Связанные документы system-design:** [Identity: регистрация](../../system-design/services/identity/30-identity-registration.md), [Identity: вход и сессии](../../system-design/services/identity/31-identity-login-sessions.md)

## Краткое решение

Создать новый Android Flutter-проект в `apps/mobile`, не перенося старый Python API
клиент буквально. UI управляет гостевой и аутентифицированной навигацией;
репозиторий аутентификации использует Identity OpenAPI v1 через единственный
адрес Gateway. Единый coordinator последовательно выполняет операции с парой
токенов; строгая ротация на стороне Identity остаётся конечной защитой. Макет следует согласованному
синему Material 3 интерфейсу, включая чекбокс показа пароля. Токены хранятся через защищённое
хранилище платформы, а refresh выполняется последовательно для одного запроса.

## Затрагиваемые границы

| Область | Изменение | Владелец данных / контракта |
| --- | --- | --- |
| `apps/mobile` | Новый Flutter-клиент, экраны и локальное защищённое хранение | Мобильное приложение |
| Identity Service | Используется без изменений | Identity владеет REST API, пользователями и сессиями |
| Gateway Service | Существующая точка входа для всех пяти auth-операций | Gateway владеет маршрутизацией, входными проверками и транспортными ошибками |
| `contracts/openapi/identity-auth-v1.yaml` | Источник HTTP-контракта; не меняется без отдельного решения | Identity |

## Данные и миграции

- Новые или изменяемые данные: локальная пара access/refresh tokens в одном значении secure storage и временный ключ повтора регистрации.
- Владелец данных: сессии и пользователи остаются в Identity; приложение владеет только данными устройства.
- Миграция и обратная совместимость: серверные миграции не требуются.
- Идемпотентность: UUID v4 передаётся только для регистрации и сохраняется для её повторной отправки в рамках незавершённого действия с неизменными email и password. Изменение любого из этих полей создаёт новый UUID в памяти формы.

## Контракты и взаимодействия

| Направление | Тип | Изменение | Версионирование / совместимость |
| --- | --- | --- | --- |
| Flutter → Gateway → Identity | REST | `register`, `login`, `refresh`, `logout`, `logout-all` по OpenAPI v1 | Пути и DTO Identity сохраняются; дополнительные ошибки описывает Gateway v1 |

Регистрация посылает `Idempotency-Key` и получает токены в `session`. Login и
refresh получают `SessionTokens` в корне ответа. Logout принимает refresh token
и возвращает `204`. Ошибки разбираются как `{error: {code, message, details?, request_id}}`.
Logout-all передаёт Bearer access token; Gateway проверяет JWT и активность
сессии через CheckSession. Остальные четыре маршрута не требуют access JWT.
Клиент не проверяет JWT сам и не обходит Gateway: Identity остаётся владельцем
паролей, refresh-token и окончательных правил сессии.

## План перехода на Gateway

Основание: [Gateway v1](../../contracts/gateway-v1.md),
[Spec 009](../009-gateway-access/spec.md),
[локальный запуск Gateway](../../services/gateway-service/README.md).

1. **G1 — сверка контрактов.** Проверить пять POST-маршрутов, авторизацию,
   заголовки `Idempotency-Key`, `Authorization`, `Retry-After`, `Cache-Control`
   и формат ошибок. Порт 8088 взят из `.env.example`; фактический порт стенда
   проверить отдельно, не выводя секреты окружения.
2. **G2 — конфигурация клиента.** Поменять default `API_BASE_URL` на
   `http://10.0.2.2:8088`, сохранить переопределение адреса Gateway через
   `--dart-define`. Проверить все вызовы клиента на отсутствие адресов Identity
   и обходных повторов. Сохранить HTTP по согласованному решению.
3. **G3 — отказы и сессия.** Ввести единый coordinator, последовательно
   выполняющий `refresh`, `logout` и `logout-all`, чтобы один refresh-token не
   отправлялся параллельно. Разделить подтверждённый отказ авторизации,
   временный `503`, сетевой сбой и `502`/`504`. Для подтверждённого
   `503 identity_unavailable` сохранять токены и показывать временную
   недоступность; при сетевом сбое, `502` или `504` после refresh удалять пару
   как результат неопределённой обработки и не повторять старый token. Явный
   logout очищает локальную сессию даже при отказе Gateway. Обработать `429` с
   `Retry-After` и безопасные сообщения для `413`, неизвестных кодов и ответов
   без ожидаемого JSON.
4. **G4 — автоматические проверки.** Проверить адрес назначения всех пяти
   операций, неизменные пути/тела, заголовки регистрации и logout-all,
   сохранение токенов при временном отказе, очистку при явном выходе и отсутствие
   повторов refresh после неопределённого результата. Добавить widget-тесты
   состояний недоступности и ошибок. Выполнить formatter, analyze, tests и APK build.
5. **G5 — Android и реальный Gateway.** На согласованном тестовом стенде пройти
   регистрацию, вход, восстановление сессии после перезапуска и оба выхода на
   Android Emulator. При доступности телефона пройти ту же проверку по USB:
   сначала дождаться явного сообщения пользователя «телефон подключён, adb
   видит устройство», затем проверить `adb devices`, выполнить `adb reverse
   tcp:8088 tcp:8088` и передать `API_BASE_URL=http://127.0.0.1:8088`.
   Подтвердить прохождение запросов через Gateway без записи секретов в логи.
   Проверить временную недоступность и отказ отозванного access на logout-all.
   Не запускать миграции пользовательских БД или остановку чужих сервисов без
   разрешения; при отсутствии стенда или телефона оставить соответствующую
   проверку открытой.
6. **G6 — документация.** Обновить mobile README: запуск Gateway и его
   зависимостей, адрес эмулятора, override и границы проверки. Сохранить
   loopback-настройки сервисов: физический телефон требует отдельно проверенного
   способа подключения, публикация Identity в LAN не является решением.

## Надёжность и безопасность

- Локальная валидация улучшает UX, но сервер остаётся источником истины.
- При запуске с сохранённой парой выполняется один refresh через coordinator. После неопределённого сетевого результата, `502` или `504` старая пара удаляется и refresh-token не повторяется: Java Identity расценивает повтор использованного токена как replay и отзывает сессию. Подтверждённый `503 identity_unavailable` сохраняет пару и предлагает явный повтор.
- Access и refresh tokens сохраняются одним значением secure storage. Ошибка записи не переводит приложение в аутентифицированное состояние; ошибка очистки сообщает о неподтверждённом локальном выходе без раскрытия секретов.
- Универсального auto-refresh/retry interceptor нет: будущий retry для защищённого чтения проектируется вместе с соответствующим API. Изменяющие запросы автоматически не повторяются.
- Сетевой сбой logout не мешает удалить локальные токены.
- Пароли, токены, `Idempotency-Key`, заголовки авторизации и полные тела ошибок не логируются.
- HTTP разрешён по решению владельца проекта, включая release-сборки. Он подходит только для доверенной сети и не обеспечивает конфиденциальность токенов.

## Проверка

- Unit-тесты: разбор Gateway-ошибок, регистрация с ключом и его смена после изменения формы, атомарное хранение токенов, coordinator, refresh и logout.
- Widget-тесты: переходы гость → регистрация/вход → главный экран → выход,
  сообщения ошибок и переключение `Show password`.
- Ручная проверка: Android Emulator → локальный Gateway → Java Identity.

## Риски и решения

| Риск или открытый вопрос | Решение / кто принимает решение |
| --- | --- |
| Адрес localhost различается на эмуляторе и устройстве | Эмулятор использует Gateway `http://10.0.2.2:8088`; для подключённого по USB телефона используется `adb reverse` и `http://127.0.0.1:8088`. URL Gateway другого окружения передаётся через `--dart-define`; Identity в LAN не публикуется. |
| Старый Flutter-код расходится с Java OpenAPI | Java OpenAPI имеет приоритет; переносить только применимые UI и безопасные технические решения. |
| Нет API для данных главного экрана | Первый экран не запрашивает неподтверждённый `/users/me`; его содержание согласуется отдельно. |
| Потеря ответа refresh | В текущем Java-контракте повтор опасен; пользователь входит заново. Идемпотентный refresh требует отдельной backend-спецификации. |
