## Переход Flutter на Gateway

Порядок и критерии проверки описаны в [плане перехода](plan.md#план-перехода-на-gateway).
Эти задачи дополняют незавершённую реализацию клиента; готовность Spec 009
сама по себе не подтверждает переключение Flutter.

- [x] **G1 [Контракты]** Сверить пять маршрутов и заголовки клиента с Gateway v1; зафиксировать фактический API-порт тестового стенда.
- [x] **G2 [Конфигурация, после G1]** Переключить default `API_BASE_URL` на Gateway `http://10.0.2.2:8088`; проверить override и отсутствие прямых обращений/fallback к Identity.
- [x] **G3 [Ошибки, после G1]** Ввести coordinator для последовательных `refresh`/logout-операций. Сохранять токены только при подтверждённом `503 identity_unavailable`; при сетевом сбое, `502` или `504` refresh удалять пару и не повторять старый token. Разделить неопределённый refresh и явный выход; обработать `429`/`Retry-After`, `413` и неизвестные ответы.
- [x] **G4 [Тесты, после G2–G3]** Проверить все пять операций через адрес Gateway, заголовки, состояния сессии, ошибки secure storage, смену Idempotency-Key после изменения формы и отсутствие опасных повторов; выполнить анализатор, тесты и Android-сборку.
- [x] **G5 [Сквозная проверка, после G4]** Проверить Android Emulator с реальным Gateway: регистрацию, login, перезапуск/refresh, logout, logout-all, временную недоступность и отказ отозванной сессии. При доступности телефона после сообщения пользователя «телефон подключён, adb видит устройство» выполнить отдельную USB-проверку через `adb reverse tcp:8088 tcp:8088`. Записать результаты и ограничения без секретов.
- [x] **G6 [Документация, после G2–G5]** Обновить mobile README и результаты Spec 008: адрес Gateway, запуск зависимостей, override, ограничения физического телефона и реально выполненные проверки.

- [x] G5: На телефоне через loopback fault proxy проверить однократный 503
  до обработки refresh и потерю ответа после успешного refresh реальным Gateway.
  Проверить явный повтор после 503, отсутствие повтора после потери ответа,
  восстановить прямой USB-маршрут; отделить искусственные отказы от реального backend.

- [x] Исключить повтор старого refresh после завершения процесса во время запроса: удалить старую пару до отправки, восстановить её только после подтверждённого `503 identity_unavailable`. Проверены порядок операций, ошибка удаления и ошибка записи новой пары.
- [x] При ошибке secure storage предлагать очистку локальной сессии, без автоматического refresh; проверить переход в Welcome после очистки.
- [x] Обработать ошибку записи токенов в форме, блокировать поля во время отправки и исправить возврат на Welcome после ошибки login.
- [x] Widget-тестами проверить Show password в регистрации и сохранение/смену Idempotency-Key при повторе/изменении пароля.
- [x] Проверить пять HTTP-операций на уровне Dio: единый Gateway URL, методы, тела, Idempotency-Key и Bearer только для logout-all; ошибки 413/429/502/503/504, Retry-After и неожиданные типы error-полей без повторов.
