# Мобильный Flutter-клиент: основа и аутентификация

> **Статус:** implemented
> **Номер:** 008  
> **Связанные документы:** [Identity OpenAPI v1](../../contracts/openapi/identity-auth-v1.yaml), [регистрация](../001-user-registration/spec.md), [выход из сессии](../003-session-logout/spec.md), [вход и сессии Identity](../../system-design/services/identity/31-identity-login-sessions.md)  
> **Заменяет / заменена:** —

## Цель

Создать самостоятельное Flutter-приложение в `apps/mobile`, которое является
клиентом Java/Spring auth API через Gateway Service. Identity остаётся владельцем
пользователей и сессий. В первой версии
пользователь видит главный экран, может зарегистрироваться, войти и выйти из
своей сессии.

## Границы

### Входит в эту спецификацию

- Android-каркас Flutter-приложения, навигация и настройка адреса API для Android Emulator и подключённого по USB телефона.
- Начальный экран для гостя и главный экран для аутентифицированного пользователя.
- Регистрация, вход, безопасное локальное хранение пары токенов и выход из текущей сессии.
- Использование существующего REST-контракта Identity v1 через Gateway без изменения Java-сервисов.
- Переключение всех пяти auth-операций на единственный клиентский адрес Gateway
  по [контракту Gateway v1](../../contracts/gateway-v1.md) и
  [Spec 009](../009-gateway-access/spec.md).

### Не входит в эту спецификацию

- Экран профиля, челленджи, модерация, видео и любые API помимо Identity.
- Изменение API, базы, миграций или бизнес-правил Java/Spring-сервисов.
- Публикация в магазины, production-инфраструктура и восстановление пароля.

## Пользователи и права

| Роль | Что может делать |
| --- | --- |
| Гость | Открыть стартовый экран, зарегистрироваться или войти. |
| Аутентифицированный пользователь | Открыть главный экран и завершить текущую сессию на данном устройстве. |

## Сценарии

### Сценарий: регистрация

**Дано:** у гостя нет сохранённой сессии.  
**Когда:** он вводит допустимые email и пароль и подтверждает регистрацию.  
**Тогда:** клиент отправляет `POST /api/v1/auth/register` с UUID v4 в
`Idempotency-Key`, сохраняет токены из `session` успешного ответа и открывает
главный экран.

### Сценарий: вход и выход

**Дано:** пользователь зарегистрирован.  
**Когда:** он успешно входит.  
**Тогда:** клиент безопасно сохраняет полученную пару токенов и открывает
главный экран. Иконка выхода в AppBar открывает варианты `Log out` и `Log out
from all devices`; второй вариант требует подтверждения. При выходе клиент
удаляет локальные токены даже при сетевой ошибке и показывает стартовый экран.

### Ошибки и граничные случаи

| Условие | Ожидаемое поведение для клиента |
| --- | --- |
| Ошибка валидации, неверные данные, лимит или временная ошибка Identity | Показать безопасное понятное сообщение; не считать пользователя вошедшим. |
| Ответ регистрации потерян или получен `503 registration_unavailable` | Дать повторить запрос с тем же сохранённым ключом и данными, пока форма открыта. |
| Refresh-token не пригоден при запуске или запросе | Удалить локальную пару и вернуть пользователя на стартовый экран. |
| Результат refresh неопределён: потеря ответа, сетевой сбой, `502` или `504` | Не повторять старый refresh-token: сервер мог принять запрос, а повторное использование отзывает сессию. Удалить локальную пару и предложить вход. |
| Сеть недоступна при выходе | Удалить локальную пару; удалённый выход может остаться неподтверждённым. |
| Gateway сообщает подтверждённый временный `503 identity_unavailable` при refresh | Сохранить токены: этот ответ не означает отзыв сессии. Показать отдельный экран временной недоступности с `Try again` и `Log out on this device`; второй вариант удаляет только локальную пару без сетевого запроса. |
| Gateway недоступен или вернул `502` / `504` | Не переключаться напрямую на Identity. При неопределённом результате refresh не повторять старый токен; для регистрации сохранить ключ повтора. |

## Визуальный интерфейс

- Интерфейс на английском использует Material 3 с выраженным синим основным
  цветом, как в согласованном макете. Название на welcome-экране — `Fitness App`.
- Welcome-экран содержит спортивную иконку, название, короткое описание и
  действия `Sign in` и `Create account`.
- Формы входа и регистрации содержат поля `Email` и `Password`, а также
  чекбокс `Show password`. При включении чекбокса текущее значение поля
  показывается на экране; при выключении снова маскируется. Это не меняет
  правила хранения: пароль остаётся только в памяти формы.
- После входа показан минимальный экран `You are signed in`. В правой части
  AppBar расположена иконка выхода. Нажатие открывает нижнее меню с действиями
  `Log out` и `Log out from all devices`; второе действие подтверждается
  отдельным диалогом.

## Бизнес-правила

- Токены, пароль и `Idempotency-Key` не выводятся в логи, сообщения об ошибке или аналитику.
- При успешной регистрации пара токенов берётся из `session`; отдельный login не выполняется.
- Для повторной регистрации одного незавершённого действия клиент использует тот же UUID, но не хранит пароль долговременно.
- UUID регистрации привязан к снимку email и password в памяти открытой формы. Повтор с неизменными данными использует тот же ключ; изменение любого из них создаёт новый UUID до следующей отправки.
- Операции, способные использовать или удалить текущую пару токенов (`refresh`, `logout`, `logout-all`), выполняются последовательно через единый локальный coordinator. Это предотвращает повторную отправку одного refresh-token из-за гонки; серверная строгая ротация остаётся окончательной защитой.
- Универсальный HTTP-interceptor, который автоматически делает refresh и повторяет произвольный запрос, в v1 не используется. Refresh выполняется только явным сценарием восстановления при запуске. Будущий controlled retry разрешается проектировать вместе с первым защищённым read API.
- Сервер остаётся единственным источником прав, валидации и статуса сессии.
- В первой версии передача выполняется по HTTP, включая release-сборки, по решению владельца проекта. Это небезопасно для недоверенных сетей и не должно быть представлено пользователю как защищённый канал.

## Данные и конфиденциальность

- Пользователь вводит email и пароль; пароль существует только в памяти формы на время отправки.
- Access и refresh tokens хранятся только в защищённом хранилище платформы одним сериализованным значением `auth_session_v1`; пара читается, записывается и удаляется как единое целое.
- Ошибка защищённого хранилища не считается сетевой ошибкой и не раскрывает секреты. При неудачной записи пользователь не считается вошедшим; при неудачном удалении приложение не заявляет об успешном локальном выходе.
- База данных и пользовательские данные не создаются в мобильном приложении.

- [x] Токены, пароль и ключ идемпотентности не логируются и не лежат в обычном хранилище.

## Согласованные решения

- Первая версия поддерживает только Android; iOS вынесен в будущую работу.
- Название — `Fitness App`; интерфейс на английском, Material 3 и согласованный синий спортивный стиль.
- Единственная точка входа Flutter — Gateway. По локальному шаблону его API
  доступен на ПК как `http://127.0.0.1:8088`, в Android Emulator —
  `http://10.0.2.2:8088`. `API_BASE_URL` задаёт адрес Gateway нужного окружения;
  прежнее решение о прямом подключении к Identity на порту 8080 заменено.
- Management-порт Gateway 8089 и внутренние адреса Identity не используются
  мобильным клиентом; fallback в обход Gateway отсутствует.
- Gateway проверяет access JWT и активность сессии для `POST /api/v1/auth/logout-all` до передачи запроса Identity. Register, login, refresh и logout не требуют access JWT: их авторизация остаётся в существующих правилах Identity.
- Для Android Emulator используется `http://10.0.2.2:8088`. Физический телефон поддерживается только в локальной USB-проверке: после явного подтверждения пользователя «телефон подключён, adb видит устройство» выполняется `adb reverse tcp:8088 tcp:8088`, а приложение запускается с `API_BASE_URL=http://127.0.0.1:8088`. Это не открывает сервисы в LAN.
- Главный экран показывает только `You are signed in`; данные профиля и другие API не запрашиваются.
- При `email_already_registered` клиент предлагает `Sign in instead` с заполненным email и без переноса пароля.
- `registration_pending` и `registration_unavailable` показывают кнопку `Try again`, которая использует тот же временный `Idempotency-Key`.
- Выход из текущей сессии использует `/logout`; выход со всех устройств — `/logout-all`; при ошибке обоих методов локальные токены удаляются.
