# Аудит Coins Service

## Подтверждённые изменения

- `wallet/WalletCreationService` использует `JdbcClient` и SQL внутри сервиса.
  Перевести на `wallet/service`, `wallet/repository` и `wallet/entity`.
- Отобразить все пять полей `coin_wallets`. Создание выполнить native INSERT
  через JPA repository с `ON CONFLICT (user_id) DO NOTHING`, как в Accounts;
  сохранить defaults БД и запрет отрицательных балансов. Не использовать merge.
- В PostgreSQL-тестах заменить `JdbcClient` на repository и EntityManager с
  явными транзакциями для подготовки данных. Проверять каждый баланс отдельно,
  чтобы сохранение суммы не скрывало изменения между доступным и резервным.
- Добавить интеграционный тест фактического SecureGrpcServer с mTLS и БД:
  существующие сетевые тесты сервера используют mock сервиса.
- Упростить gRPC-адаптер: отдельно разбор UUID, вызов сервиса и отправка ответа;
  сохранить `INVALID_ARGUMENT`, безопасный `INTERNAL` и успех после commit.
- Использовать обычные imports вместо полных имён типов в interceptor,
  понятные имена и Lombok для простого внедрения зависимостей; не добавлять
  mapper или интерфейс сервиса без необходимости.
- Добавить production-профиль с ECS-логированием и README локального запуска.

## Решение по запуску gRPC

Coins в текущем scope нужен регистрации для создания кошелька. HTTP здесь
предоставляет технические endpoint, а не альтернативу этой операции. Как в
Accounts после Spec 010, gRPC должен стартовать всегда: удалить
`coins.grpc.enabled` из кода и шаблонов. Отсутствующие/невалидные mTLS-материалы
прерывают запуск. Это изменение конфигурации запуска, не ослабление mTLS и не
изменение правил кошелька. Тесты БД подменяют только жизненный цикл сервера;
отдельный сквозной тест запускает настоящий сервер.

## Сохраняемые гарантии

Схема и Liquibase-история не меняются. Повтор создания не меняет баланс или
timestamps существующей строки. Два конкурентных вызова создают один кошелёк.
Авторизуется только Identity по доверенному клиентскому сертификату. Права,
маршруты и номера полей protobuf сохраняются в рамках переименованного v1.

## Проверка

Аудит выполнен по исходникам, миграции, конфигурации и существующим тестам.
Результаты исполнения тестов рефакторинга записываются в tasks.md после запуска.
