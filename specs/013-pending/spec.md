# Spec 013: защита доступа к сервисам и pre-authentication Identity

> **Статус:** approved — ближайший этап согласован по итогам grilling 2026-11-12. Реализация не разрешена и не начата.
> **Номер:** 013
> **Документы:** [план](plan.md), [задачи](tasks.md), [вопросы](questions.md), [текущая схема](current-state.md).

## Цель и границы

Закрыть обход Gateway, подтвердить личность вызывающего сервиса и разрешать
ей только конкретные операции. После проверки доверенного пути убрать повторную
криптографическую проверку JWT только из Identity logout-all.

Ближайший этап: Gateway → Identity по HTTP, сохранение существующих gRPC,
служебный доступ, проверка защиты, затем pre-authentication Identity.
Сетевой инвентарь охватывает внутренние сервисы; минимальные изменения их bind
допустимы только по установленной схеме запуска. Массовая переделка их security
и пользовательских API не входит в этап. Новые публичные маршруты не добавляются.

Внешний пользовательский вход — через Gateway. Внутренние сервисы общаются
напрямую по согласованным HTTP/gRPC-контрактам, с проверкой service identity
и разрешения на конкретную операцию. Gateway не является обязательным
посредником межсервисных вызовов. Клиентское приложение — мобильное.

## Доступ

Ни принадлежность сети, ни сертификат произвольного сервиса нашей CA сами по себе
не разрешают операцию. TLS проверяет цепочку и срок сертификатов; получатель
проверяет точную service identity из URI SAN и allowlist операций, запрещая остальное.
Заголовки клиента не являются подтверждением TLS identity.
Gateway проверяет сертификат Identity и соответствие DNS/IP SAN имени в адресе
назначения. Запрещены trust-all, отключение проверки имени и fallback на HTTP.
Выдача CA сертификатов должна исключать получение чужой service identity;
ключи Gateway недоступны другим процессам/контейнерам без разрешения.

Gateway принят как доверенный компонент пользовательской аутентификации.
Захват Gateway вместе с его ключом позволяет подделать контекст: mTLS защищает
от постороннего caller, но не от захваченного доверенного Gateway. Эта граница
доверия принята пользователем; ключи сервисов необходимо изолировать.
Смена сертификатов выполняется с перезапуском соответствующих сервисов;
короткий перерыв допустим. Обновление без перезапуска не входит в этап.

### Матрица целевого доступа

| Кто вызывает | Получатель / интерфейс / операция | Подтверждение личности | Разрешение |
| --- | --- | --- | --- |
| Пользователь | Gateway, пять POST /api/v1/auth/{register,login,refresh,logout,logout-all} | Для logout-all JWT + CheckSession; для остальных собственные credentials операции в Identity | Только текущий каталог |
| Gateway | Identity HTTP, те же пять POST | mTLS, URI SAN spiffe://fitness.local/gateway-service | Только эти операции; пользовательская авторизация отдельно |
| Gateway | Identity GET /.well-known/jwks.json | Тот же mTLS и service identity | Только чтение JWKS, без пользовательского JWT |
| Gateway | Identity gRPC CheckSession | Существующий mTLS + allowed-caller Gateway | identity.session.verify |
| Identity | Accounts gRPC CreateProfileIfAbsent | mTLS, URI SAN spiffe://fitness.local/identity-service | identity.registration.provision; сохранить идемпотентность |
| Identity | Coins gRPC CreateWalletIfAbsent | mTLS, та же identity Identity | identity.registration.provision; сохранить идемпотентность |
| Оператор recovery (будущий доступ) | Identity /api/v1/admin/identity/registration-operations/**, только существующие методы | Предложение: отдельный сертификат оператора + существующие JWT, активная сессия и SUPER_ADMIN из БД | Сейчас запрещено по умолчанию; будущий канал требует отдельного решения |
| Локальный оператор / мониторинг | Отдельные management health/readiness/liveness/info/prometheus | Предложение: loopback и доступ ОС/SSH; удалённый мониторинг — отдельная identity | Только согласованные диагностические endpoints; Q002 |
| Локальные инструменты | Пользовательский API через Gateway | Обычный путь пользователя | Нет исключения по local-профилю |
| Локальная проверка приложения | Реальные локальные Gateway, Identity, Accounts и Coins | Настроенные сертификаты сервисов; отдельные credentials для негативных проб | Разрешено создать тестового пользователя через регистрацию; отдельный стенд не требуется |
| Интернет, другой сервис, произвольный сертификат CA | Внутренние порты / чужие операции | Недостаточно | Запрет; Gateway также не получает доступ к recovery автоматически |

Management не должен попадать в публичный каталог Gateway. Закрытие JWKS не должно
создать цикл запуска: Identity выдаёт JWKS аутентифицированному Gateway независимо
от готовности Gateway и наличия пользовательской сессии.

Для подтверждённой локальной схемы отдельных процессов используется loopback
внутренних HTTP/gRPC/management плюс mTLS. Для контейнеров loopback хоста не
заменяет внутреннюю сеть без публикации портов; для нескольких серверов нужны
правила доступа от конкретных источников. Пользователь подтвердил локальные процессы и будущие серверные контейнеры (Q001).
Документация одного сервера не является доказательством настроенного firewall.

## Пользовательский контекст Identity

Переход разрешён только после завершения проверок доверенного пути в целевой
среде применения. Локальная проверка разрешает только локальный этап, не rollout.
Для logout-all Gateway передаёт исходный Bearer; Identity принимает его только
от разрешённого TLS caller, разбирает claims без повторной проверки подписи,
создаёт Authentication и ограниченный временем запроса SecurityContext.

- sub — канонический UUID пользователя в principal; sid и exp сохраняются
  как типизированные данные контекста, без повторного отказа по сроку exp или активности sid после допуска Gateway. principal не зависит от класса криптографического verifier.
- Известные роли из RoleCode: USER, MODERATOR, ADMIN, SUPER_ADMIN → ROLE_<role>.
  Неизвестные строки не дают прав; отсутствующие/пустые роли не дают ROLE_USER.
  Некорректные типы roles, sub, sid, exp и повреждённый JWT приводят к отказу.
- Отсутствие роли само по себе не добавляет новое требование ROLE_USER для
  logout-all: текущая операция требует аутентифицированного владельца сессии.
  Проверки role-protected операций обязаны отказать при отсутствии нужной роли.
- X-User-Id/X-Roles и подобные входные заголовки не используются для аутентификации.
- Проверки прав на операции и объекты остаются в Identity. Контекст очищается
  после успеха и ошибок, не переносится в параллельные или следующие запросы.
- AccessTokenVerifier сохраняется для recovery: его JWT пока проверяется полностью.

## Состояние и бизнес-инварианты logout-all

Момент допуска команды — успешная проверка JWT и CheckSession в Gateway.
До этого допуска истёкший токен или недействительная сессия приводят к отказу
Gateway. После допуска Identity получает исходный токен по доверенному mTLS-пути
и завершает отзыв всех сессий пользователя, несмотря на последующее изменение
состояния. Это согласованное изменение прежнего поведения, а не только рефакторинг.

| Проверка сейчас | Целевое решение |
| --- | --- |
| Повторная криптографическая проверка JWT | Убрать для logout-all после проверки защиты; сохранить проверку формата доверенного контекста |
| lockUser и требование ACTIVE | Сохранить необходимую блокировку для согласованного отзыва; статус, изменившийся на заблокированный, не отменяет выход |
| exp > now внутри транзакции | Убрать повторный отказ из-за истечения токена после допуска Gateway |
| sessions.check(userId, sid) | Убрать повторный отказ из-за недействительности исходной сессии после допуска Gateway |
| revokeAllSessions внутри транзакции | Сохранить атомарный отзыв всех сессий пользователя |

Успех — 204 без тела, в том числе если все сессии уже закрыты. Нельзя вернуть
успех при техническом сбое, из-за которого отзыв не выполнен. Сохраняются
существующие контракты технических ошибок и общий deadline Gateway; этот принцип
не означает бесконечное ожидание или гарантированную доставку ответа клиенту.
Операция отзыва повторяема без дополнительных эффектов, но повторный внешний
запрос заново проходит Gateway и с уже отозванной сессией может получить 401.

Объект операции определяется только sub доверенного контекста, не клиентским
заголовком или произвольным user_id. Порядок необходимых блокировок и транзакцию
согласовать с существующими refresh/logout/login при реализации. Сетевых вызовов
внутри транзакции не добавлять. Новые правила будущего входа здесь не вводятся.

### Роли и их обновление

Роль USER автоматически не назначается. Отсутствующие, пустые или только
неизвестные роли не мешают выходу из своих сессий, но не дают доступа к операциям,
требующим известную роль. Повреждённый контекст отклоняется.

Принята задержка снятия прав до 15 минут: уже выданный access-токен сохраняет
прежние роли до истечения срока, даже после успешного refresh. Refresh читает
актуальные роли из БД для нового access-токена; клиент должен вызвать refresh,
токен не обновляется сам. Это не отменяет проверку сессии Gateway и текущую
проверку SUPER_ADMIN из БД для recovery. Снятие всех ролей и новые административные
операции не меняются автоматически: существующий signer требует непустые роли.

Identity сохраняет регистрацию, пароль при входе, выпуск access/JWKS,
refresh/reuse detection, хранение и отзыв сессий, CheckSession и бизнес-правила.
Для четырёх публичных auth-операций Gateway по-прежнему удаляет Authorization,
не проверяет JWT/сессию, сохраняет refresh_token в теле. Изменение этих правил
не входит в спецификацию.

## Критерии готовности

- [ ] Разрешённые запросы через Gateway и служебные взаимодействия проходят.
- [ ] Прямой внешний доступ к внутренним портам запрещён в проверяемой среде.
- [ ] Без сертификата, с чужой service identity даже от своей CA, с недоверенной
  CA, истёкшим сертификатом, неверным серверным именем доступ отклоняется.
- [ ] Верный caller не получает право на чужую операцию; нет plaintext bypass.
- [ ] JWKS загружается по mTLS, Gateway переходит в readiness; при отказе TLS
  остаётся not ready, liveness и предусмотренная диагностика доступны.
- [ ] Recovery закрыт по умолчанию, management доступен только предусмотренным локальным способом.
- [ ] Pre-authentication проверен для корректных, отсутствующих, неизвестных,
  некорректных ролей; method security, собственность объектов и изоляция контекста проверены.
- [ ] После допуска Gateway отзыв исходной сессии, истечение токена и блокировка
  пользователя не мешают logout-all; все сессии отозваны, ответ 204.
- [ ] Уже закрытые сессии дают 204 при доставке ранее допущенной команды;
  технический сбой не выдаётся за успех. Новый запрос проходит Gateway заново.
- [ ] Транзакционность и защита от гонок проверены; refresh/replay и регистрация
  сохраняют поведение. Собственные сессии можно закрыть без известных ролей.
- [ ] Приложение проверено локально на разрешённом тестовом пользователе;
  существующие пользователи и секреты не изменены.
- [ ] Свидетельства локальных тестов отделены от проверок развёрнутой среды.

## Content-Encoding и будущие работы

В текущем allowlist Content-Encoding отсутствует; статический риск передачи
сжатых байтов без метаданных подтверждён. Отдельного воспроизводящего теста сейчас
нет. По решению пользователя Q003 проверка и изменение сейчас отложены.
Вариант 415 не согласован; риск не считается устранённым.

Accounts/Coins и остальные пользовательские API подключаются отдельными будущими
задачами: маршруты, защита обхода, claims, method/object security и негативные тесты.
Настройка firewall, CA и rollout в развёрнутой среде — отдельные разрешённые
операционные действия. Эта спецификация не разрешает deploy или миграции БД.
