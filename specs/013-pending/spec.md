# Spec 013: локальный HTTP и отложенный pre-authentication Identity

> **Статус:** локальные изменения T002–T002b выполнены; документы приведены к решению пользователя от 2026-11-12. Pre-authentication не реализован.
> **Документы:** [план](plan.md), [задачи](tasks.md), [решения](questions.md), [текущая схема](current-state.md).

## Текущий объём

Локально сервисы запускаются отдельными Java-процессами. Gateway → Identity
работает по обычному HTTP, включая JWKS. HTTPS и клиентские сертификаты для
этого HTTP-пути отменены. Существующий mTLS внутренних gRPC остаётся.
Подготовка серверного запуска в Docker не входит в текущую работу: не создавать
его конфигурацию, сетевую схему или план запуска без отдельного запроса.

Сохранены loopback внутренних локальных listeners, отдельный management Identity
и закрытый recovery. Прямые HTTP-запросы других локальных процессов к разрешённым
операциям Identity допустимы. Allowlist методов и путей ограничивает операции,
но не подтверждает, что запрос пришёл от Gateway.

Identity продолжает полностью проверять JWT для logout-all. Проверки состояния
пользователя, срока токена и сессии в LogoutService, транзакции и блокировки
сохраняются. Удаление этой повторной проверки сейчас не разрешено.

Rate limiter Identity, его настройки, зависимости и связанные тесты удалены
в T002a по запросу пользователя. Перенос ограничителя в Gateway не входит в работу.
Новые публичные маршруты не добавляются.

## Матрица текущего локального доступа

| Кто вызывает | Сервис / интерфейс / операция | Подтверждение личности | Что разрешено |
| --- | --- | --- | --- |
| Клиент | Gateway: пять POST register/login/refresh/logout/logout-all | Для logout-all JWT и CheckSession; для остальных credentials проверяет Identity | Текущий каталог /api/v1/auth/** |
| Gateway или другой локальный процесс | Identity HTTP: пять auth POST | Личность вызывающего сервиса не проверяется; logout-all требует полноценный JWT | Только разрешённые методы и пути; бизнес-проверки Identity сохраняются |
| Gateway или локальный инструмент | Identity HTTP GET /.well-known/jwks.json | Без сертификата и пользовательского JWT | Чтение публичных ключей, необходимое при старте Gateway |
| Gateway | Identity gRPC CheckSession | Существующий mTLS и allowed-caller Gateway | identity.session.verify |
| Identity | Accounts gRPC CreateProfileIfAbsent | Существующий mTLS и разрешение Identity | identity.registration.provision |
| Identity | Coins gRPC CreateWalletIfAbsent | Существующий mTLS и разрешение Identity | identity.registration.provision |
| Локальный оператор / инструмент | Management Identity на отдельном loopback listener | Локальный доступ; без HTTP-сертификата | Предусмотренные health/readiness/liveness/info/prometheus; пользовательский API запрещён |
| Любой HTTP caller | Административное восстановление регистрации | Вход закрыт | Recovery не используется; код JWT/сессии/SUPER_ADMIN сохранён |
| Локальные тесты | Реальное приложение пользователя | Обычный HTTP; существующий mTLS для gRPC | Разрешено создать тестового пользователя через API; отдельный стенд не требуется |

Локальные ограничения не доказывают защиту развёрнутой среды. Требование будущего
внешнего входа только через Gateway сохранено как направление, но сейчас сервер
не подготавливается и его защита не объявляется готовой. Межсервисные вызовы
не обязаны проходить через Gateway; права определяются контрактом каждой операции.

## Проверенное состояние и ограничения

Результаты и объём проверок приведены в [задачах](tasks.md). После возврата HTTP
прошли шесть адресных тестов, Spotless/SpotBugs и семь проверок запущенных
Identity/Gateway: JWKS, readiness, маршрут login, отказ logout-all без JWT,
закрытый recovery и разделение API/management. Это не полный сквозной прогон
всех бизнес-сценариев и не проверка серверной сети.

Исторический [отчёт T002](verification-t002.md) описывает прежний HTTP mTLS,
который отменён в T002b; его TLS-результаты не относятся к текущему HTTP.

## Отложенные решения grilling — не текущая реализация

Следующие требования сохраняют согласованные бизнес-решения. Применять их можно
только после отдельного согласования и проверки доверенного пути Gateway → Identity
и команды на реализацию. HTTP без проверки caller сам по себе такого доверия
не устанавливает. Старые требования HTTP mTLS отменены; замена сейчас не выбирается.
Gateway как доверенный компонент аутентификации остаётся принятой границей:
при его компрометации доверенный пользовательский контекст может быть подделан.

### Пользовательский контекст Identity

Переход отложен. Для его возобновления нужны отдельная команда пользователя
и завершённые проверки доверенного пути в согласованной среде применения.
Для logout-all Gateway передаёт исходный Bearer; Identity принимает его только
по отдельно согласованному и проверенному доверенному пути, разбирает claims без повторной проверки подписи,
создаёт Authentication и ограниченный временем запроса SecurityContext.

- sub — канонический UUID пользователя в principal; sid и exp сохраняются
  как типизированные данные контекста, без повторного отказа по сроку exp или активности sid после допуска Gateway. principal не зависит от класса криптографического verifier.
- Известные роли из RoleCode: USER, MODERATOR, ADMIN, SUPER_ADMIN → ROLE_<role>.
  Неизвестные строки не дают прав; отсутствующие/пустые роли не дают ROLE_USER.
  Некорректные типы roles, sub, sid, exp и повреждённый JWT приводят к отказу.
- Отсутствие роли само по себе не добавляет новое требование ROLE_USER для
  logout-all: текущая операция требует аутентифицированного владельца сессии.
  Проверки role-protected операций обязаны отказать при отсутствии нужной роли.
- X-User-Id/X-Roles и подобные входные заголовки не используются для аутентификации.
- Проверки прав на операции и объекты остаются в Identity. Контекст очищается
  после успеха и ошибок, не переносится в параллельные или следующие запросы.
- AccessTokenVerifier сохраняется для recovery: его JWT пока проверяется полностью.

### Состояние и бизнес-инварианты logout-all

Момент допуска команды — успешная проверка JWT и CheckSession в Gateway.
До этого допуска истёкший токен или недействительная сессия приводят к отказу
Gateway. После допуска Identity получает исходный токен по доверенному пути
и завершает отзыв всех сессий пользователя, несмотря на последующее изменение
состояния. Это согласованное изменение прежнего поведения, а не только рефакторинг.

| Проверка сейчас | Целевое решение |
| --- | --- |
| Повторная криптографическая проверка JWT | Убрать для logout-all после проверки защиты; сохранить проверку формата доверенного контекста |
| lockUser и требование ACTIVE | Сохранить необходимую блокировку для согласованного отзыва; статус, изменившийся на заблокированный, не отменяет выход |
| exp > now внутри транзакции | Убрать повторный отказ из-за истечения токена после допуска Gateway |
| sessions.check(userId, sid) | Убрать повторный отказ из-за недействительности исходной сессии после допуска Gateway |
| revokeAllSessions внутри транзакции | Сохранить атомарный отзыв всех сессий пользователя |

Успех — 204 без тела, в том числе если все сессии уже закрыты. Нельзя вернуть
успех при техническом сбое, из-за которого отзыв не выполнен. Сохраняются
существующие контракты технических ошибок и общий deadline Gateway; этот принцип
не означает бесконечное ожидание или гарантированную доставку ответа клиенту.
Операция отзыва повторяема без дополнительных эффектов, но повторный внешний
запрос заново проходит Gateway и с уже отозванной сессией может получить 401.

Объект операции определяется только sub доверенного контекста, не клиентским
заголовком или произвольным user_id. Порядок необходимых блокировок и транзакцию
согласовать с существующими refresh/logout/login при реализации. Сетевых вызовов
внутри транзакции не добавлять. Новые правила будущего входа здесь не вводятся.

### Роли и их обновление

Роль USER автоматически не назначается. Отсутствующие, пустые или только
неизвестные роли не мешают выходу из своих сессий, но не дают доступа к операциям,
требующим известную роль. Повреждённый контекст отклоняется.

Принята задержка снятия прав до 15 минут: уже выданный access-токен сохраняет
прежние роли до истечения срока, даже после успешного refresh. Refresh читает
актуальные роли из БД для нового access-токена; клиент должен вызвать refresh,
токен не обновляется сам. Это не отменяет проверку сессии Gateway и текущую
проверку SUPER_ADMIN из БД для recovery. Снятие всех ролей и новые административные
операции не меняются автоматически: существующий signer требует непустые роли.

Identity сохраняет регистрацию, пароль при входе, выпуск access/JWKS,
refresh/reuse detection, хранение и отзыв сессий, CheckSession и бизнес-правила.
Для четырёх публичных auth-операций Gateway по-прежнему удаляет Authorization,
не проверяет JWT/сессию, сохраняет refresh_token в теле. Изменение этих правил
не входит в спецификацию.


## Вне текущей работы

- Подготовка серверного запуска в Docker и любые действия в развёрнутой среде.
- Новые пользовательские маршруты Accounts/Coins и их pre-authentication.
- Административный клиент и открытие recovery.
- Content-Encoding: по решению пользователя сейчас ни воспроизводящего теста,
  ни исправления. Риск передачи сжатого тела без заголовка не считается устранённым;
  вариант ответа 415 не согласован.

Коммиты, push, merge, deploy и миграции пользовательских БД требуют отдельного
разрешения. После каждого разрешённого пункта — результат и остановка для ревью.
