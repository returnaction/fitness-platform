# План Spec 013

> **Статус:** in-progress — T002 и дополнение T002a выполнены и проверены локально; остановка для ревью. T003 и следующие этапы ждут новой команды пользователя.
> **Основание:** [спецификация](spec.md), [текущая схема и точки кода](current-state.md).

## Актуальное решение: HTTP без сертификатов (2026-11-12)

По последнему указанию пользователя HTTPS и HTTP mTLS удаляются из Identity.
Локально Gateway и Identity работают по HTTP; HTTP caller не аутентифицируется.
Loopback, разделение API/management, закрытый recovery и полная JWT-проверка
Identity сохраняются. Существующий mTLS gRPC не меняется. Локальные процессы
могут обращаться к Identity напрямую — запрет таких обращений сейчас не требуется.
На сервере внешний доступ предполагается ограничивать публикацией только Gateway
и настройками Docker-сетей; это ещё не реализовано и не проверено.

T003 (внедрение HTTP mTLS) отменён. T004–T006 в прежнем виде отложены: доверенный
путь для pre-authentication теперь не установлен. Нельзя удалять JWT-проверку
Identity или реализовывать новую семантику logout-all на основании старого плана.
Следующие разделы описывают предыдущее решение; требования HTTP mTLS в них
заменены настоящим разделом и не являются командой на реализацию.

## 1. Защита доступа

Локально: отдельные процессы, внутренние HTTP/gRPC/management на loopback.
HTTP Gateway → Identity: обязательный клиентский сертификат, точный URI SAN
Gateway и allowlist пяти POST плюс GET JWKS. Проверка серверной цепочки и имени
Identity в обоих клиентах Gateway. Отдельные ключи/права доступа к файлам,
ограниченный срок сертификатов; документировать замену/перезапуск и аварийный отзыв
доступа. Замена сертификатов с перезапуском согласована, короткий перерыв допустим; hot reload не нужен. Проверить существующую инфраструктуру step-ca, не вводить новую PKI без причины.

Сначала оставить повторную JWT-валидацию logout-all. Recovery закрыть по умолчанию,
без разрешённого оператора; не удалять механизм. Существующие проверки JWT,
сессии и SUPER_ADMIN сохранить. Оператор сейчас им не пользуется.
Management вынести на отдельный локальный listener, не проксировать через Gateway.
По дополнительному решению пользователя T002a удаляет rate limiter Identity,
его настройки, зависимости и тесты. Перенос limiter в Gateway не входит в работу.

Сервер позже: контейнеры, наружу пользовательский вход только Gateway;
внутренние порты не публиковать на публичные интерфейсы. Адреса внутри контейнеров
выбирать по реальной сети, не копировать loopback процессов. mTLS и allowlist
обязательны также внутри контейнерной сети. Схема сети, CA, мониторинга и
управления определяется до развёртывания, не выдумывается сейчас.

## 2. Проверка защиты — обязательный gate

Проверять запущенное локальное приложение, без создания отдельного стенда.
Реальные TLS-соединения: разрешённый Gateway; отсутствие
сертификата; другой сервис той же CA; неизвестная CA; истёкший сертификат;
неверное имя Identity; попытки доступа к неразрешённым операциям и HTTP bypass.
Проверить оба клиента Gateway, JWKS startup/retry/readiness, management, закрытый
recovery, gRPC CheckSession/provision и регистрацию/refresh/logout.
Проверить локальный bind отдельно от TLS. Для серверной среды нужны внешняя
проба портов, проба из контейнера другого сервиса и проверка правил публикации.
Локальный успех не закрывает серверную проверку.

## 3. Pre-authentication только Identity logout-all

После локального gate, в рамках отдельно разрешённой реализации: небольшой
парсер доверенного контекста и principal отдельно от AccessTokenVerifier.
Использовать существующие RoleCode, без общей библиотеки auth для всех сервисов.
TLS caller проверяется раньше claims. Не хранить сырой токен в principal/логах.
Изменить LogoutService по согласованной семантике: после допуска Gateway
не отказывать из-за отзыва исходной сессии, истечения exp или статуса пользователя,
изменившегося на заблокированный. Сохранить транзакцию, необходимые блокировки
и отзыв всех сессий. Уже закрытые сессии дают 204; технический сбой — ошибку.
Не переносить эти изменения в recovery, refresh, login и CheckSession.
Контекст принимается только от Gateway; захват Gateway — принятая граница доверия.
Отсутствие ролей не означает USER; неизвестные строки игнорируются для прав,
неверные типы отклоняются. Не добавлять ROLE_USER как новое условие logout-all.
Старые роли access действуют до истечения (максимум 15 минут); refresh берёт
текущие роли из БД. Существующий recovery проверяет SUPER_ADMIN из БД.

## 4. Проверки поведения

Unit/security HTTP: claims, method security, отказ чужому caller, очистка
SecurityContext, отсутствие доступа к чужим сессиям. Целенаправленные PostgreSQL
integration-тесты: после допуска Gateway токен истёк / сессия отозвана /
пользователь заблокирован — logout-all всё равно атомарно закрывает все сессии.
Уже закрытые сессии — 204. Сбой БД не даёт ложного успеха или частичного отзыва.
До допуска Gateway недействительный токен/сессия — отказ; повторный внешний
запрос проверяется заново. Проверить гонки существующих операций техническими
тестами, без новых продуктовых правил. Сохранить тесты административного verifier.

Сквозная проверка — запуск реальных локальных Gateway, Identity, Accounts и Coins
как Java-процессов с локальной конфигурацией пользователя. Разрешено зарегистрировать
тестового пользователя через API и работать с его сессиями. Проверить пять операций,
refresh/replay, JWT/JWKS, mTLS и предусмотренную диагностику. Существующие аккаунты
не менять; секреты и сертификаты пользователя не перезаписывать. Негативные TLS
пробы использовать без ослабления работающей политики. Отдельный стенд не создавать.
Существующие автоматические тестовые механизмы проекта остаются; они не заменяют
проверку приложения. Прежний изолированный E2E-скрипт не является обязательным
новым стендом; при необходимости переиспользовать сценарии для локального запуска.

Использовать Maven Wrapper и версии корневого pom, существующие Spotless,
SpotBugs и тесты. Базовая команда из корня:
`./mvnw.cmd -pl services/gateway-service,services/identity-service -am verify`.
При изменении bind Accounts/Coins включить их проверки. Для форматирования
использовать существующий spotless:apply; проверку jar E2E проводить отдельно.
Не менять mvnw. Новые миграции не ожидаются; миграции пользовательских БД без
разрешения не запускать, в том числе автоматически при старте сервисов.
Разрешена работа тестового пользователя через API локального приложения.
Совместимость выбранных TLS API сверить с закреплёнными зависимостями до кодирования.

## Выпуск и будущие этапы

Перед включением pre-auth в контейнерах повторить gate именно там. До проверки
не выпускать сборку без повторной JWT-валидации в незакрытую среду. План возврата:
предыдущая проверенная сборка с JWT-валидацией и сохранённым mTLS, без открытия портов.
Deploy/firewall/выдача сертификатов выполняются отдельно по разрешению пользователя.

Подключение пользовательских Accounts/Coins — отдельные спецификации/маршруты,
защита обхода, claims, method/object security, негативные роли и изоляция контекста.
Content-Encoding по решению пользователя отложен: сейчас ни теста, ни исправления.
