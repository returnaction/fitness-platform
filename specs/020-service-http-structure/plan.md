# План: структура HTTP-компонентов

> **Спецификация:** [spec.md](spec.md)
> **Статус:** draft — реализация отложена

## Подготовка после разрешения пользователя

1. Прочитать инженерные стандарты, контракты и документацию конкретного сервиса.
2. Собрать текущие servlet/Security-цепочки, MVC-interceptors, обработчики ошибок,
   matchers, dispatcher types, регистрации bean и используемый web-стек.
3. В verification.md перечислить для каждого сервиса: состояние, необходимые
   изменения, сохранённые контрактные проверки и обоснованные исключения.
4. Согласовать очередь сервисов. Не считать весь список существующих сервисов
   обязательным списком правок: некоторые потребуют только записи «не применимо».

## Перенос одного сервиса

Сначала проверить исходные HTTP-тесты. Переместить общие классы по пакетам,
обновить импорты, настроить явные регистрации без двойного исполнения.
Не смешивать перемещение с исправлением бизнес-логики. Сохранить специализацию
Security, ошибок, кеширования и query-параметров сервиса. Добавить простые
комментарии и README с успешным и ошибочными путями запроса.

Запустить подходящие HTTP/интеграционные тесты и Maven Wrapper verify для
затронутых модулей. Тестировать реальный порядок и результат запроса, а не
воспроизводить в тесте список классов из конфигурации. После отчёта остановиться
для ревью, если пользователь не разрешил продолжать.

## Данные и взаимодействия

Изменения схемы, транзакционных границ, идемпотентности и сетевых контрактов
не планируются. Интеграционные проверки используют изолированное окружение;
миграции пользовательских БД, commit, push, merge и deploy требуют отдельного
разрешения. Перед началом реализации выбрать ветку по действующим правилам:
разрешение на текущую ветку относится только к подготовке этой спецификации.

## Проверки

- Успех, отсутствие/неверный токен, отказ по роли или сессии — где применимо.
- Ошибки формата, query-параметры на разрешённых и запрещённых путях.
- RequestId и контрактные заголовки на успехе и всех имеющихся путях ошибки.
- Public endpoints, health/management, CORS/CSRF, async/error dispatch — если
  используются. Поведение определить по контракту и исходной реализации.
- Отсутствие повторного вызова собственных фильтров из-за двойной регистрации.
- Для Gateway: сохранение JWT/CheckSession, маршрутизации и передачи заголовков.
- Итоговые verify/SpotBugs и сквозные HTTP-проверки затронутой связки.

Неизменённые сервисы не объявлять проверенными только по сходству структуры.
