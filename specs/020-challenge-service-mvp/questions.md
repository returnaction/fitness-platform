# Вопросы Spec 020

> **Спецификация:** [spec.md](spec.md)
> **Статус:** открытые вопросы для будущих спецификаций; решения MVP зафиксированы в [decisions.md](decisions.md).

## 1. Лимиты полей

- **Затрагивает:** T002.1, T004.8, T007.
- **Свидетельство:** в дизайне 39 и 60 лимиты title, description, stake и duration не заданы.
- **Варианты:** подтвердить предложенные 1–120 / 2000 / 1–1 000 000 / 1–30; изменить значения; отложить публикацию до отдельного продуктового решения.
- **Рекомендация:** подтвердить предложенные значения до статуса `approved`.
- **Блокирует:** финальную схему OpenAPI и валидацию черновика.

## 2. Формат Kafka-события

- **Затрагивает:** T002.2, T002.3, T004.15, T005.6.
- **Свидетельство:** `19-kafka-topology.md` требует snake_case-оболочку; примеры в 34/35 используют camelCase.
- **Варианты:** snake_case-оболочка + camelCase `data`; полностью camelCase; изменить topology.
- **Рекомендация:** snake_case-оболочка + camelCase `data`, отдельные event-DTO с `@JsonProperty`.
- **Блокирует:** контракты событий и golden-тесты.

## 3. Production-источник результата

- **Затрагивает:** T004.16, T007.
- **Свидетельство:** исходный черновик признаёт источник неопределённым; в системе нет модерации и админ-процесса.
- **Варианты:** оставить внутренний gRPC с mTLS до спеки модерации; добавить административный процесс; отложить результат.
- **Рекомендация:** внутренний gRPC `FinalizeResult` с отдельным доверенным SAN; публичного назначения победителя нет.
- **Блокирует:** только production-эксплуатацию; MVP можно проверить с тестовым клиентом.

## 4. Локальная Kafka

- **Затрагивает:** T006.1.
- **Свидетельство:** Kafka в проекте отсутствует; конституция требует локальный Docker Compose KRaft, PostgreSQL — вне Docker.
- **Варианты:** отдельный `deployment/compose.local-kafka.yaml`; сервис в production Compose; Testcontainers только для тестов.
- **Рекомендация:** отдельный локальный файл, production Compose и release scripts не менять.
- **Блокирует:** сквозной сценарий settlement.

## 5. TTL и очистка идемпотентности

- **Затрагивает:** T004.7, T004.13.
- **Свидетельство:** исходный черновик не задаёт TTL и лимиты; Coins не удаляет операции.
- **Варианты:** не чистить в MVP; ввести TTL после окна повтора; архивировать завершённые операции.
- **Рекомендация:** не чистить в MVP; запретить удаление незавершённых операций и release intents.
- **Блокирует:** только будущую эксплуатационную политику.

## 6. Rate limit

- **Затрагивает:** T003.3, T006.6.
- **Свидетельство:** в Spec 017 отдельный rate limit не вводился; порогов нет.
- **Варианты:** использовать лимиты Gateway по умолчанию; ввести отдельные пороги; отложить.
- **Рекомендация:** не добавлять отдельные пороги до нагрузочных наблюдений.
- **Блокирует:** ничего в MVP.

## 7. Длительная недоступность БД

- **Затрагивает:** T006.6, T007.
- **Свидетельство:** унаследовано из Spec 017; неизвестно, укладывается ли ожидание соединения в deadline Gateway 7s.
- **Варианты:** измерить и зафиксировать; изменить пул/таймауты; оставить как известное ограничение.
- **Рекомендация:** измерить на challenge-service и Coins; не выдавать сценарий за успешный до измерения.
- **Блокирует:** полноту критерия `503`.

## 8. Отсутствующий кошелёк Coins

- **Затрагивает:** T002.2, T005.2.
- **Свидетельство:** кошелёк создаётся при регистрации, но контракт ReserveStake не описывает отсутствие строки.
- **Варианты:** `FAILED_PRECONDITION WALLET_NOT_FOUND`; трактовать как `INSUFFICIENT_FUNDS`; `INTERNAL`.
- **Решение (2026-11-17):** в gRPC — явный `FAILED_PRECONDITION` с reason `WALLET_NOT_FOUND`, не бизнес-исход и не маскируется под `INSUFFICIENT_FUNDS`. Публично Challenge отвечает `409 insufficient_coins`; отдельный публичный код не вводится.

## 9. Сертификат источника результата

- **Затрагивает:** T002.3, T004.16.
- **Свидетельство:** источник результата ещё не реализован; нужен тестовый клиент для MVP.
- **Варианты:** отдельный SAN `result-source`; временно разрешить `moderation-service`; ручной сертификат.
- **Рекомендация:** отдельный тестовый сертификат с конфигурируемым SAN, не ослабляя проверку mTLS.
- **Блокирует:** E2E-проверку результата.

## 10. Создание базы и миграции

- **Затрагивает:** T004.2, T005.1.
- **Свидетельство:** базы `fitness_challenge` нет; миграции Coins изменяют пользовательскую БД.
- **Варианты:** отдельное разрешение пользователя на каждую миграцию; подготовить SQL и не выполнять; отложить.
- **Рекомендация:** подготовить миграции, но выполнять только по явному разрешению.
- **Блокирует:** T004.2 и T005.1.

## 11. Nickname и список участников

- **Затрагивает:** только будущие спецификации.
- **Свидетельство:** дизайн 39 предполагает nickname из Accounts; MVP возвращает только счётчики.
- **Варианты:** отдельная спецификация; пакетное обогащение; не добавлять.
- **Рекомендация:** не блокировать MVP; вынести в отдельную спеку.

## Решённые вопросы

- Номер спецификации: 020, ветка `feature/50-challenge-service-dev`.
- Ставки: gRPC, а не OpenAPI.
- Seal: Begin/Put/Finalize вместо `SealStakeSet`.
- Внутренний результат: gRPC `FinalizeResult` с mTLS, не HTTP через Gateway.
- Отмена: Freeze + Complete, без `ListActiveHoldsForCancellation`.
- События: `challenge.finished` и `coins.settlement_completed`.
- Наблюдаемость: `refundStatus` и `settlementStatus` в `GET challenge`.
- Settlement: одна транзакция для двух holds, без escrow и large-bank worker.
- Выбран вариант B: Kafka, outbox/inbox, batch seal, freeze/complete, `ListResultWinners` и детальные settlement-таблицы остаются в MVP.
- Отсутствующий кошелёк Coins: `FAILED_PRECONDITION WALLET_NOT_FOUND`; публично `409 insufficient_coins`.
- Пакет gRPC ставок: `fitness.coins.stake.v1` и `io.github.returnaction.fitness.contracts.coins.stake.v1`.
