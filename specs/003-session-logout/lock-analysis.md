# Проверка текущих блокировок Identity

Это анализ исходного кода и конкретных конкурентных проверок, а не доказательство
отсутствия deadlock для всех возможных сценариев.

| Сценарий | Что делает текущий код |
| --- | --- |
| Refresh | В `RefreshTokenService.refresh` транзакция сначала находит связь без блокировки, затем блокирует `users`, `auth_sessions`, `refresh_tokens`; после этого проверяет секрет и состояние. |
| Вход | `RegistrationSessionService.createLogin` в транзакции блокирует активного пользователя, затем учётные данные, создаёт сессию и refresh. |
| Выдача после регистрации | `RegistrationSessionService.create` сначала блокирует пользователя, затем операцию, отзывает прежнюю сессию операции и создаёт новую. |
| Активация worker | `RegistrationLeaseRepository.completeRegistrationAndActivateUser` сначала блокирует пользователя, затем обновляет операцию и активирует пользователя в одной транзакции. |
| Проверка сессии | `SessionVerificationRepository.check` делает чтение без блокировки в read-only транзакции; оно само не защищает от изменения сессии сразу после проверки. |
| Административная авторизация | `RecoveryAccessVerifier` проверяет JWT, актуальную сессию и `SUPER_ADMIN`. Для logout-all обычного пользователя её нельзя применять без отделения проверки роли. |

В текущей схеме есть индексы `auth_sessions_user_id_index` и
`refresh_tokens_session_id_index`. Достаточность индексов и необходимость
миграции для новой операции проверяются при реализации.

## План проверки при реализации

- Проверять авторизацию logout-all повторно после блокировки пользователя и
  до отзыва, внутри одной транзакции; JWT-проверка до блокировки не заменяет
  проверку активного состояния после неё.
- Синхронизировать параллельные тесты для обоих порядков logout-all и login,
  выдачи после регистрации, logout/refresh и двух logout-all. Проверять commit,
  rollback, срок ожидания, отсутствие deadlock и конечное состояние БД.
- Для активации worker и выдачи после регистрации воспроизведён deadlock
  прежнего варианта: один запрос удерживал пользователя, второй — операцию.
  Оба пути изменены на явный порядок `users → registration_operations`.
  Конкурентный PostgreSQL-тест и чистая сборка Identity прошли после изменения.
- Проверить истечение access во время ожидания блокировки, отказ БД и ответ
  клиенту; никакой network call не удерживает транзакцию открытой.
