# Выход из сессии и со всех устройств

> **Заменяет / заменена:** —

## Цель

Пользователь может завершить текущую сессию или выйти со всех своих устройств,
чтобы прекратить обновление токенов этих сессий. Уже выданный access-токен
может оставаться действительным до истечения срока.

## Границы

### Входит в эту спецификацию

- HTTP API Identity для выхода из одной и из всех сессий.
- Проверка прав, отзыв сессий и влияние на refresh и проверку access-токена.
- Локальные проверки, контракты и примеры запросов.

### Не входит в эту спецификацию

- Добавление ролей в JWT и отдельная система управления ролями.
- Интерфейс Flutter, развёртывание, HTTPS и настройка сервера.
- Создание новых защищённых бизнес-операций в других сервисах.
- Kafka, события и новые межсервисные зависимости без согласованной необходимости.

## Пользователи и права

| Роль | Что может делать |
| --- | --- |
| Владелец сессии | Завершить свою сессию или все собственные сессии. |
| Посторонний | Не может отозвать чужую сессию, зная только идентификатор. |

## Сценарии

Владелец проекта подтвердил использование refresh для обычного logout и
действующего access для logout-all, а также правила повтора и лимиты ниже.

### Выход с текущего устройства

**Дано:** клиент располагает refresh-токеном своей сессии.
**Когда:** отправляет `POST /api/v1/auth/logout` с JSON `{"refresh_token":"<token>"}`.
**Тогда:** Identity проверяет секрет и отзывает связанную сессию; при успехе
возвращает `204` без тела. Для неизвестного, неверного или уже отозванного
токена возвращается тот же `204`, без раскрытия существования сессии. Один
идентификатор токена без корректного секрета не позволяет отозвать сессию.
Если refresh уже был использован при обновлении, но его секрет верен, logout
отзывает связанную сессию. Это не позволяет получить новую пару токенов.

### Выход со всех устройств

**Дано:** пользователь предъявил действующий access-токен активной сессии.
**Когда:** отправляет `POST /api/v1/auth/logout-all` с Bearer-токеном.
**Тогда:** Identity отзывает все его активные сессии, включая текущую, и
возвращает `204` без тела. Повтор с уже отозванной сессией получает `401`;
если первый ответ потерян, для повторной авторизации нужен новый вход.

### Ошибки и граничные случаи

| Условие | Поведение для клиента |
| --- | --- |
| Отсутствует тело или повреждён JSON для logout | `400 invalid_request`; состояние не меняется. |
| Пустое, отсутствующее или длиннее 256 символов поле `refresh_token` в JSON | `422 validation_error`; состояние не меняется. |
| Невалидный или отозванный access для logout-all | `401 invalid_access_token`; состояние не меняется. |
| Ошибка БД / проверки авторизации | `503 identity_unavailable`; успех не подтверждается. |
| Слишком много запросов | `429 rate_limited` и `Retry-After`; logout и logout-all имеют отдельные лимиты по 30 запросов в минуту с IP. |
| Неподдерживаемый `Content-Type` тела logout | `415 unsupported_media_type`; состояние не меняется. |
| Неподдерживаемый `Accept` | `406` без тела; запрос не должен отозвать сессию. Проверить порядок Security и MVC при реализации. |

## Бизнес-правила

- Успех возвращается после фиксации отзыва в базе Identity. Повтор обычного
  logout не создаёт новую операцию и не раскрывает состояние токена.
- Refresh после отзыва сессии не выдаёт новую пару токенов.
- По выбору владельца проекта защищённые сервисы проверяют JWT локально:
  подпись, срок, issuer, audience и необходимые права, без обязательного
  запроса в Identity на каждый запрос. Отзыв сессии не делает ранее выданный
  access недействительным для таких сервисов до истечения его срока — до 15 минут.
- Сам Identity для logout-all проверяет актуальность предъявленной сессии;
  это правило не требует вызова `CheckSession` другими сервисами на каждый запрос.
- Это решение заменяет требование немедленного отзыва в разделе «Согласованные
  правила login, refresh и logout» связанного документа system-design для
  сценариев, которые проверяют JWT локально.
- Logout-all и создание сессии одного пользователя сериализуются через
  блокировку пользователя. Сессия, создание которой зафиксировано до того,
  как logout-all получил блокировку, отзывается; создание, получившее эту
  блокировку после завершения logout-all, может выдать новую сессию. Это
  правило применяется и к входу, и к выдаче сессии после регистрации.
- Состояние токена и сессии, предъявленных для logout-all, повторно проверяется
  внутри транзакции после получения блокировки, чтобы два одновременных
  logout-all не подтвердили успех для уже отозванной сессии.

## Данные и конфиденциальность

Identity владеет `auth_sessions` и `refresh_tokens`. Открытые токены, их
секреты, заголовки авторизации и персональные данные не записываются в логи
и не попадают в ошибки. Клиент удаляет свои токены после подтверждённого выхода;
реализация Flutter остаётся отдельной задачей.
