# Задачи: рефакторинг Gateway

> **Спецификация:** [spec.md](spec.md)  
> **План:** [plan.md](plan.md)  
> **Статус:** in-progress; выполнены каркас и основа запроса/ошибок (Э02–Э03).

Основание — целевые решения Spec 012. Старый код Gateway не определяет требования.
Начало изменения приложения и удаления старого кода требует команды на реализацию.
T003/T005 — сводные задачи: закрываются только после всех их подзадач и T007–T012.
Решённый вопрос не означает выполненную реализацию или пройденный тест.

Основная задача — [шесть согласованных пунктов в spec.md](spec.md#цель):
разрешённые маршруты, пропуск проверки для публичных операций, JWT и сессия
для защищённых, передача разрешённых запросов или ошибка; бизнес-правила — в сервисе.
Технические задачи ниже обеспечивают этот поток и не расширяют его функциональность.

## Порядок написания кода

Работать по этапам Э01 → Э11. Это основной порядок выполнения; разделы ниже
сохраняют подробные критерии и прежние номера задач, на которые ссылается spec.
Внутри этапа сначала код, затем его проверки. Следующий этап начинается после
проверки результата предыдущего. Сводные T003/T005 не являются отдельными этапами.
Пользователь разрешил реализацию непосредственно в gateway-service после удаления
старого кода и локальные коммиты после проверенных задач. T002b–d остаются открытыми;
их проверки выполняются вместе с соответствующими частями сервиса, без отдельного стенда.

| --- | --- | --- |
| Э01 | Подготовить сборку и технические решения | T001, T002a–d: матрица пяти маршрутов, версии, воспроизводимая сборка; проверены точки подключения отмены HTTP, ошибок и блокировки до готовности. Неподтверждённые свойства не объявлены работающими. |

| Э03 | Сделать основу запроса и ошибок | T003c и основа T003h: request ID, монотонный deadline, DTO/коды/writer, MDC cleanup. Проверки T005d; единый ID и формат ошибок до MVC, изоляция параллельных запросов. |
| Э04 | Загрузить ключи и управлять готовностью | T009 (загрузка), T010: повторы до успеха, not ready до ключей, запрет обслуживания даже при прямом доступе, management и остановка. Проверки T005g: отказ/восстановление JWKS, атомарная публикация, отсутствие загрузок после успеха. |
| Э05 | Описать маршруты и отсечь неподдерживаемые запросы | T003b, T008, T012: единый каталог, 404/405/Allow, query 400, без разрешающего CORS. T005a и часть T005g: правильный порядок отказов, отсутствие вызовов JWT/сессии/downstream. Защищённый маршрут остаётся закрытым до Э07. |

| Э07 | Проверять активность сессии | T003e, завершение защитной цепочки T003d/T007: CheckSession только после корректного JWT; INVALID → 401, технический сбой → 503, без downstream. Сессионная часть T005c, передача остатка deadline и request ID в gRPC. |
| Э08 | Передавать разрешённый запрос в Identity | Маршрутизация T003b, T003g и Token Relay из T003d: общий транспорт, allowlist заголовков, исходный bearer на защищённом маршруте, удаление Authorization на публичных. T005b и проверка заголовков на тестовом downstream; никакого проксирования при отказе предыдущих этапов. |
| Э09 | Завершить отмену HTTP и транспортные ошибки | T003f, завершение T003h, T011: общий deadline до конца тела, cleanup, 502/504, отсутствие записи после commit; без прикладного лимита тела. T005e/T005f: медленная передача, гонки, отсутствие утечек и влияния отмены на следующий запрос. |
| Э10 | Проверить весь поток целиком | Завершить T005a–g на собранном Gateway: пять операций, refresh/logout-all, отзыв сессий, startup/readiness, отсутствие двойных фильтров, ID/ошибки, отсутствие секретов в логах. Ранее пройденные тесты повторяются в общей сборке. |
| Э11 | Завершить проверки и документацию | T006: formatter/static analysis/build/tests, команды и результаты, инструкции запуска и смены ключей. Закрыть T003/T005 только по доказательствам. |

Части одной задачи могут проходить через несколько этапов: например, T003h
начинается с DTO/writer в Э03, подключает security-ошибки в Э06 и завершается
транспортными ошибками в Э09. До выполнения всех частей задача остаётся открытой.
Это исключает требование написать весь Gateway, прежде чем проверить первый шаг.

## Сквозные решения grilling: реализация и критерии

- [ ] T007: Привести ошибки к окончательной модели: неверный JWT и неизвестный kid
  после загрузки — 401; технический сбой CheckSession — 503. Сетевой загрузки JWKS
  в пользовательском запросе нет. До первичной загрузки Gateway не готов (T009/T010).
- [ ] T008: Мобильный клиент, без разрешающих CORS-заголовков/preflight-исключения;
  OPTIONS на известном пути — 405 с Allow, на неизвестном — 404.
- [ ] T009: Загрузить JWKS до готовности, повторять до успеха без общего лимита.
  Применить таймаут/паузу из spec; исключить параллельные попытки. Атомарно опубликовать
  корректный набор, прекратить загрузки до перезапуска; без TTL и скрытого refresh.
  Проверить недоступный/некорректный JWKS, восстановление, остановку, неизвестный kid,
  локальную валидацию без сети. Описать и проверить сценарий смены набора при рестарте.
- [ ] T010: До ключей readiness=false и пользовательский API не обслуживается,
  включая прямое обращение к порту; management доступен для диагностики.
  Ожидание ключей не ломает liveness. После инициализации сбой Identity сам по себе
  не снимает readiness. Проверить оба состояния и переход между ними.
- [ ] T011: Не вводить прикладной лимит тела/RequestSizeLimitFilter/собственный 413
  по такому лимиту. Это не отменяет deadline и реальные ограничения транспорта.
- [ ] T012: Query string отклоняется после пути/метода, до JWT/CheckSession;
  400 invalid_request с общим DTO/request ID, без downstream. Проверить приоритет
  404/405, запросы без query и запрет извлечения токенов из query.
