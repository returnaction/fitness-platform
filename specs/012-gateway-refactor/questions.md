# Вопросы Spec 012

## Текущий статус

Ключи загружаются до готовности с повторами до успеха; после загрузки сетевого
обновления нет. Неизвестный kid даёт 401. Открытых продуктовых вопросов в этом
списке нет. Технические проверки и реализация остаются открытыми в tasks.md;
завершение обсуждения не является разрешением на реализацию.

## Q1 — Недоступность JWKS

- Задачи: T002, T003, T005, T007, T009.
- Основание: раздел JwtDecoderConfiguration оставляет кеш, обновление и недоступность
  JWKS открытыми; SecurityErrorHandler описывает 401 для ошибок аутентификации и
  отдельно 503 для технической недоступности Identity. Случай загрузки ключей
  явно не разграничен.
- Варианты: считать невозможность проверки ошибкой токена (401); различать
  недействительный токен (401) и невозможность проверки из-за зависимости (503).
- Рекомендация: второй вариант. Известный ключ в действующем кеше можно использовать
  для полной проверки подписи; отсутствие необходимого ключа из-за сетевого сбоя
  означает 503 без доступа. Заведомо недействительный токен — 401.
- Блокировка решения снята; реализация и тесты остаются открытыми.
- Статус: согласовано пользователем: 503 при технической невозможности проверки, 401 при недействительном JWT; действующий кеш разрешён. Историческая формулировка уточнена Q3–Q4/Q8/Q9: TTL и обновлений нет; до первичной загрузки Gateway не готов, после неё проверка локальна.

## Q2 — Клиенты первого выпуска

- Задачи: T002, T003, T005, T008.
- Основание: раздел «Пользователи и права» обозначает клиента как «Фронт»,
  но не определяет браузерные origins и поддержку отдельного web-фронтенда.
  Публичный каталог содержит только четыре POST-операции, защищённый — logout-all;
  политика браузерного preflight не определена.
- Варианты: мобильный/API-клиент без cross-origin web-доступа; также web-фронтенд
  с другого origin; web-фронтенд с того же origin.
- Рекомендация: если браузерный клиент не нужен для первого выпуска, не добавлять
  cross-origin доступ. Если нужен — определить его явно сейчас, затем уточнить origins
  и preflight. Выбор зависит от продукта, а не от существующего кода.
- Блокировка решения снята; реализация и тесты остаются открытыми.
- Статус: согласовано пользователем: мобильное приложение, браузерного клиента нет; разрешающий CORS и исключение preflight не добавляются.

## Q3–Q4 — Заменены решением о загрузке при старте

Ранее обсуждались запрет просроченного кеша, TTL 5 минут и обновление раз в минуту.
Пользователь выбрал однократное получение JWKS при старте. TTL и периодический
опрос не вводятся; набор используется до завершения процесса. Задачи: T009/T005.
Смена набора в Identity требует перезапуска Gateway для загрузки нового набора.
Частота ротации в Identity в Spec 012 не определена.
### Q5 — Readiness при недоступности Identity
- Задачи: T002, T010, T005.
- Основание: раздел RouteValidationFilter оставляет management открытой частью T002;
  семантика readiness относительно внешних зависимостей не определена.
- Варианты: исключать Gateway из обслуживания при сбое Identity; сохранять готовность
  самого Gateway и возвращать предусмотренные ошибки конкретным запросам.
- Рекомендация: второй вариант. Локальная неготовность Gateway влияет на readiness;
  сбои Identity отражаются отдельной диагностикой, не вызывают циклов перезапуска.
- Блокировка решения снята; реализация и проверки остаются открытыми.
- Статус: согласовано пользователем: недоступность Identity не делает Gateway неготовым. При полном отказе Identity login/refresh также недоступны; готовность Gateway не означает успех его зависимых операций.

### Q6 — Предел размера входящего auth-запроса
- Задачи: T002, T011, T005.
- Основание: раздел «Заголовки и входящий запрос» не определял предел тела.
- Рассмотрено: ограничение на Gateway, отдельном внешнем входе или в Identity.
- Предложение ограничения на Gateway отклонено пользователем.
- Решение: в Spec 012 прикладное ограничение размера тела на Gateway не добавлять.
  RequestSizeLimitFilter и собственный ответ 413 по такому лимиту не реализуются.
  Это не обещание неограниченных ресурсов транспорта и не изменение других сервисов.
- Статус: согласовано; блокировка снята, проверка реализации остаётся открытой.

### Q7 — Query-параметры текущих auth-маршрутов
- Задачи: T002, T012, T005.
- Основание: query-параметры не описаны контрактом пяти текущих операций.
- Рассмотрено: передавать query или отклонять неподдерживаемый формат.
- Решение: отклонять query с 400 invalid_request без downstream; неизвестный путь
  и неверный метод сохраняют приоритетные 404/405. Токены из query не извлекаются.
- Статус: согласовано; блокировка снята, реализация и тесты остаются открытыми.
## Q8 — Первоначальная готовность без ключей
- Задачи: T009, T010, T005.
- Основание: первоначальная инициализация отличается от отказа Identity после загрузки ключей.
- Решение пользователя: повторять загрузку до получения корректного набора; до успеха
  Gateway не готов (readiness=false). Не завершать запуск ошибкой из-за временной
  недоступности JWKS и не объявлять готовность без ключей.
- Каждая попытка имеет конечный таймаут, между попытками есть пауза; общего лимита
  попыток нет. После успеха повторы прекращаются. Shutdown прекращает ожидание.
- Q5 сохраняется после успешной инициализации: последующий сбой Identity не снимает
  готовность самого Gateway. Ожидание первоначальных ключей не является сбоем liveness.
- Статус: согласовано; реализация и проверки остаются открытыми.
## Q9 — Неизвестный kid после успешной загрузки ключей
- Задачи: T009, T007, T005.
- Основание: T009 оставляет отказ при неизвестном kid открытым; автоматическая
  повторная загрузка исключена. Ключ может быть чужим или новым ключом Identity.
- Варианты: 401 invalid_access_token как неподтверждённый доверенным набором токен;
  503 authentication_unavailable как невозможность проверки потенциально нового ключа.
- Решение: после успешной загрузки неизвестный kid даёт 401. Новый ключ Identity
  тоже не принимается до перезапуска Gateway, поэтому процедура смены должна
  предусматривать согласованный перезапуск. Не запускать запрос JWKS по неизвестному kid.
- Блокировка Q9 снята; реализация и проверки остаются открытыми.
- Статус: Q9 согласован пользователем. Поведение до загрузки определяется отдельно в Q8.
