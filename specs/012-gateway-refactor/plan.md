# План реализации: рефакторинг Gateway

> **Статус:** implemented-and-verified (реализовано и проверено локально)<br>
> **Спецификация:** [spec.md](spec.md)  
> **Задачи:** [tasks.md](tasks.md)  
> **Решения grilling:** [questions.md](questions.md)

Основная задача — [шесть согласованных пунктов в spec.md](spec.md#цель):
разрешённые маршруты, пропуск проверки для публичных операций, JWT и сессия
для защищённых, передача разрешённых запросов или ошибка; бизнес-правила — в сервисе.
Технические задачи ниже обеспечивают этот поток и не расширяют его функциональность.

## Основание и границы

Новая реализация выполнена по Spec 012. Старый код Gateway не является
источником требований. Пользователь удалил старые исходники и тесты в коммите
fb56c0c; модуль сохранён и реализован заново. Сверка замены — T003a0.
Меняется только Gateway и его пять POST-маршрутов Identity; новые API, Accounts,
схемы БД и миграции не входят в работу. Изменение принимающих сервисов,
pre-authentication и закрытие обхода Gateway — отдельная последующая работа.
Собственная проверка Identity для logout-all пока сохраняется.

## Архитектура

Spring Cloud Gateway Server Web MVC, виртуальные потоки, общий HTTP-транспорт.
Без Resilience4j, semaphore, отдельных пулов и квот по downstream. Список операций
единственный — GatewayRouteCatalog; маршрутизация и policy строятся из него.
Версии и совместимость библиотек, API и инструментов проверяются в T002a;
примеры spec не являются проверенной сборкой.

Клиент — мобильное приложение. Разрешающий CORS и preflight-исключение не добавляются.
Прикладной лимит размера тела не вводится. Неограниченность ресурсов транспорта
не обещается. Query string на пяти auth-операциях отклоняется с 400 invalid_request.

## Запуск и ключи

До готовности Gateway получает корректный JWKS из доверенного адреса Identity.
Попытка ограничена 3 секундами, после неудачи пауза 5 секунд; общего предела попыток
нет. Это настройки первоначальной загрузки, независимые от deadline запросов.
До успеха readiness=false и пользовательский API не обслуживается, включая прямое
обращение к порту; management доступен. Способ изоляции проверить в T002d.
Ожидание само по себе не является сбоем liveness; shutdown прекращает попытки.

После успешной атомарной загрузки набор хранится до завершения процесса:
TTL, периодического обновления и сетевых обращений decoder нет. Неизвестный kid
даёт 401 invalid_access_token. Для смены набора нужен перезапуск; плановую и
экстренную процедуры описывает spec. Возможности Identity для бесшовной ротации
не проверены, его изменения здесь не реализуются.
После инициализации сбой Identity сам по себе не снимает готовность Gateway;
ошибки конкретных операций сохраняются. При полном отказе Identity login/refresh
тоже не работают. Прежняя модель 503 от загрузки JWKS внутри запроса заменена.

## Обработка запроса

Условие входа — Gateway готов. Порядок:

1. Общий монотонный deadline 3 секунды и новый UUID запроса.
2. Путь/метод по каталогу: 404 либо 405 с Allow.
3. Query string: 400 invalid_request, без последующих проверок и downstream.
4. Для logout-all: локальная проверка JWT/claims, затем CheckSession по gRPC.
5. Разрешение маршрута, исходящие заголовки и HTTP-вызов с остатком бюджета.

Register/login/refresh/logout пропускают JWT и CheckSession, Authorization удаляется.
Logout-all получает исходный проверенный bearer. Поддельные user/role headers не
передаются. Request ID общий для HTTP/gRPC/MDC/ответа. При отказе последующие этапы
не вызываются; фильтры не регистрируются дважды.

Оба JWT-валидатора используют один Clock; общий deadline использует монотонное
время. CheckSession INVALID даёт 401, техническая недоступность — 503 без HTTP-вызова.
Таймаут downstream до commit — 504; после commit передача прерывается без нового JSON.
Отмена HTTP-ожидания не гарантирует отмены операции Identity; автоматический повтор
изменяющего запроса не добавляется.

## Технические проверки и результат

HTTP-отмена и обработка ошибок реализованы и проверены в основном модуле (Э09).
Результаты — в [tasks.md](tasks.md), T003f/T003h, и
[technical-review.md](technical-review.md).

Обновление Э10 (2026-11-12): основной verify и сквозной сценарий с настоящими
четырьмя сервисами, отдельными временными БД и mTLS прошли. Проверены public bearer
bypass, refresh/replay, отзыв сессий, отказ Identity, ID/логи и смена JWKS после
рестарта. Сценарий и команды находятся в [README Gateway](../../services/gateway-service/README.md).
Э11: финальный clean verify и сборка Docker-образа прошли, документация обновлена.

Проверка документации и API выполнена: [результаты и ограничения](technical-review.md).
Выбраны ApplicationRunner и gate пользовательского API для начальной готовности,
глобальный advice без selectors и адаптер общей HTTP-фабрики для отмены.
Прерывание медленного входного тела и исполняемая сборка проверены на закреплённом стеке.

T002b проверяет реальную отмену HTTP, включая медленную передачу и получение
соединения, общую длительность, cleanup, async/error dispatch и гонки.
Общий планировщик отменяет вызов, не пишет ответ; регистрация живёт до конца тела.
Проверка чтения входного тела также необходима — одних сетевых read timeout недостаточно.

T002c проверяет ошибки servlet/security/firewall/MVC и применимость advice к
функциональным маршрутам. Общие GatewayErrorCode и ApiErrorResponse используются
через writer или MVC advice; после commit повторная запись исключена.

Проверки выполнены на фактических версиях библиотек. Адаптер клиентского
чтения/записи рассчитан на Tomcat HTTP/1.1; другой контейнер или HTTP/2 требуют
отдельной реализации и проверки. Развёртывание и защита от обхода Gateway
в этот результат не входят.

## Порядок выполнения и доказательства

Порядок кода и проверок задан этапами Э01–Э11 в
[tasks.md](tasks.md#порядок-написания-кода): подготовка → каркас → request ID/deadline
и ошибки → ключи/готовность → каталог → JWT → сессия → проксирование → отмена HTTP
и транспортные ошибки → сквозная проверка → итоговые проверки и документы.
Каждый этап включает собственные проверки; тесты не откладываются до конца.
Идентификаторы T001–T012 и их критерии сохранены, соответствие этапам указано в таблице.
Проверки включают маршруты, JWT/claims, отзыв сессии, startup/readiness, неизвестный
kid, отсутствие загрузок после успеха, исходные токены, CORS/query, общий deadline,
гонки/отмену, единый DTO и отсутствие утечки секретов. Команды build/formatter/
static analysis/tests и локального запуска приведены в README Gateway.
Все задачи Spec 012 закрыты по результатам проверок; последующая работа вне
спецификации остаётся отдельной и автоматически не запускается.
