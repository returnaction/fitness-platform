## Краткое решение

Maven-модуль `services/gateway-service` использует Temurin 25.0.5 / Spring Boot
4.1.2 и Spring Cloud BOM 2025.1.4 (Gateway Server MVC 5.0.4). Совместимость
подтверждена [официальной матрицей](https://spring.io/projects/spring-cloud/)
и сборкой/запуском. MVC сохраняет стек проекта и синхронный gRPC-клиент.
Apache HttpClient (версия Boot BOM) явно отключает retries, redirects и cookies.
Численные настройки и ошибки закреплены в [контракте Gateway](../../contracts/gateway-v1.md).

Общий документ доступа содержит открытые вопросы; более конкретный контракт
сессий уже требует JWT + CheckSession. Использовать этот контракт и при
реализации актуализировать общий документ, не выдавая черновик за готовую систему.

## Затрагиваемые границы

Первая версия запускается локально в одном экземпляре. Остановка Gateway
означает недоступность API; отказоустойчивость этим этапом не заявляется.
Фронт не переключать: готовность сервера проверяется независимо от приложения.

| Область | Изменение | Владелец |
| --- | --- | --- |
| Gateway | Маршруты, входная проверка, лимиты и ошибки прокси | Gateway |
| Identity | Разрешённая service identity Gateway, JWKS и существующий CheckSession | Identity |
| Клиент | Документированный базовый URL Gateway | Мобильное приложение |
| Локальная среда | Закрытые порты upstream, сертификаты и настройки | Инфраструктура проекта |

## Данные и миграции

Новая БД и миграции не нужны. Таблицы сессий остаются в Identity.
Gateway не держит транзакции и не читает базы других сервисов. Идемпотентность
auth-команд остаётся в существующих контрактах. Автоматические повторы
проксируемых изменяющих запросов отключены.

## Контракты и взаимодействия

- Клиент → Gateway → Identity: только POST register/login/refresh/logout/logout-all
  под `/api/v1/auth`. Первые четыре не требуют access JWT на Gateway;
  logout-all требует JWT и активной сессии. Существующие DTO не копировать в
  новую модель бизнес-логики Gateway. Сохранить `Cache-Control: no-store`.
- Gateway → JWKS Identity: доверенный конфигурационный адрес, ограниченный кеш,
  обновление при неизвестном `kid` с защитой от лавины запросов. Недоступность
  ключей без пригодного кеша — временный `503`; подтверждённо неверный токен — `401`.
- Gateway → Identity: [identity-session-v1.proto](../../contracts/proto/identity-session-v1.proto),
  `request_id`, `user_id=sub`, `session_id=sid`; ответы ACTIVE/INVALID.
  URI SAN Gateway: `spiffe://fitness.local/gateway-service`;
  настроить `IDENTITY_SESSION_GRPC_ALLOWED_CALLER`. Проверять CA, имя сервера,
  клиентский сертификат и право `identity.session.verify`.
- Для CheckSession: одна попытка с deadline 2500 мс, без автоматических повторов.
  Это укладывается в максимальный бюджет существующего контракта; постоянные
  ошибки mTLS/прав также не повторяются.
  Начальные 1000 мс оказались недостаточны для первого вызова в сквозном тесте
  при параллельной сборке; после наблюдаемого DEADLINE_EXCEEDED выбран общий
  бюджет 2,5 секунды и предварительное установление канала при запуске.
- До кода зафиксировать в `contracts/` таблицу маршрутов, примеры запросов,
  ошибки Gateway с `request_id`, численные лимиты и правила заголовков.

## Надёжность и безопасность

Для v1 передавать исходный Bearer-токен Identity, сохраняя его собственные проверки.
Не вводить доверие к простому `X-User-Id`. Внешние identity/role-заголовки удалять;
forwarded-заголовки принимать только от явно доверенного прокси, иначе заменять.
Согласовать это с существующим определением клиентского IP и rate limiter Identity.
HTTP upstream в локальной среде закрыть от внешней сети; для удалённых соединений
предусмотреть TLS. Проверить обход снаружи той сети, которая считается недоверенной.

Внешний API использует HTTPS, локальный HTTP допускается только в явно описанном
режиме разработки. Публичный запуск и production HTTPS — отдельный этап.
Браузерных клиентов не будет: разрешённые CORS origins отсутствуют,
разрешающие CORS-заголовки не выдаются. Это не заменяет проверку доступа.
Установить лимиты тела, соединений и времени ответа. Не раскрывать upstream URL
и исключения. Management вынести отдельно; health не должен раскрывать секреты.
Метрики: длительность, статусы, ошибки CheckSession, отказы маршрутизации.

## Проверка

- Обновить `postman/fitness-local.postman_collection.json`: использовать `base_url`
  Gateway, сохранить существующие auth-запросы, добавить refresh с обновлением
  токенов и assertions статусов/ответов. Для проверки отзыва сохранить старый
  access-токен до очистки переменных logout. Добавить отсутствие/подделку токена,
  недоступность Identity и запрет внутренних маршрутов. Не сохранять реальные
  пароли и токены в экспортируемой коллекции; ручные проверки дополняют тесты.
- Зафиксировать для будущего клиента: при `503` сохранять токены и показывать
  временную ошибку. Реализация и проверка этого поведения во Flutter отложены
  до отдельного запроса владельца и не блокируют завершение серверной части.

- Unit: разрешённые пути/методы, claims, заголовки, ошибки, таймауты и лимиты.
- Integration: реальный HTTP proxy, JWKS с ротацией, gRPC mTLS с временными
  сертификатами; отказ неизвестному клиенту и отказ при неверном сертификате сервера.
- Сквозные: Gateway + Identity с изолированной PostgreSQL; login, refresh,
  logout, logout-all, отозванный токен, сбой проверки сессии и гонка с logout.
- Проверить отсутствие повторов POST, сохранение ответов и отсутствие секретов
  в логах. Проверить подделку forwarded-заголовков и невозможность прямого доступа.
- Maven Wrapper verify, форматирование и статический анализ по правилам проекта.
  Не запускать миграции против пользовательской БД.

## Риски и решения

| Риск | Решение |
| --- | --- |
| CheckSession увеличивает нагрузку и связывает доступность с Identity | Измерить задержки и нагрузку; сохранить немедленный отзыв и fail-closed. |
| Потерянный ответ refresh | Не повторять POST автоматически; сохранить действующий контракт клиента. |
| Несовместимый стек Gateway | Проверить совместимость до закрепления библиотек. |
| Будущий сервис доверяет поддельному ID | Не открывать маршрут до проверки безопасного пользовательского контекста. |
| Несколько экземпляров обходят локальный rate limit | Для v1 описать один экземпляр; распределённый лимит определить до масштабирования. |
