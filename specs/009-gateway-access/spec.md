# Единая точка входа и проверка доступа через Gateway

> **Статус:** implemented
> **Номер:** 009
> **Связанные документы:** [сессии Identity](../../system-design/services/identity/31-identity-login-sessions.md), [внутренние API](../../system-design/interactions/59-identity-accounts-internal-api.md), [мобильный клиент](../008-mobile-flutter-auth/spec.md)
> **Заменяет / заменена:** —

## Цель

Приложение обращается к одному адресу API. Gateway направляет запросы в
нужный сервис и допускает защищённые запросы только с проверенным токеном
и действующей сессией. Identity сохраняет ответственность за пароли и токены.

## Границы

### Входит в эту спецификацию

- Новый `gateway-service`, явный список разрешённых маршрутов и HTTP-методов.
- Проксирование существующих register, login, refresh, logout, logout-all Identity
  с сохранением путей `/api/v1/auth/*`, тел, статусов и `Cache-Control`.
- Проверка access JWT и вызов `CheckSession` по mTLS для защищённых маршрутов.
- Настройка доверия Identity к Gateway, защита внутренних адресов и заголовков.
- Ограничения размера запросов, времени ожидания и частоты запросов.
- Документация единого адреса для клиента и сквозные проверки.
- Один локальный экземпляр Gateway; автоматические тесты и обновление
  [существующей коллекции Postman](../../postman/fitness-local.postman_collection.json).
  Готовность фронта не является условием завершения этой спецификации.

### Не входит в эту спецификацию

- Новые бизнес-API Accounts, Coins, Challenge или каталога упражнений.
  Их маршруты добавляются только после готовности собственных контрактов.
- Изменение сроков токенов, ролей, правил регистрации и отзыва сессий.
- Выдача токенов самим Gateway, чтение им таблиц Identity, собственная БД.
- Агрегация ответов, Kafka, RabbitMQ, service discovery и production-развёртывание.
- Реализация экранов Flutter и переключение приложения на Gateway: только
  по отдельному запросу владельца после готовности фронта.
- Сайт и Flutter Web: продукт предназначен только для мобильного приложения.
- Перенос видеофайлов через Gateway, несколько экземпляров и публичный запуск.

## Пользователи и права

| Участник | Поведение |
| --- | --- |
| Не вошедший пользователь | Может вызвать register/login и предъявить refresh-токен для refresh/logout по существующему контракту. |
| Вошедший пользователь | Может вызвать разрешённый защищённый маршрут после проверки JWT и сессии. |
| Оператор | Доступ к management и recovery осуществляется отдельно; публичный Gateway эти маршруты не открывает. |

## Сценарии

### Вход и обновление

**Дано:** приложение знает адрес Gateway. **Когда:** оно вызывает login или
refresh. **Тогда:** Gateway передаёт запрос Identity без требования действующего
access-токена; Identity проверяет предъявленные данные и возвращает прежний ответ.
Gateway не повторяет автоматически запрос при потере ответа: повтор refresh
может отозвать сессию по действующим правилам Identity.

### Защищённый запрос

**Дано:** JWT и сессия действительны. **Когда:** клиент вызывает logout-all.
**Тогда:** Gateway проверяет JWT, отправляет извлечённые `sub` и `sid` в
`CheckSession`, получает `ACTIVE` и передаёт исходный Bearer-токен Identity.
Identity сохраняет собственную проверку доступа и выполняет операцию.

### Ошибки и граничные случаи

| Условие | Результат |
| --- | --- |
| Нет access-токена, неверны подпись, алгоритм, issuer, audience, claims или срок | `401 invalid_access_token`; бизнес-обработчик не вызывается. |
| `CheckSession` возвращает `INVALID` | `401 invalid_access_token`; запрос не передаётся дальше. |
| Identity не отвечает при проверке сессии | `503 identity_unavailable`; доступ не разрешается. |
| Сервис запрещает доступ к объекту | Сохраняется его `403`; Gateway не отменяет решение сервиса. |
| Неизвестный путь или запрещённый метод | `404` или `405` по зафиксированной таблице маршрутов; произвольного проксирования нет. |
| Превышен лимит | `429` с `Retry-After`; слишком большое тело — `413`. |
| Недоступен HTTP upstream / истёк срок ожидания | Безопасные `502` / `504`; без автоматического повтора изменяющей операции. |
| Клиент прислал поддельные user/role/forwarded-заголовки | Они не становятся доверенным контекстом. |

## Бизнес-правила

- JWT подписывает только Identity. Gateway получает открытые ключи из доверенного
  настроенного JWKS, а не из URL в предъявленном токене. Алгоритм — ES256;
  обязательные claims и максимальный срок определяет контракт Identity.
- На каждом защищённом запросе после проверки JWT выполняется `CheckSession`.
  Положительные ответы не кешируются в v1. Кеш открытых ключей не является
  кешем состояния сессии; обновление ключей ограничено по времени и частоте.
- После подтверждённого logout новые проверки отклоняют отозванную сессию.
  Запрос, прошедший проверку до logout, может завершиться после него.
- Gateway проверяет вход; сервис-владелец проверяет права на конкретное действие.
  Пользовательский JWT не заменяет служебную идентичность.
- Маршруты разрешаются по списку. Recovery, actuator и внутренний gRPC не
  публикуются через клиентский API. Сервисы недоступны извне в обход Gateway.

## Данные и конфиденциальность

Временная ошибка `503` не означает отзыв сессии. Контракт будущего мобильного
клиента: сохранить токены и показать временную недоступность, не выполнять
автоматический выход. Изменения клиента в эту спецификацию не входят.

Браузерные origins не разрешаются; CORS не является защитой от посторонних
клиентов. Мобильное приложение и Postman проходят обычные проверки доступа.

Gateway не хранит пользователей, пароли или сессии. Закрытый ключ Identity
не передаётся Gateway. Пароли, токены, тела auth-запросов, персональные данные
и секреты сертификатов не попадают в логи. Диагностика использует `request_id`
и технические метрики без пользовательских идентификаторов в labels.

## Критерии готовности

- [x] Все пять auth-операций работают через единый адрес с прежним контрактом.
- [x] Поддельный, истёкший токен и отозванная сессия не достигают обработчика.
- [x] Проверены mTLS, запрет постороннего вызывающего и недоступность Identity.
- [x] Подмена заголовков и прямой обход Gateway исключены в проверенной среде.
- [x] Работают ограничения и безопасные ошибки без утечки секретов; разрешающие CORS-заголовки не выдаются.
- [x] Проверены ротация JWKS, logout и повтор refresh при потере ответа.
- [x] Обновлены контракты, настройки и инструкции; необходимые проверки прошли.
- [x] Существующая коллекция Postman проверяет auth через Gateway, включая refresh и отказ после отзыва; реальные секреты не сохранены в Git.

## Открытые вопросы

Границы согласованы владельцем в ходе grilling 11 ноября 2026: auth Identity,
один локальный экземпляр, только мобильный клиент, существующий Postman,
без переключения фронта. Продуктовых вопросов для v1 не осталось.
Технические решения и проверки завершены; см. [результаты](verification.md).
Будущие бизнес-маршруты требуют отдельной проверки доверия и прав перед включением.
