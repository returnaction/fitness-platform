# Пригодность ledger для будущих ставок

Статическое ревью 2026-11-17. Проверены LedgerEntryEntity, LedgerEntryType и
changeset 002. Это разбор модели, не работающая реализация Challenge и не тест API ставок.
Определения таблиц принадлежат [модели Coins](../../system-design/services/coins/36-coins-data-model.md);
будущий процесс описан в [контракте ставок](../../system-design/services/coins/34-coins-stake-and-settlement-contract.md).

## Пример с двумя участниками

У A и B изначально по 30 доступных монет, резерв 0. Ставка каждого — 10.
Все строки имеют user_id, challenge_id, собственный id и время.
O-A, O-B и O-result ниже обозначают разные UUID операций.

| Операция/index | Пользователь | Тип | available_delta | locked_delta | Балансы после записи |
| --- | --- | --- | ---: | ---: | --- |
| O-A / 0 | A | CHALLENGE_STAKE_LOCK | -10 | +10 | A: 20 / 10 |
| O-B / 0 | B | CHALLENGE_STAKE_LOCK | -10 | +10 | B: 20 / 10 |
| O-result / 0 | A | CHALLENGE_STAKE_RELEASE | +10 | -10 | A: 30 / 0 |
| O-result / 1 | B | CHALLENGE_STAKE_FORFEIT | 0 | -10 | B: 20 / 0 |
| O-result / 2 | A | CHALLENGE_WIN_CREDIT | +10 | 0 | A: 40 / 0 |

В примере A победил: собственная ставка возвращена отдельной записью,
выигрыш получен из ставки B. Итог: 40 + 20 = исходные 60, резерв нулевой.
Сумма изменений доступного и резервного балансов по завершённому расчёту равна 0.
Промежуточные записи расчёта не означают самостоятельные завершённые выплаты;
атомарность или учёт промежуточного банка должны определяться будущим контрактом расчёта.

Альтернатива при отмене соревнования после резервирования: каждому записывается
CHALLENGE_STAKE_RELEASE (+10/-10), и оба возвращаются к 30/0.
Отмена и распределение выигрыша — разные взаимоисключающие сценарии.

## Что позволяет существующая модель

- Знаковые delta выражают все четыре вида движений без изменения истории подарков.
- challenge_id связывает движения с соревнованием без FK в чужую базу.
- operation_id объединяет несколько записей одного действия. entry_index должен
  быть уникальным внутри операции **среди всех пользователей**, а не начинаться
  заново для каждого: UNIQUE(operation_id, entry_index) глобален.
- Повтор той же пары operation/index будет отклонён БД. Это защита от повторной
  строки, но не готовый обработчик идемпотентной команды.
- reverses_entry_id позволяет связать новую компенсирующую запись с ошибочной.
  Исходную запись сохраняем; автоматической отмены от заполнения ссылки не происходит.

## Что ещё потребуется при реализации ставок

1. Учёт конкретного резерва и его состояния. Сейчас нет coin_holds в миграциях
   и нет hold_id в ledger. Пара user/challenge не различает повторные участия.
   В будущей схеме нужна явная связь с hold через поле или таблицу операций;
   challenge_id не следует считать достаточной ссылкой на исходный резерв.
2. Идемпотентность команд Reserve/Release/Settle с проверкой совпадения параметров
   и сохранением отказов. daily_reward_requests предназначена только для подарка.
   Новый случайный operation_id при каждом повторе обойдёт уникальность ledger.
3. Проверка наличия монет, состояния резерва, допустимых переходов и полномочий
   Challenge. Обновление баланса, резерва и ledger — согласованная транзакция Coins.
4. Проверка сохранения банка при распределении, округлений и остатка. Одна строка
   WIN_CREDIT сама по себе не доказывает, что сумма обеспечена ставками проигравших.
5. Сумма и знаки для каждого entry_type, обязательность challenge_id для ставок,
   соответствие владельца и суммы reversal сейчас не гарантируются общим CHECK.
   Будущие команды должны проверять эти инварианты; ограничения БД уточняются отдельно.
6. Для разбитого на части расчёта нужно долговечное состояние операции и повторов.
   Нельзя держать транзакцию Coins открытой во время вызова Challenge.

## Вывод для 019

Текущий ledger подходит как основа записи движений подарка и будущих ставок.
Для подарка переделывать схему из-за ставок сейчас не требуется. Полноценная
система резервирования ещё не реализована и потребует добавочных таблиц/связей
и команд в отдельной спецификации. Отчёт подтверждает выразимость движений,
но не готовность API ставок и не доказанную связь с конкретным будущим hold.
