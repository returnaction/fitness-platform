## Цель

Предоставить единый серверный справочник активных упражнений и их вариаций.
Клиент использует его при составлении расписания, а Challenge — для серверной
проверки задания перед публикацией. В первой версии данные только читаются и
поставляются Liquibase-миграциями; администратор их не изменяет.

## Границы

### Входит в эту спецификацию

- Отдельные PostgreSQL-база `fitness_exercise_catalog` и роль приложения.
- Liquibase-миграции категорий, упражнений, вариаций и утверждённых seed-данных.
- Read-only REST: активные категории, список активных упражнений и карточка
  упражнения с активными вариациями.
- Внутренний gRPC Challenge → Catalog: проверка активности и целевого значения,
  возврат доверенного снимка задания.
- Метрики v1: `REPETITIONS` / `REP` и `DURATION` / `SECOND`.
- Unit- и PostgreSQL-интеграционные проверки миграций, чтения и валидации.

### Не входит в эту спецификацию

- Admin API, административные таблицы, аудит, идемпотентность admin-команд.
- Kafka, outbox и события изменений каталога.
- Локализация, медиа, поиск, рекомендации, AI-проверка и новые метрики.
- Ручная правка таблиц, seed-данных или хранение настоящих паролей в Git.
- Изменения Challenge, Video Proof и Moderation сверх согласованной интеграции.

## Пользователи и права

| Роль / сервис | Что может делать |
| --- | --- |
| Авторизованный пользователь | Через API Gateway читать активные категории, упражнения и вариации. Не может менять каталог. |
| API Gateway | Проверять пользовательский access token и направлять разрешённый REST-запрос в Catalog. |
| `challenge-service` | Вызывать внутренний gRPC для проверки вариации и цели перед публикацией. |
| Администратор PostgreSQL | Один раз создаёт базу и прикладную роль по инструкции подготовки базы. |
| Администратор каталога | В MVP не имеет endpoint для изменения данных. |

## Сценарии

### Пользователь выбирает упражнение

**Дано:** миграцией загружены активные категория, упражнение и `STANDARD`.
**Когда:** пользователь отправляет REST-запрос с access token в API Gateway,
а Gateway успешно проверяет token и направляет запрос в Catalog.
**Тогда:** он получает только активные записи, их метрику, инструкцию, минимум,
максимум и шаг допустимой цели.

### Challenge публикует расписание

**Дано:** Challenge получил `exercise_id`, `variation_id` и положительный
`target_value`. **Когда:** он вызывает Catalog по gRPC перед публикацией.
**Тогда:** Catalog проверяет всю активную цепочку, диапазон и шаг, затем
возвращает доверенный snapshot. Challenge сохраняет его в своей БД.

### Каталог временно недоступен

**Дано:** Challenge готовит публикацию. **Когда:** Catalog отвечает
`UNAVAILABLE` или истекает deadline. **Тогда:** Challenge не публикует
challenge по данным клиента, сохраняет черновик и повторяет проверку позднее.

### Ошибки и граничные случаи

| Условие | Ожидаемое поведение |
| --- | --- |
| Неизвестное либо неактивное упражнение при публичном чтении | `404 not_found`, без раскрытия выключенной записи. |
| Неактивная категория, упражнение или вариация по gRPC | Бизнес-исход `INACTIVE`; публикации нет. |
| Цель вне диапазона или не кратна шагу | `TARGET_OUT_OF_RANGE` либо `TARGET_STEP_INVALID`; публикации нет. |
| Неизвестный ID по gRPC | `NOT_FOUND`; публикации нет. |
| У пользователя нет действительного access token | API Gateway возвращает `401 unauthenticated`; Catalog не получает запрос. |

## Бизнес-правила

- Catalog — единственный владелец своих таблиц; другие сервисы не имеют прямого
  подключения, внешних FK и общей транзакции с ним.
- Физического удаления нет. `is_active` и `version` создаются сразу, но в MVP
  меняются только новой Liquibase-миграцией.
- Каждое активное упражнение имеет активную вариацию `STANDARD`.
- Цель — положительное `int64`; сервер не доверяет метрике, диапазону или
  названию, присланному телефоном.
- Симметричные вариации используют `target_step = 2`.
- Catalog не хранит опубликованные snapshot Challenge и не меняет старые
  challenge после будущей правки справочника.
- API Gateway — единственная внешняя точка входа в REST Catalog: он валидирует
  пользовательский JWT. Catalog не разбирает, не валидирует и не авторизует
  пользовательский token.
- REST-порт Catalog не публикуется в интернет и принимает запросы только от
  доверенного Gateway во внутренней сети. Внутренний gRPC принимает только
  удостоверенный `challenge-service`.

## Данные и конфиденциальность

Catalog не хранит профиль, пароль, токен, ставку, видео или данные участника.
Публичный API отдаёт только активные справочные записи. Пароль роли PostgreSQL
находится только в игнорируемом `.env` либо защищённой конфигурации среды;
пароли, токены и заголовки авторизации не попадают в журналы.

## Критерии готовности

- [ ] База и наименее привилегированная роль описаны; Liquibase управляет
  схемой, но не создаёт базу или роль.
- [ ] Миграции на чистой PostgreSQL создают каталог и утверждённые seed-данные.
- [ ] Gateway возвращает `401` для неавторизованного внешнего запроса; Catalog
  выдаёт Gateway только активный каталог и корректно обрабатывает `404`.
- [ ] Единый use case валидирует цель и используется gRPC endpoint-ом.
- [ ] Challenge получает snapshot или различимый бизнес-исход; временный сбой
  не приводит к публикации.
- [ ] Тесты покрывают миграции, диапазоны, шаги, активность и gRPC-ошибки.
- [ ] Admin API, admin-таблицы и события не добавлены.

## Открытые вопросы

- Утвердить точные тексты инструкций, описаний, кодов и ограничений seed-данных.
- Согласовать формат cursor для `GET /api/v1/exercises`.
- Согласовать технический механизм доверия Gateway → Catalog во внутренней
  сети и service identity для gRPC. Пользовательский JWT уже закреплён за
  Gateway и не является предметом проверки Catalog.
- Решить отдельным ADR, будет ли Catalog самостоятельным развёртываемым
  процессом уже в MVP. Эта спецификация предполагает отдельную БД и модуль
  сервиса, но не утверждает deployment-топологию.
