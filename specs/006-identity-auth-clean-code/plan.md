# План: понятный код входа и обновления сессии

> **Спецификация:** [spec.md](spec.md)
> **Статус:** implemented
> **Связанные документы:** [инженерные стандарты](../../docs/engineering-standards.md), [JWT и роли](../005-jwt-role-claims/spec.md), [выход из сессии](../003-session-logout/spec.md)

## Краткое решение

Зафиксировать существующие HTTP-ответы в тестах. JWT обязателен по решению
владельца: прежний флаг выключения не должен отключать подпись. Упростить вход
и refresh и перенести формирование ошибок в общий обработчик. Сохранять
контракты и безопасность.

Целевая форма контроллера входа — ориентир, а не требование буквально
скопировать имена типов:

```java
@RestController
@RequestMapping("/api/v1/auth")
@RequiredArgsConstructor
public class LoginController {

    private final LoginService loginService;

    @PostMapping("/login")
    ResponseEntity<LoginTokenResponse> login(@RequestBody LoginRequest request) {
        LoginTokenResponse response = loginService.login(request);

        return ResponseEntity.ok()
                .header(HttpHeaders.CACHE_CONTROL, "no-store")
                .body(response);
    }
}
```

Аналогично контроллер refresh принимает DTO, вызывает сервис и возвращает
успешный ответ. Ошибки и `request_id` формирует `ApiExceptionHandler`.
При реализации проверить, что это не меняет сообщения и `Cache-Control` ошибок.

## Карта классов Identity

Пути указаны относительно пакета `io.github.returnaction.fitness.identity`.
Это план рефакторинга: новые имена появятся только при реализации.

| Класс или пакет | Ответственность | Планируемое изменение |
| --- | --- | --- |
| `session.controller.LoginController` | Принимает HTTP-запрос входа и возвращает успешный ответ. | Переименовать `PendingLoginController` и убрать обработку ошибок. |
| `session.service.LoginService` | Проверяет пользователя, пароль и статус; запускает создание сессии и токенов. | Переименовать и упростить `PendingLoginService`. |
| `session.repository.LoginRepository`, `session.model.LoginUser` | Ищет данные для входа и возвращает их в понятной модели. | Использовать `Optional`, сохранять проверку пароля с `dummyHash` при отсутствии пользователя. |
| `session.dto.LoginRequest`, `LoginTokenResponse` | Данные HTTP-запроса и успешного ответа входа. | Отдельный DTO входа сохраняет формат JSON. |
| `shared.validation.CredentialsValidator` | Проверяет учётные данные и нормализует email для входа и регистрации. | Использует общий `ValidatedCredentials`, не обращается к БД. |
| `session.controller.RefreshController` | Принимает запрос refresh и возвращает успешный ответ. | Убрать выбор ошибок, получение `request_id` и `ObjectProvider`. |
| `session.service.RefreshTokenService` | Проверяет и ротирует refresh в транзакции, сохраняет отзыв сессии при повторе. | Упростить логику без изменения порядка блокировок и транзакции. |
| `session.dto.RefreshRequest`, `RefreshResponse` | Данные запроса и ответа refresh. | Использовать существующие DTO, сохранив контракт. |
| `session.exception` | Понятно обозначает ошибки входа и refresh. | Добавлять типы ошибок по необходимости, без дублирования общих ошибок. |
| `shared.web.ApiExceptionHandler` | Преобразует ошибки в единый HTTP-ответ и добавляет `request_id`. | Дополнить существующий обработчик; сохранить статус, код, сообщение и заголовки. |
| `session.service.SessionTokenService` | Выпускает токены при входе и регистрации в транзакции. | Общий сервис вместо `RegistrationTokenService`. |
| `session.model.IssuedTokens` | Внутренний результат выдачи пары токенов. | Отдельный `record`; `toString` не раскрывает токены. |
| Существующие репозитории и компоненты подписи JWT | Работа с данными и подпись токенов. | Переиспользовать; сохранить границы транзакций. |

Преобразование результата повторного refresh в HTTP-ошибку должно происходить
после фиксации транзакции, сохранившей отзыв сессии. Отдельный сервис или фасад
добавляется только если это нужно для понятной границы транзакции; заранее его
название и создание не предписываются.

## Затрагиваемые границы

| Область | Изменение | Владелец |
| --- | --- | --- |
| Identity: session | Понятные контроллеры, сервисы, DTO и обработка ошибок login/refresh | Identity |
| Identity: JWT и связанные компоненты | Обязательная конфигурация ключей и обычные зависимости | Identity |
| Тесты и документация | Сохранение поведения и настройка временных ключей | Identity |

Уточнить имена `PendingLoginController` и `PendingLoginService`, отражающие
только один из обрабатываемых статусов. Проверить вызовы и тесты до переименования.
Не вводить посредников без реальной ответственности; явно обосновать отдельную
границу там, где она нужна для транзакции.

По решению владельца в эту ветку также входит обязательный запуск компонентов
Accounts/Coins, worker и внутреннего сервера проверки сессий. Тестировать
некорректную конфигурацию и перезапуск/недоступность сервисов. Внутренний сервер
по-прежнему требует mTLS и явный URI доверенного клиента; не расширять доступ.

## Данные и миграции

Изменений схемы нет. Использовать существующие JPA/Hibernate-репозитории.
Не удерживать транзакцию при сетевом вызове и не менять порядок блокировок.
После корректного повтора refresh отзыв сессии должен быть зафиксирован до
передачи ошибки в HTTP-слой. Не выбрасывать непроверенное runtime-исключение
внутри транзакции, которое откатит отзыв: отдельно проверить границу commit.

## Контракты и взаимодействия

Источники истины: [OpenAPI](../../contracts/openapi/identity-auth-v1.yaml),
[регистрация](../001-user-registration/spec.md), [выход](../003-session-logout/spec.md)
и [роли](../005-jwt-role-claims/spec.md). Сохранить поля, HTTP-статусы, коды и
сообщения ошибок, `request_id`, заголовки и текущие правила авторизации.
Режим запуска без JWT убирается намеренно; обновить `.env.example`, локальную
документацию и потребителей настроек. Не менять реальные `.env` и ключи пользователя
без необходимости и предварительной проверки.

## Надёжность и безопасность

- Проверить все `@ConditionalOnProperty(identity.jwt.enabled)` и `ObjectProvider`,
  включая registration, security, JWKS и recovery; менять только зависимости,
  необходимые для обязательного JWT, сохраняя их поведение.
- Отсутствующие, повреждённые или несовместимые ключи должны приводить к
  понятной ошибке запуска; тесты генерируют собственные временные ключи.
- Уважать существующую атомарность и порядок блокировок при refresh; правильный
  повтор старого токена отзывает сессию, неправильный секрет её не отзывает.
- Не раскрывать секреты или персональные данные в ответах и логах.

## Проверка

- HTTP: login/refresh успех, неверные данные, PENDING, недоступный аккаунт,
  невалидный и повторный refresh, сбой БД, отсутствие ролей; тело, заголовки,
  статусы и `request_id` до и после изменения совпадают.
- PostgreSQL: успешная ротация, повтор старого refresh фиксирует отзыв сессии,
  неправильный секрет не отзывает, откат при сбоях и конкурентные запросы.
- Конфигурация: валидные временные ключи позволяют запуск; отсутствующие,
  неверные и несовместимые ключи не позволяют запуск. Проверить тестовые профили.
- Регрессии регистрации, logout, recovery, JWKS и claim ролей; сквозной сценарий
  трёх сервисов с изолированной БД. Полный Maven verify и форматирование.

## Риски и решения

| Риск | Решение |
| --- | --- |
| Исключение откатит отзыв сессии | Сохранить транзакционную границу и доказать поведение интеграционным тестом. |
| Обязательный JWT сломает запуск тестов | Настроить временные ключи и проверить все профили и зависящие компоненты. |
| Ошибки или `Cache-Control` изменятся | Сравнить реальные HTTP-ответы с текущим контрактом. |
| Упрощение контроллера создаст лишние уровни | Вводить отдельные классы только при понятной необходимости. |
