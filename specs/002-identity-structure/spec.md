# Единая структура identity-service

> **Статус:** implemented
> **Номер:** 002
> **Связанные документы:** [инженерные стандарты](../../docs/engineering-standards.md), [регистрация](../001-user-registration/spec.md)
> **Заменяет / заменена:** —

## Цель

Привести пакеты `identity-service` к единому понятному принципу: разработчик
находит код по функции и затем по его назначению. Существующее поведение
регистрации, входа и взаимодействия сервисов сохраняется.

## Границы

### Входит

- Согласовать структуру пакетов Identity и правила размещения классов.
- Переместить относящиеся к сервису классы и тесты, обновить пакеты и импорты.
- Закрепить общие правила в инженерных стандартах и проверить сборку.
- Добавить Lombok в проект и использовать в Identity для сокращения
  шаблонного кода, сохранив поведение и требования безопасности.

### Не входит

- Новая функциональность, включая logout; изменения других микросервисов.
- Изменение REST/gRPC-контрактов, правил безопасности, схемы БД или миграций,
  кроме согласованных исправлений ответов `405`, `415` и `406` в Spring MVC.
- Изменение поведения регистрации, входа, refresh, восстановления и сессий.

## Сценарии и правила

- Код группируется по функции; внутри функции применяются понятные пакеты
  `controller`, `service`, `repository`, `entity`, `dto`, `exception`,
  `config`, `grpc`, `worker` по необходимости.
- Общие классы размещаются в `shared` или `security` только если используются
  несколькими функциями; зависимости между пакетами проверяются при переносе.
- Настройки и исключения не смешиваются с сервисами только потому, что они
  участвуют в одном сценарии.
- Тесты находятся в `src/test/java`: тест конкретного класса — в пакете этого
  класса, межслойный сценарий — в пакете функции, общесервисный — в общем
  пакете сервиса. Имена и запуск описаны в инженерных стандартах.
- Lombok применяется там, где уменьшает шаблонный код; правила безопасности,
  совместимость с JPA и корректность сгенерированных методов проверяются.
- Восстановление регистрации не создаёт второй набор слоёв внутри `recovery`:
  его контроллер, сервис и исключения находятся в соответствующих пакетах
  `registration`; защита операторского API — в `registration/security`.
- По решению владельца проекта сущности пользователя, credentials, ролей и их
  репозитории размещаются внутри `registration`: в `entity/user`, `entity/role`
  и `repository`. Вход также использует некоторые из этих классов. Операция
  регистрации и её статус находятся в `registration/entity/operation`.
  Это разбиение не меняет таблицы в базе.
- Клиент продолжает отправлять те же HTTP-запросы; ответы сохраняются с учётом
  согласованных исправлений `405`, `406` и `415`. Внутренние gRPC-вызовы,
  авторизация и работа с БД сохраняют прежний контракт.

## Данные и конфиденциальность

Identity остаётся владельцем своих данных. Перестановка классов не меняет
хранение паролей и токенов и не добавляет секреты или персональные данные в логи.

## Критерии готовности

- [x] Структура соответствует согласованной схеме без пустых пакетов-заготовок.
- [x] HTTP-регистрация и вход, gRPC-взаимодействие и существующие ошибки работают в проверенных сценариях как раньше.
- [x] Spring находит компоненты и ресурсы, необходимые для проверенных сценариев.
- [x] Существующие тесты Identity проходят после переноса; тесты с локальными сертификатами проверены отдельно.
- [x] Инженерные стандарты описывают принятые правила; изменения проверены.
- [x] Lombok подключён и применяется в Identity; версия закреплена в корневом
  Maven POM, сборка и необходимые тесты проходят.

## Зависимости пакетов

JWT остаётся в `security`, восстановление регистрации — в `registration`.
На текущем этапе принимаются взаимные зависимости пакетов, описанные в
[structure-map.md](structure-map.md); это не доказательство циклов Spring bean.
Прямые циклы импортов между Java-классами при проверке не обнаружены.
