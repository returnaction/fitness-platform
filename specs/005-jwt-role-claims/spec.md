# Роли пользователя в access-токене

> **Статус:** implemented
> **Номер:** 005
> **Связанные документы:** [регистрация](../001-user-registration/spec.md), [выход из сессии](../003-session-logout/spec.md), [сессии Identity](../../system-design/services/identity/31-identity-login-sessions.md)
> **Заменяет / заменена:** —

## Цель

Передавать назначенные пользователю роли в подписанном access JWT, чтобы
сервисы могли проверять права по доверенному токену без обязательного запроса
к Identity при каждом защищённом действии.

## Границы

### Входит в эту спецификацию

- Зафиксировать согласованный формат claim ролей и правила его проверки.
- Добавить роли в access при регистрации, входе и refresh и проверить их
  актуальность на момент выпуска токена.
- Проверить в тестовом окружении локальную проверку JWT и ограничение доступа
  по ролям на тестовом защищённом endpoint без добавления production API.
- Документировать контракт, совместимость и тесты.

### Не входит в эту спецификацию

- Экран Flutter, управление ролями, назначение или отзыв ролей через API.
- Новые бизнес-операции, права на конкретные ресурсы и миграция схемы без
  обоснования. Подключение реальных endpoints Accounts и Coins — отдельная задача.
- События Kafka, развёртывание, HTTPS и немедленный отзыв всех access-токенов.

## Пользователи и права

| Роль | Что может делать |
| --- | --- |
| Пользователь | Получает токен со своими назначенными ролями, когда выполнены условия выдачи сессии. |
| Защищённый сервис | После проверки токена применяет правила доступа своей операции; владение проверяет только там, где это требуется конкретной функцией. |
| Клиент | Передаёт токен; самостоятельно изменённым ролям доверять нельзя. |

## Сценарии

### Выпуск access-токена

**Дано:** у активного пользователя есть назначенная роль `USER`.
**Когда:** Identity выдаёт access при регистрации, входе или refresh.
**Тогда:** Identity включает массив `"roles": ["USER"]` в подписанный JWT.
В массив попадают только фактически назначенные роли; вычисляемые права
унаследованных ролей не добавляются в токен. При нескольких назначенных
ролях передаются все они.

Например, пользователю назначены `USER` и `MODERATOR` — токен содержит
`["USER", "MODERATOR"]`. Если назначен только `MODERATOR`, в токене будет
только `["MODERATOR"]`, но проверка прав учитывает наследование `USER`.

### Запрос к защищённой операции

**Дано:** клиент предъявил Bearer access с необходимой ролью.
**Когда:** сервис получает защищённый запрос.
**Тогда:** сервис проверяет подпись, разрешённый алгоритм, issuer, audience,
срок и обязательные поля, затем разрешает или запрещает действие по своим
правилам. JWT из другого контекста и неподписанным данным доверять нельзя.

### Ошибки и граничные случаи

| Условие | Согласованное поведение |
| --- | --- |
| Токен отсутствует, истёк, подменён или не подходит по issuer/audience | `401`, доступ не предоставляется. |
| Токен проверен, но роли недостаточно | `403`, доступ не предоставляется. |
| Старый проверенный токен без `roles` | Для операции, требующей роль, `403`; в отсутствие требования роли claim сам по себе не даёт дополнительных прав. |
| В массиве есть неизвестная роль | Не давать права по неизвестной роли; известные роли того же проверенного токена учитываются. |
| Claim `roles` не массив или в массиве есть нестроковый элемент | `401`; токен считается некорректным. |
| У активного пользователя нет назначенных ролей | Не выдавать новый access; `500 internal_error` без внутренних деталей. |
| Роли в Identity недоступны из-за сбоя БД | Не выдавать токен с придуманной ролью; `503 identity_unavailable`. |

## Бизнес-правила

- Роль `USER` уже назначается при создании пользователя; `PENDING` не получает
  сессию до завершения регистрации. Другие роли нельзя придумывать по запросу клиента.
- Источник назначений — данные Identity; значения JWT только подписанное
  представление ролей на момент выдачи, а не новая база прав.
- Согласована иерархия `SUPER_ADMIN → ADMIN → MODERATOR → USER`: каждая роль
  включает права ролей справа. Наследование применяется при проверке доступа
  сервисом, а не расширением массива назначенных ролей в JWT.
- Согласно решению владельца проекта сервисы могут проверять JWT локально:
  ранее выданный токен может содержать старую роль до истечения срока access —
  не более 15 минут, в том числе после удаления роли или отзыва сессии.
- При refresh заново читаются текущие роли, а не копируются из старого access.
  Отдельно проверить регистрацию и повторную выдачу сессии.
- Изменение назначений и выдача токена одному пользователю должны иметь
  определённый порядок: если удаление роли завершилось раньше выдачи нового
  токена, его claim не содержит удалённую роль. Токен, выданный до удаления,
  может содержать прежнюю роль до истечения срока. При ошибке выдачи refresh
  не должен частично ротироваться.
- Существующий административный API восстановления регистрации сохраняет
  проверку актуального `SUPER_ADMIN` и состояния сессии в базе Identity;
  изменение роли для него действует при следующей проверке, даже если старый
  токен ещё не истёк.
- Доступ к конкретным ресурсам определяется правилами соответствующей функции.
  Например, просмотр чужого профиля не запрещается только потому, что он чужой;
  проверка владения применяется для действий, где это прямо требуется.

## Данные и конфиденциальность

Identity владеет таблицами `roles` и `user_roles`. Не добавлять email, пароль,
секреты, refresh-токен или лишние персональные данные в JWT и журналы. JWT
подписан, но не считается зашифрованным: его содержимое доступно предъявителю.

## Открытые вопросы

Продуктовые правила этой задачи согласованы. Границы конкретных полномочий
ролей определяются в задачах соответствующих функций; сама иерархия не
определяет доступ к каждому ресурсу. При будущем изменении ролей необходимо соблюдать проверенный протокол
блокировки пользователя, описанный в плане.
