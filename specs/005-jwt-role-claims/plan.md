# План реализации: роли в access JWT

> **Спецификация:** [spec.md](spec.md)
> **Статус:** approved
> **Связанные документы system-design:** [сессии Identity](../../system-design/services/identity/31-identity-login-sessions.md), [регистрация](../../system-design/services/identity/30-identity-registration.md)

## Краткое решение

В текущем Java-коде `AccessTokenSigner` выдаёт `iss`, `aud`, `sub`, `sid`,
`iat`, `exp`, `jti`, но не роли. Таблицы `roles` и `user_roles` принадлежат
Identity; в схеме есть `USER`, `MODERATOR`, `ADMIN`, `SUPER_ADMIN`. Начальная
роль `USER` назначается при регистрации. Назначение остальных ролей и
разрешения сервисов не считаются реализованными только из наличия справочника.

Роли из Identity подписываются в claim `roles` при всех
трёх путях выдачи access. Владелец проекта согласовал проверку через тестовый
защищённый endpoint без новых production API в Accounts и Coins. В токене —
только назначенные роли; на стороне потребителя применяется иерархия
`SUPER_ADMIN → ADMIN → MODERATOR → USER`. Старый токен без `roles` не даёт
доступа к endpoint, где требуется роль.

## Затрагиваемые границы

| Область | Изменение | Владелец данных / контракта |
| --- | --- | --- |
| Identity | Чтение ролей и выдача JWT при регистрации, входе и refresh | Identity |
| Тестовый потребитель | Проверка JWT и сопоставление ролей с разрешением без production endpoint | Тестовое окружение |
| Документация | Формат claim, совместимость, примеры и ошибки | Identity / соответствующий сервис |

## Данные и миграции

- Использовать текущие `roles` и `user_roles`; проверить схему и индекс доступа.
  Миграция не предполагается без доказанной необходимости.
- Доступ к БД — Spring Data JPA / Hibernate по инженерным стандартам;
  не добавлять `JdbcClient` в код приложения.
- Согласовать чтение пользователя, ролей и создание токена с границами
  существующих транзакций и блокировок. Не удерживать транзакцию при сети.
- Обеспечить согласованный порядок изменения роли и выдачи токена: если
  изменение завершилось раньше выдачи, новый claim отражает это изменение.
  Проверить порядок блокировок и способ сериализации на временном PostgreSQL.
  Будущие способы изменения ролей также должны соблюдать выбранный протокол;
  API управления ролями в текущую задачу не входит.
- Миграции к пользовательской базе не применять без отдельного разрешения.

## Контракты и взаимодействия

| Направление | Тип | Изменение | Версионирование / совместимость |
| --- | --- | --- | --- |
| Identity → клиент | HTTP / JWT | Массив назначенных `roles` в access при register/login/refresh | Старые токены без ролей не получают роль по умолчанию |
| Клиент → потребитель | HTTP Bearer | JWT проверяется локально, затем проверяется право | Сервис проверяет свой issuer/audience и доступ к ресурсу |

Сохранить общий JSON ответа токенов и действующую ротацию refresh; изменение
JWT — изменение контракта даже при неизменной форме JSON. Обновить
[OpenAPI](../../contracts/openapi/identity-auth-v1.yaml) и документацию JWT
после согласования; роли не помещаются в refresh или логи.

## Надёжность и безопасность

- Проверять подпись JWT, алгоритм, `kid`, issuer, audience и сроки перед
  использованием ролей. Некорректный токен и недостаточные права различать.
- Не назначать роль из входного JSON и не превращать отсутствующую роль в `USER`.
- Неверный тип `roles` или нестроковый элемент — `401`; неизвестная строковая
  роль не даёт прав и не отменяет известные. Старый JWT без `roles` получает
  `403` только там, где роль обязательна.
- Для активного пользователя без назначенных ролей возвращать безопасный
  `500 internal_error`, при недоступности БД — `503 identity_unavailable`;
  при неуспешном refresh не допускать частичной ротации.
- Не менять существующую проверку актуального `SUPER_ADMIN` в базе для
  административного восстановления регистрации.
- Избегать выдачи частично сформированного токена при сбоях и откатывать
  необходимые изменения сессии / refresh; не допускать утечки секретов в логи.
- Зафиксировать согласованное ограничение устаревших прав в ранее выданном JWT
  до 15 минут и совместимость со старыми токенами; не обещать
  немедленный отзыв роли.

## Проверка

- Unit: содержимое `roles`, одна и несколько ролей, пустые и неизвестные,
  отсутствие client-supplied данных, корректность подписи.
- HTTP/PostgreSQL: register, login, refresh, PENDING, изменение назначений
  перед refresh, сбой чтения ролей и отсутствие частичной выдачи / ротации.
- Проверка потребителя: 401 для недействительного JWT, 403 без роли, успешный
  доступ с ролью и через иерархию, неизвестные роли, модифицированный claim,
  неверные issuer/audience; production endpoint не добавлять без согласования.
- Конкурентные тесты с PostgreSQL: изменение роли и выпуск/refresh в пределах
  согласованной модели, отсутствие гонок с существующими блокировками.
- Выполнить необходимые Maven-тесты и сквозную локальную проверку; проверить
  документацию и отсутствие реальных данных в примерах / логах.

## Риски и решения

| Риск или открытый вопрос | Решение / кто принимает решение |
| --- | --- |
| Устаревшие привилегии в живом JWT | Владелец согласовал задержку до 15 минут; refresh выдаёт актуальные роли. |
| Старые токены без claim | Не дают доступа к endpoint, требующему роль; без назначения прав по умолчанию. |
| Ошибка в claim позволяет повышение прав | Строгая проверка подписи и формата, негативные тесты. |
| Роли в токене путают с владением ресурсом | Доступ к объекту определяется отдельно по правилам соответствующей функции. |
