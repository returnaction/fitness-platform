# Передача готового видео в модерацию: проект контракта

Учебная модель будущих Java / Spring-сервисов. Описывает предлагаемое
разделение обязанностей, а не существующие API или проверенную реализацию.
Challenge отвечает за допуск задания; Video Proof — за готовый файл и проверку
доступа к нему; Moderation — за карточку и решение. У каждого своя база.

## Почему нужен допуск

При обычном участии готовое видео должно попасть в модерацию автоматически.
Но если участник оспаривает решение предыдущего дня, он может выполнять
следующие задания. Их видео сохраняются и подготавливаются, однако ждут исхода
апелляции. При удовлетворении допускаются к проверке; при отказе сохраняются,
но не проверяются. Правило: [апелляция](../services/moderation/25-moderation-decisions.md#апелляция-согласованная-модель).

Поэтому наличие готового файла **не равно** разрешению создать актуальную
карточку модерации. Разовая проверка по сети также не делает две базы общей
транзакцией. Ниже предложен проект с версией допуска и проверкой при решении.

## Последовательность

1. Video Proof надёжно сохраняет playback-версию и публикует через свой outbox
   `video.ready.v1` для Challenge. В событии идентификаторы и факты о файле;
   самого файла и временной ссылки нет.
2. Challenge через inbox проверяет связь записи с разрешённой загрузкой,
   задание и текущие условия участия. Временно недостающий факт не считается
   окончательным отказом. Если есть апелляция предыдущего дня — сохраняет
   ожидание, а не допускает запись к модерации.
3. Когда допуск разрешён, Challenge сохраняет для конкретной отправки допуск
   с возрастающей версией и доверенный неизменяемый снимок задания, а также
   outbox-событие `proof.review_admitted.v1`. Снимок берётся из Challenge,
   а не из данных телефона. Точный состав упражнения приведён ниже.
4. Moderation атомарно сохраняет inbox и карточку по событию. Повтор того же
   события или повтор того же допуска не создаёт ещё одну карточку. Если
   Moderation временно недоступен, событие остаётся для доставки; загружать
   видео заново не нужно.
5. Модератор открывает карточку. После проверки роли и назначения Video Proof
   выдаёт ссылку максимум на пять минут на **точную версию** playback. Ссылка и файл не
   публикуются в Kafka, а наличие `asset_id` само по себе права не даёт.
6. После выбора решения Moderation сохраняет его и событие через outbox.
   Challenge через inbox проверяет актуальность допуска и применяет решение
   к заданию. Сами видео, задание, допуск и решение — разные сущности.

## Событие `video.ready.v1` — предлагаемый контракт

Отправитель Video Proof, получатель Challenge. Ключ Kafka — `submission_id`;
топик и формат сериализации приведены в [каталоге](../architecture/messaging/19-kafka-topology.md).
Оболочка соответствует
[общему проекту событий](../architecture/messaging/12-kafka-event-contract-draft.md).

```json
{
  "event_id": "<uuid>",
  "event_type": "video.ready",
  "schema_version": 1,
  "occurred_at": "2026-11-05T12:00:00Z",
  "producer": "video-proof",
  "correlation_id": "<uuid>",
  "data": {
    "submission_id": "<uuid>",
    "authorization_id": "<uuid>",
    "task_id": "<uuid>",
    "asset_id": "<uuid>",
    "asset_generation": 1
  }
}
```

Событие означает техническую готовность конкретного playback; оно не означает,
что упражнение, личность или действие перед камерой проверены. Challenge
проверяет, что `submission_id`, `authorization_id` и `task_id` относятся к
его разрешению. Выбор второй генерации playback не должен молча заменить файл
уже проверенной карточки; политика корректирующей генерации ещё открыта.

## Событие `proof.review_admitted.v1` — предлагаемый контракт

Отправитель Challenge, получатель Moderation. Ключ Kafka — `submission_id`.
Сервисная авторизация и формат определены в [каталоге](../architecture/messaging/19-kafka-topology.md);
их ещё нужно реализовать и испытать.

```json
{
  "event_id": "<uuid>",
  "event_type": "proof.review_admitted",
  "schema_version": 1,
  "occurred_at": "2026-11-05T12:00:03Z",
  "producer": "challenge",
  "correlation_id": "<uuid>",
  "data": {
    "admission_id": "<uuid>",
    "admission_version": 1,
    "submission_id": "<uuid>",
    "asset_id": "<uuid>",
    "asset_generation": 1,
    "task_id": "<uuid>",
    "task_snapshot": {
      "schema_version": 1,
      "exercise_id": 1,
      "variation_id": 1,
      "exercise_name": "Push-up",
      "variation_name": "Narrow grip",
      "description": "Выполнить отжимания узким хватом",
      "instructions": "Поставьте руки ближе ширины плеч и выполните отжимания.",
      "target": {"metric": "REPETITIONS", "value": 10, "unit": "REP"}
    }
  }
}
```

Это иллюстрация для заданий с повторениями. Предлагаемый единый формат:
[контракт метрик задания](../services/exercise-catalog/49-task-metric-contract.md).
В v1 поддерживаются повторения и секунды; обязательные поля и единицы — в
контракте снимка. Расширение метрик и локализации требует отдельной версии.
Снимок не содержит имени или nickname игрока, ставки и названия challenge.
Секреты, подписанные ссылки и сам файл в событие не включаются. Технические
системные промпты не являются заданием модератору; их сохранение для будущей
автоматической проверки проектируется отдельно.

## Дубликаты, порядок и изменение допуска

- Kafka доставляет сообщения как минимум один раз; outbox отправителя и inbox
  получателя фиксируются каждый в своей локальной транзакции. Повтор того же
  `event_id` и тех же данных — no-op; тот же ID с другим payload — карантин.
- Уникальность карточки обеспечивается бизнес-ключом допуска; повтор события
  с новым `event_id` не создаёт вторую карточку. Точная DDL-ограничения ещё
  определяются в канонической модели Moderation.
- События одного submission в одном топике ключуются одинаково, но порядок
  между разными топиками не гарантирован. Moderation хранит версию допуска и
  обрабатывает ранний отзыв или отсутствующую предыдущую версию без молчаливого
  принятия устаревшего состояния. Механизм хранения ожидания ещё нужен.
- Если Challenge отменяет допуск, он сохраняет новую версию и публикует отзыв.
  Moderation закрывает карточку при получении. Уже открытое видео или ранее
  выданная временная ссылка могут оставаться доступными после отзыва: URL
  действует до пяти минут, а уже начатая передача или кеш могут сохраняться
  дольше. После истечения новая ссылка требует повторной проверки прав.
- При получении решения Challenge повторно сверяет сохранённую версию допуска
  и состояние задания. Устаревшее решение остаётся в аудите Moderation, но не
  применяется к результату. Для запрета просмотра сразу после отзыва нужна
  отдельная синхронная проверка и способ отзыва доступа; это ещё не доказано.

Названия события отзыва, DTO и атомарный переход допуска с решением должны
быть утверждены до реализации. Нельзя заявить, что задержка Kafka исключает
все гонки: гарантия строится на версии, проверках и восстановлении.

## Проверки перед реализацией

Реальные PostgreSQL двух сервисов и Kafka: Moderation недоступна при отправке,
повтор event ID и новый event ID с тем же допуском, потеря offset после commit,
события не по порядку, апелляция и ожидающее видео, отзыв допуска во время
открытия карточки и во время решения, повторная генерация playback, недоступный
Video Proof при выдаче ссылки, запрет доступа чужого модератора. Также сверить
совместимость схем, права на события и отсутствие PII / URL в логах.

Это перечень будущих проверок; ни реализация, ни интеграционные тесты на этом
этапе не выполнялись.
