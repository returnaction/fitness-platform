# Identity и Accounts: внутренние контракты v1

Внутренние контракты Java / Spring-сервисов. Проверка сессии реализована в
Identity; остальные описания ниже могут оставаться проектными. Таблицы Identity
определены в [регистрации](../services/identity/30-identity-registration.md) и [сессиях](../services/identity/31-identity-login-sessions.md),
таблица Accounts — в [профиле](../services/accounts/32-accounts-profile.md); здесь нет дублирования.
Методы предназначены сервисам, а не мобильному приложению.

## Общие требования

gRPC использует mTLS с клиентскими сертификатами от собственной private CA
проекта. URI SAN сертификата определяет service identity, а получатель выдаёт
ей только минимальные права; для Identity это
`spiffe://fitness.local/identity-service`. Пользовательские access token и
service JWT в первой версии не применяются. Сервисная identity не заменяет
пользовательскую сессию.
UUID задаются строками lowercase, даты RFC 3339 UTC; proto-типы и кодогенерация
будут определены при реализации. `request_id UUID` связывает диагностику, но
не является секретом. Права Identity проверяются на каждом вызове, нельзя
подменить user_id заголовком клиента. Deadline и ограниченные повторы:
стартовое предложение 1 секунда на попытку, не более двух read-only попыток с
общим бюджетом 2,5 секунды; значения проверяются под нагрузкой.

`INVALID_ARGUMENT` — неверный формат; `UNAUTHENTICATED` — сервисная identity
не проверена; `PERMISSION_DENIED` — сервис не имеет разрешения;
`UNAVAILABLE` / `DEADLINE_EXCEEDED` — нет достоверного ответа. После такого
сбоя нельзя считать сессию действительной или возвращать чужой email по кешу.
Логи не содержат email, токенов и содержимого профиля.

## Проверка сессии: сервис → Identity

Контракт метода определён в [identity-session-v1.proto](../../contracts/proto/identity-session-v1.proto).
Сервер Identity включается явно и принимает только одну service identity,
заданную в `IDENTITY_SESSION_GRPC_ALLOWED_CALLER`. Значение задаёт разрешённого
вызывающего для `identity.session.verify`; пустая или некорректная URI не
позволяет включить сервер. На текущем этапе конкретная identity Gateway и его
клиент ещё не настроены. Сертификат сервера и CA передаются отдельно через
переменные `IDENTITY_SESSION_GRPC_*`, а порт не публикуется в интернет.

`CheckSession` требует service permission `identity.session.verify`:

```text
Запрос: {request_id, user_id, session_id}
Ответ:  {status: ACTIVE | INVALID, checked_at}
```

Вызывающий сервис сначала проверяет подпись, issuer, audience и срок access
token согласно [контракту сессий](../services/identity/31-identity-login-sessions.md), затем
передаёт полученные из проверенного token ID. Identity читает основную БД,
сверяет принадлежность, статус пользователя, отзыв и срок сессии. `INVALID`
означает недействительную сессию без раскрытия, существует ли пользователь;
внешний API возвращает `401 invalid_access_token`. При недоступности Identity
внешний API возвращает временный `503`, а не разрешает запрос и не объявляет
пользователя неверным. Кеш решения о сессии в v1 не используется. Запрос,
прошедший проверку до logout, может завершиться после него.

Это read-only вызов: повтор с теми же параметрами не меняет состояние, но
ответ может измениться после отзыва сессии. Время `checked_at` берётся из
PostgreSQL в том же запросе, что и проверка. Batch и подписки не входят в v1.
Ограничение на вступление и срочная полная блокировка имеют разные смыслы;
`CheckSession` сам по себе не разрешает новую бизнес-операцию Challenge.

## Публичный email: Accounts → Identity

`GetPublicProfileEmail` разрешён только service identity Accounts с правом
`identity.profile.email.read`:

```text
Запрос: {request_id, user_id}
Ответ:  {user_id, email, email_version}
```

Identity читает основной источник email и возвращает актуальное значение;
`email_version` — версия записи Identity; поле и атомарное увеличение при
смене email определены в [модели Identity](../services/identity/30-identity-registration.md#identity-users).
`NOT_FOUND USER_NOT_FOUND` — отсутствие аккаунта;
это нарушение связности для существующего профиля, Accounts снаружи возвращает
общую `503 profile_unavailable` и создаёт технический сигнал, не выдаёт чужой
или старый email. `UNAVAILABLE` / `DEADLINE_EXCEEDED` дают тот же временный
ответ. Email не кешируется как источник публичного профиля в v1.

Перед вызовом Accounts читает профиль с primary и обращается за email только
при `PUBLIC`. Затем снова читает primary: если версия изменилась, повторяет
процесс не более двух раз; при `PRIVATE` возвращает только разрешённый
никнейм/публичный ID, при повторной гонке — `503 profile_unavailable`.
Эта проверка не образует общей транзакции с отправкой HTTP-ответа: запрос,
успевший пройти финальную проверку до смены на PRIVATE, может закончиться
после неё. Строгий отзыв уже сформированного ответа невозможен одним gRPC;
данное ограничение явно относится к будущей системе.

## Получить публичные данные участника: сервис → Accounts

`ResolvePublicProfileIds` доступен Challenge с правом `accounts.profile.resolve`:

```text
Запрос: {request_id, user_ids: [uuid, ...]}
Ответ:  {items: [{user_id, status: FOUND | NOT_FOUND, public_profile_id, nickname}]}
```

В одном запросе 1–100 различных ID, порядок ответа соответствует запросу;
повторяющийся ID — `INVALID_ARGUMENT DUPLICATE_USER_ID`. Accounts читает
основную БД, каждый найденный ID соответствует собственной записи профиля.
Для `FOUND` `public_profile_id` и актуальный `nickname` обязательны; для
`NOT_FOUND` оба поля отсутствуют. Email, имя, фамилия, bio и другие поля этим
методом не возвращаются. Ник и публичный ID берутся из одной версии профиля.
Сервис получает внутренний user_id только потому, что уже имеет разрешённый
контекст участия; мобильному клиенту возвращается только `public_profile_id`.
Отсутствующий профиль активного пользователя — сигнал на восстановление,
Challenge не выдумывает ID; `UNAVAILABLE` — временная ошибка. Публичный ID не
предоставляет права видеть приватные поля. Подмена ID сервисным клиентом не
отменяет проверку его разрешения и предметного контекста.

Чтобы не превращать метод в массовый справочник пользователей, вызывающий
Challenge ограничивает запрос своими участниками, а сервисная выдача ограничена
вышеуказанной identity и лимитами; cross-service проверка принадлежности к
challenge не является автоматической гарантией `ResolvePublicProfileIds` и
должна быть проверена на стороне Challenge до формирования ответа клиенту.

Challenge вызывает метод только после проверки права на страницу участников и
передаёт ID этой страницы. При `NOT_FOUND` или недоступности Accounts Challenge
возвращает `503 profile_unavailable`, не выдаёт неполный список как полный и
пишет безопасный диагностический код без PII. Внешний DTO не содержит внутренний
`user_id`. Порядок в ответе соответствует запросу; nickname может измениться
между страницами. Вызов read-only и не изменяет участие или ставки.

## Обязательные проверки

Отзыв сессии сразу после выдачи JWT, недоступность Identity, неправильный
audience, подмена user_id, отзыв прав сервиса, приватность между двумя чтениями,
профиль без Identity, отсутствие записи Accounts, UUID-дубликаты и лимит batch,
недоступность primary, отсутствие email/токенов в логах. Для проверки гонок
нужны отдельные реальные PostgreSQL и запущенные сервисы. Тесты не выполнялись.
