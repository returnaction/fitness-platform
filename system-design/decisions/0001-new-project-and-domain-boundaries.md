# ADR 0001: Отдельный Java-проект и границы предметных областей

- Статус: принято для учебного проектирования; технические детали открыты.
- Дата: 2026-11-05.
- Область: новая проектируемая система. Этот ADR не меняет существующее
  приложение и его ADR.

## Контекст

Существующий проект — приложение с backend на Python / FastAPI. Для его MVP
принят модульный монолит (исторический ADR
`docs/decisions/0001-use-modular-monolith.md` не перенесён в этот репозиторий).
В `docs/system-design` мы учимся проектировать систему с выделенными бизнес-областями
и возможностью их отдельного развёртывания. Пользователь выбрал Java / Spring
для новой системы и планирует создать для неё отдельный проект.

## Решение

1. Пока ведём проектирование в `docs/system-design` существующего репозитория.
2. Позднее создаём отдельный проект для новой реализации и переносим в него
   необходимые документы, схемы и решения из `docs/system-design`.
3. Существующий Python-код и его документацию используем как справочный материал:
   изучаем реализованное поведение, но не считаем его обязательным устройством
   новой системы. Перенос самого кода, данных или пользователей этим решением
   не предусмотрен; если понадобится, его спроектируем отдельно.
4. В новой модели выделяем ответственности Challenge, Coins, Video Proof,
   Moderation, Identity / Accounts, Exercise Catalog и Notifications. Каждая
   область отвечает за свои правила и данные; конкретное взаимодействие — через
   явные контракты, а не произвольные изменения чужих таблиц.
5. Java / Spring — выбранное направление для нового backend. Конкретные версии,
   структура проекта и порядок реализации ещё определяются.

Карта контекстов — [DDD](../domain/27-ddd-context-map.drawio); общая модель —
[итог System Design](../overview/28-system-design-summary.md).

## Альтернативы

- Продолжить развивать только существующий Python-монолит: проще сохранять
  нынешнее поведение, но не соответствует выбранной учебной цели Java / Spring.
- Переписать существующее приложение на месте: смешало бы текущий работающий
  продукт и учебную разработку; выбрана отдельная кодовая база.
- Сразу считать каждый контекст отдельным готовым микросервисом: такое
  решение без проработки контрактов и эксплуатации преждевременно.

## Последствия и границы решения

- Правило модульного монолита MVP остаётся действующим для существующего
  проекта. Учебная система и будущий отдельный проект не переопределяют его.
- Мы проектируем отдельные сервисные границы и их взаимодействия. Этот ADR
  не устанавливает обязательный первый вариант развёртывания нового проекта:
  выбор первого приложения, числа сервисов и этапов выделения ещё предстоит
  принять отдельно до реализации.
- Копируемая модель предметной области содержит исторические сведения о старом
  коде и должна быть уточнена под согласованные правила новой системы.
- Где будет находиться новый репозиторий, какие документы войдут в начальную
  версию, как синхронизировать изменения и нужно ли переносить данные — открытые
  вопросы на момент фактического создания проекта.
- Рабочий учебный стенд на одной машине не обеспечивает независимости отказов
  предполагаемых узлов. Kafka, RabbitMQ и реплики остаются проектной моделью
  до отдельной настройки и проверки.
