# Вход и доступ в будущей системе

Общая проектная модель. Локальный auth Gateway реализован по
[спецификации 009](../../../specs/009-gateway-access/spec.md);
[контракт v1](../../../contracts/gateway-v1.md) ограничен пятью auth-операциями
Identity. Остальные бизнес-маршруты ниже остаются проектными. Мобильное
приложение пока не переключено; сайта и Flutter Web не будет.

## Основной путь

1. Identity проверяет данные входа и выдаёт ограниченный по времени токен.
2. Телефон отправляет запрос с токеном в единую точку входа — API Gateway.
3. В auth v1 Gateway проверяет JWT и сессию через CheckSession для logout-all,
   затем передаёт исходный Bearer Identity. Register/login/refresh/logout
   проверяются Identity по собственным контрактам. Сервисы сохраняют проверки прав.
4. Сервис получает подтверждённый идентификатор аккаунта и проверяет право на
   конкретное действие в своей области. Пароль пользователя он не получает.

## Согласованные правила входа и безопасности

- Приложение использует ограниченный токен доступа и refresh-токен для его
  обновления. Недействительный refresh требует нового входа; временный 503
  не является отзывом сессии и не должен удалять токены клиента.
- После смены пароля другие пользовательские сеансы завершаются; механизм
  отзыва и поведение уже выданных токенов нужно определить при реализации.
- Роли и право на конкретный объект проверяются сервером. Обычный участник
  не получает доступ к модерации, знание адреса или ID видео не заменяет права.
  Закрытый challenge допускает вступление по соответствующей ссылке или паролю.
- Сервисные вызовы имеют отдельную проверку идентичности и минимальные права.
- Пароли хешируются надёжным алгоритмом; пароли и токены не записываются в логи.
  Многократные неудачные попытки входа временно ограничиваются.
- Действия модерации и администрации, в том числе ограничения аккаунтов,
  аудируются; личность модератора недоступна обычным участникам.

## Устройства и переключение аккаунтов

Пользователь может иметь несколько сеансов, видеть их в настройках и завершать
по отдельности; выход с одного устройства не завершает остальные. Смена пароля
завершает другие сеансы. Данные и баланс принадлежат аккаунту, а не устройству;
после смены аккаунта приложение показывает данные вошедшего пользователя.
Новая запись разрешена только для задания текущего пользователя. До смены
аккаунта активную запись нужно завершить или отменить. Уже начатая загрузка
никогда не переходит другому аккаунту; её право и технический способ продолжения
после выхода ещё нужно определить. Обычное ограничение запрещает новые
вступления, но позволяет заканчивать существующие challenge.

## Ограничение новых вступлений

Действительный токен сам по себе не подтверждает актуальное право вступить в
новый challenge. При вступлении учитываются актуальные ограничения Identity и
согласованный порядок начатых операций: новые операции запрещаются сразу при
команде ограничения, ранее разрешённые завершаются. Восстановление операций
при сбоях ещё проектируется. Обычное ограничение новых вступлений отличается от
полной блокировки доступа.

## Доступ сервисов друг к другу

- Для будущих внутренних HTTP- и gRPC-вызовов выбран вариант служебных короткоживущих
  токенов. Доверенная служба авторизации выдаёт токен после подтверждения
  личности сервиса; сервис не назначает себе права сам.
- Токен указывает вызывающий сервис, получателя, разрешённые действия и срок.
  Получатель проверяет подпись, срок, назначение и права; соединение защищается.
- Например, Challenge вызывает Coins с разрешением зарезервировать ставку,
  ID аккаунта и операции. Coins самостоятельно проверяет баланс. Пароль
  пользователя не передаётся; пользовательский и служебный доступ различаются.
- Для Kafka и RabbitMQ нужны собственная аутентификация и права сервисов;
  тот же HTTP-токен не предполагается автоматически использовать для брокеров.

### Сервисные токены: что уже описано и что открыто

Это проект первой учебной версии, не развёрнутая инфраструктура. Для вызовов
**Identity → Accounts / Coins**, необходимых регистрации, в
[регистрации Identity](../../services/identity/30-identity-registration.md#сервисные-credentials-и-разблокировка-обработки)
принят отдельный вариант:

- Вызов использует mTLS с клиентским сертификатом от private CA проекта. URI
  SAN `spiffe://fitness.local/identity-service` определяет service identity
  Identity; Accounts и Coins разрешают ей только
  `identity.registration.provision`.
- Service JWT в этом сценарии v1 не применяется. Private CA будет работать
  через step-ca в платформенной инфраструктуре; private key и сертификаты не
  хранятся в Git, Docker image или логах.
- При выпуске и ротации сертификатов нужно обеспечить отдельные ключи сервиса,
  ограниченный срок действия, доверие старому и новому CA material на период
  смены и аварийную замену при компрометации. Реальная настройка и испытания
  относятся к платформенной ветке.

Выбор mTLS выше относится только к provisioning регистрации. Для других
внутренних HTTP/gRPC-сценариев service JWT остаётся кандидатом, пока для них
не принят отдельный контракт. Пользовательский access token не является
service credential. Доступ брокеров Kafka / RabbitMQ также имеет отдельную
аутентификацию и ACL.

## Права на Kafka и RabbitMQ

У каждого сервиса или worker — собственная служебная идентификация и только
необходимые права на публикацию и чтение. Предварительные примеры:

- Video Proof публикует свои события в Kafka и передаёт задачи в RabbitMQ;
  worker получает разрешённые ему задачи обработки.
- Moderation получает карточки для проверки и публикует события о решениях.
- Challenge читает нужные ему события и публикует события своей области.
- Coins получает результат challenge и публикует результат обработки монет.

Сервис уведомлений не получает полномочий выдавать себя за Coins и отправлять
от его имени команды или события. Точные учётные данные, права, топики и
очереди определяются при детальном проектировании и зависят от конфигурации
брокеров; этот документ не утверждает, что защита уже реализована.

## Публичный профиль в Challenge

Аккаунты и вход относятся к Identity; публичный профиль и никнейм в текущем
проекте находятся в области Accounts. Точная будущая граница между Identity и
Accounts ещё проектируется. В любом случае Challenge хранит ссылку `user_id`,
не управляет паролем или исходными данными профиля и не читает таблицы другого
сервиса напрямую.

Для списка участников возможна локальная копия разрешённых публичных сведений
в Challenge, обновляемая по событиям профиля через Kafka. Она служит только
отображению; профиль остаётся источником истины. Изменения могут приходить с
задержкой или повторяться: нужны версии профиля, Inbox и защита от записи более
старой версии поверх новой. Путь начального наполнения, восстановление после
потери копии, договорённости о топиках и случаях отсутствующего профиля ещё
предстоит спроектировать. Никнейм или устаревшая копия профиля не используются
для проверки актуального права на вступление или идентификации пользователя.

Модератору не передаются ни никнейм, ни данные профиля для обычной проверки;
необходимые служебные идентификаторы не являются данными для отображения.

## Как Coins доверяет запросу Challenge

1. Identity выдаёт пользователю токен. Gateway принимает пользовательский
   запрос, проверяет его по согласованной политике и передаёт в Challenge.
2. Challenge проверяет право пользователя на конкретное действие и определяет
   challenge и ставку из своих серверных данных, не доверяя сумме от телефона.
3. Challenge вызывает Coins по защищённому соединению со служебным токеном,
   предназначенным Coins и разрешающим нужную операцию. В команде передаются
   ID операции, аккаунта, challenge и серверная сумма.
4. Coins проверяет подлинность и права сервиса, контракт запроса и свой баланс,
   затем выполняет разрешённую идемпотентную операцию. Сам по себе переданный
   ID пользователя не подтверждает ни личность пользователя, ни полномочия
   вызывающего сервиса.

Сервис не должен доверять произвольному заголовку `user_id`, присланному из
интернета. Если Gateway передаёт подтверждённый контекст заголовками, должны
быть исключены подмена и прямой обход Gateway; способ доверия ещё не выбран.
Для действий, где требуется проверять права самого пользователя, нужно
отдельно определить безопасную передачу пользовательского контекста. Служебный
токен Challenge подтверждает сервис, но сам по себе не подтверждает право Ани
на challenge. Потерянный ответ повторяется с тем же ID операции; служебные
секреты и токены не попадают в клиентское приложение, логи или события.

## Открыто

- Для будущих бизнес-маршрутов: как сервисы доверяют пользовательскому контексту
  и исключают обход Gateway. Для auth v1 определены JWT + CheckSession,
  повторная проверка в Identity и локальная loopback-изоляция; процессы на
  компьютере разработчика считаются доверенными, production-изоляция отложена.
- Как защищается связь между сервисами и проверяются их собственные полномочия.
- Какая именно служба выдаёт служебные токены, как сервис подтверждает свою
  личность и как выдаются, хранятся и меняются служебные ключи и разрешения.
- Как быстро и надёжно учитываются ограничения и отзыв доступа; какие сведения
  нужны каждому сервису и как выдаются права на просмотр S3.
- Публичное размещение и масштабирование Gateway. Локальный auth v1 — один
  Spring Cloud Gateway Server MVC; ошибки и обновление токена определены
  контрактом v1, распределённые лимиты и production HTTPS не реализуются здесь.
