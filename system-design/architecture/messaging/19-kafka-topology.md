# Учебная топология Kafka

Черновик будущей системы; не описание настроенного кластера. Подробный состав
событий и правила обработки: [контракт](12-kafka-event-contract-draft.md).

## Публикации и получатели

| Событие | Издатель | Получатель | Ключ партиции (проектный) |
| --- | --- | --- | --- |
| `video.ready` | Video Proof | Challenge | `submission_id` |
| `proof.review_admitted` | Challenge | Moderation | `submission_id` |
| `moderation.review_decided` | Moderation | Challenge | `submission_id` |
| `challenge.finished` | Challenge | Coins | `challenge_id` |
| `coins.settlement_completed` | Coins | Challenge | `challenge_id` |

### Каталог основной цепочки v1

Для первой версии каждое событие из таблицы публикуется в отдельный топик
`fitness.<event_type>.v1` с точным именем из таблицы: например,
`fitness.video.ready.v1` и `fitness.coins.settlement_completed.v1`. Kafka key —
UTF-8 канонический lowercase UUID из последнего столбца; value — UTF-8 JSON.
Обязательная оболочка: `event_id` UUID, `event_type`, целый `schema_version=1`,
`occurred_at` RFC 3339 UTC, `producer`, `correlation_id` UUID и объект `data`.
В пределах v1 неизвестные необязательные поля игнорируются, обязательные поля
и их смысл не меняются; несовместимое изменение требует новой версии и топика.
Договорённость распространяется только на пять строк таблицы: другие события
и реестр схем определяются отдельно. Нельзя считать имена уже развёрнутыми.

| Тип | Единственный владелец схемы | Получение и повторы |
| --- | --- | --- |
| `video.ready` | [Video Proof → Challenge](../../interactions/44-video-moderation-handoff.md#событие-videoreadyv1--предлагаемый-контракт) | Challenge проверяет submission и версию файла; тот же факт не создаёт новый допуск. |
| `proof.review_admitted` | [Challenge → Moderation](../../interactions/44-video-moderation-handoff.md#событие-proofreview_admittedv1--предлагаемый-контракт) | Moderation проверяет версию допуска и tombstone; повтор не создаёт вторую карточку. |
| `moderation.review_decided` | [Moderation → Challenge](../../services/moderation/47-moderation-api.md#события-и-отказ) | Challenge проверяет решение и актуальность допуска; зависимость может ожидать. |
| `challenge.finished` | [Challenge → Coins](../../services/coins/34-coins-stake-and-settlement-contract.md#событие-окончательного-результата-v1-проект) | Coins фиксирует inbox и задачу, получает победителей по gRPC; событие само ничего не начисляет. |
| `coins.settlement_completed` | [Coins → Challenge](../../services/coins/35-coins-large-settlement.md#событие-завершения-расчёта) | Challenge фиксирует факт завершения расчёта; не повторяет проводки Coins. |

При повторе одинакового `event_id` и payload получатель не применяет факт
повторно; тот же ID с другим payload сохраняется для технического разбора.
Разные ID одного бизнес-факта также не должны приводить к дублю: проверяются
его стабильные бизнес-ключи и версии. Изменение отправителя и outbox — один
локальный commit; inbox и действие получателя — другой. Offset подтверждается
после надёжной фиксации применения либо долговечного ожидания/карантина;
ожидание не считается применением. Порядок между топиками не гарантирован.

Сервисы публикуют факты через свой Outbox; каждый независимый сервис-получатель
имеет свою consumer group и Inbox. Несколько экземпляров одного сервиса могут
работать в одной группе. Публикации и подписки Notifications, события апелляции
и результат обработки Coins ещё предстоит определить; не считать их готовыми.

Изменение публичного профиля также может потребоваться Challenge для
обновления отображаемого никнейма. Это кандидат на отдельное событие, не часть
четырёх утверждённых контрактов; см. [доступ и профиль](../access/15-auth-gateway-draft.md).

## Ключ и порядок

Каждое событие имеет неизменный при повторе `event_id` для Inbox. Ключ партиции
выбирается отдельно по сущности, а не по случайному event ID. Порядок Kafka
существует только внутри одной партиции конкретного топика и соответствует
порядку записи, не гарантируя правильный бизнес-порядок при гонках издателей,
повторах Outbox или передаче между топиками. Получатель проверяет состояние и
версию сущности; несогласованность удерживается для обработки или разбора.

Один общий `submission_id` не обеспечивает порядка между `video.ready`,
`proof.review_admitted` и `moderation.review_decided`, если они в разных топиках. Финальную
границу топиков, правила версии сущностей и изменение числа партиций ещё нужно
спроектировать. Количество партиций выбирается на основании нагрузки и нужной
параллельности, а не из текущей оценки DAU.

## Надёжность и доступ

- Для важных топиков: `replication.factor=3` (включая лидера),
  `min.insync.replicas=2`, `acks=all`; KRaft. Другие параметры ещё выбираются.
- Результат обработки и Inbox фиксируются одной локальной транзакцией;
  при необходимости Outbox создаётся там же. Offset подтверждается после неё
  только по непрерывно обработанным сообщениям партиции.
- Временные ошибки повторяются с задержкой; некорректные данные фиксируются
  для разбора и оповещения. Зависимые действия нельзя применять как будто
  проблемное событие обработано. Технический процесс ошибок ещё проектируется.
- Каждому сервису — свои права на конкретные публикации и чтение. Видео, пароли,
  токены и временные ссылки не помещаются в события.
- Срок хранения Kafka не является резервной копией. Предложена
  [стратегия восстановления и очистки](../recovery/53-event-recovery-and-safe-cleanup.md);
  конкретные API, позиции чтения и восстановление кластера ещё требуется
  определить и проверить.
