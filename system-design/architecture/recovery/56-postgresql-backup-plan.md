# PostgreSQL backup и WAL: проект учебной системы

План для будущего Java / Spring-проекта, а не настройка текущего сервера.
Инструмент для проектирования: **pgBackRest** с базовыми копиями и архивом WAL.
Он поддерживает full/differential backup и восстановление; настройки и версии
не проверялись в нашем окружении. [Руководство pgBackRest](https://pgbackrest.org/user-guide.html).
Для PITR PostgreSQL нужны базовая копия и непрерывная цепочка WAL; архив WAL
не восстанавливает все внешние конфигурационные файлы.
[Документация PostgreSQL 17](https://www.postgresql.org/docs/17/continuous-archiving.html).

## Что и куда копируем

У каждого PostgreSQL-кластера свой stanza и идентичность; если несколько
логических БД находятся в одном PostgreSQL-кластере, физическая копия и PITR
восстанавливают кластер целиком, а не отдельный сервис. Для каждого кластера
сохраняются база, необходимые WAL и метаданные pgBackRest; конфигурация,
секреты и ключи восстанавливаются отдельно из управляемого источника. Секреты
не хранятся в репозитории, событиях или логах.

Для учебного стенда выбираем локальный repository pgBackRest в отдельном
каталоге `/srv/fitness-lab/backups/postgresql`, вне каталогов данных PostgreSQL,
с отдельными stanza для PostgreSQL-кластеров. Это проект пути для будущей Linux
среды; каталог сейчас не создаём. Все контейнеры находятся на одной машине,
поэтому эта копия помогает от логической ошибки, но **не защищает от потери
сервера или диска**. Для проверки сценария полной потери нужен отдельный
repository в другой области отказа; до его появления риск считается открытым.
Шифрование repository включено; ключ доставляется из отдельного хранилища
секретов при запуске, не сохраняется в репозитории проекта или конфиге с
общим доступом. Резервирование ключа и его восстановление проверяются отдельно.

## Стартовое расписание — техническое предложение

| Что | Предложение | Назначение и ограничение |
| --- | --- | --- |
| Полная копия | Каждое воскресенье в 00:15 UTC. | Базовая точка восстановления; окно проверяется по нагрузке. |
| Дифференциальная копия | Ежедневно с понедельника по субботу в 00:15 UTC. | Уменьшает объём восстановления относительно одной недельной полной копии. |
| WAL | Непрерывное архивирование завершённых сегментов; `archive_timeout` стартово 60 секунд. | Цель ограничения возраста незакрытого сегмента, не гарантия RPO 60 секунд и не RPO 0. |
| Хранение | Цель PITR минимум за последние 30 суток; стартово `repo1-retention-full-type=count`, `repo1-retention-full=6`. | Шесть недельных полных копий дают запас при штатном расписании, но число копий не гарантирует 30 дней при сбоях: проверять реальное окно и WAL, оповещать при нехватке. |
| Проверка | Ежедневно проверять успех backup и архивирования; еженедельно выполнять изолированное восстановление, ежемесячно — тренировку всей цепочки. | Проверка backup-файла не заменяет реальный restore и проверку бизнес-инвариантов. |

Срок 30 дней относится **к учебным резервным копиям БД**, не к видео и не к
сроку хранения журнала модерации. Это выбранный старт для проектирования, не
юридическая политика и не подтверждённое измерением RPO/RTO. Хранение базы с
историей допускает удаление по её правилам лишь после согласования backup,
retention и требований к данным. pgBackRest может удалять WAL вместе с
устаревшими копиями; aggressive expiry может сократить реальное окно PITR.
Правила конфигурации и зависимости копий нужно проверить на своей версии.

Проверять и оповещать: отсутствие последнего полного или ежедневного backup,
ошибки и лаг архива WAL, размер `pg_wal`, свободное место, недоступность
repository и неудачный тест restore. Не очищать WAL вручную для освобождения
места без подтверждённого плана: это может уничтожить цепочку восстановления.

## Как восстанавливаем

1. При инциденте останавливаем опасные операции и ограничиваем writers в
   затронутом контуре по [контракту восстановления](54-event-recovery-contract.md).
2. Выбираем проверенный backup и целевую точку; проверяем доступность всей
   цепочки WAL, версию PostgreSQL, конфигурацию и ключи. Если цепочки нет —
   не объявляем RPO 0 и не выдумываем недостающие операции.
3. Восстанавливаем **в изолированный экземпляр**, а не поверх работающей базы.
   Сохраняем данные повреждённого экземпляра для разбора в рамках политики
   доступа; любые файловые операции и их конкретные команды определяются
   отдельным runbook после выбора инфраструктуры.
4. Проверяем успешный запуск, целевую точку, schema version, контрольные суммы,
   журналы событий и состояние внутренних операций. Для Coins дополнительно
   сверяем кошельки, holds, ledger, escrow и фазы settlement с Challenge.
5. Если обнаружены отсутствующие подтверждённые денежные операции или нельзя
   доказать полноту, оставляем денежные действия и зависимые операции
   заблокированными и передаём расхождение на разбор. Координатор не правит
   баланс вручную и не проводит повторную выплату по предположению.
6. После проверки и утверждённой процедуры подключения выполняем сверку
   событий, checkpoint Kafka и контролируемое возобновление по
   [контракту](54-event-recovery-contract.md). Частично восстановленный контур
   не объявляется полностью готовым.

Для Coins действует выбранное правило: A — основная база, B — синхронная
реплика и не повышается автоматически. При отказе A ждём её восстановления;
способ восстановления или замены A без нарушения этого правила проектируется
отдельно. Успешный backup не гарантирует сохранность последних подтверждённых
операций: при потере A и B архив WAL может отставать. RPO 0 остаётся целью,
а не обещанием при любом повреждении.

## До внедрения

Выбрать и закрепить точные версии PostgreSQL / pgBackRest, внешний repository,
механизм управления ключами, параметры
синхронной репликации, реальные RPO/RTO и пороги оповещений. Проверить full,
differential и PITR в отдельной среде, отсутствие нужного WAL, недоступность
repository, восстановление ключей, потерю A и B, совпадение ledger и кошельков,
две независимые БД после разных точек восстановления и связь с Kafka offsets.
Миграции, настройки backup, архивирование и тестовое восстановление в этом
задании **не выполнялись**.
