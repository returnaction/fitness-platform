# Карта контрактов будущих сервисов

Текущие отметки аудита каждого сервиса и найденные несостыковки:
[проверка документации](62-service-documentation-audit.md). Эта карта — обзор,
она не означает завершения детальной сверки.

Учебный проект Java / Spring: документы ниже описывают проектируемую систему,
а не работающие микросервисы. Существующий Python-монолит — источник примеров,
но его правила не переносятся автоматически. Монеты виртуальные.

Количество компонентов — проектное решение, а не доказательство, что каждый
нужно сразу разворачивать отдельно.

## Как оформляем каждый контракт

1. Назначение, владелец данных и ограничения: кто имеет право менять состояние.
2. Таблицы PostgreSQL: имя, поля и типы, обязательность, ключи, ограничения,
   индексы, конкурентный доступ и границы транзакций. Одна таблица имеет одно
   основное определение; другие документы дают на него ссылку.
3. HTTP: метод и путь, права, запрос и ответ с примерами, статус успеха,
   формат ошибок и коды, правила повторов и конфликтов.
4. Взаимодействия: инициатор, получатель, транспорт, состав команды/события,
   версия схемы, идентификаторы, результат, повторы и обработка ошибок.
5. Состояния, переходы, дедлайны и бизнес-инварианты; отдельно — ожидаемые
   данные и события после каждого действия.
6. Восстановление после сбоя, идемпотентность, параллельные запросы, аудит,
   наблюдаемость и сценарии проверки. Явно отделять решения от предложений.

## Общие механизмы и границы

- Данные принадлежат сервису; между его БД и БД другого сервиса нет общего FK
  или единой транзакции. Ссылки между сервисами — идентификаторы и контракты.
- Для факта и события — локальная транзакция с outbox; получатель применяет
  событие с inbox и бизнес-проверкой. Доставка может повторяться. Карантин
  некорректных сообщений не заменяет повторы временных сбоев.
- Kafka используется для событий; RabbitMQ — для задач подготовки видео;
  gRPC — для выбранных межсервисных запросов; REST — для приложения. Точные
  маршруты и настройки определяются предметными контрактами.
- Запись критичных данных Challenge, Coins, Moderation и Video Proof ожидает
  синхронную реплику согласно согласованной модели; физический стенд на одном
  сервере не обеспечивает независимость от отказа самого сервера.
- Ошибку нельзя считать одной только HTTP-цифрой: DTO, стабильный код и
  поведение клиента описываются в контракте конкретного API. Секреты, токены и
  ссылки на видео не попадают в события и журналы.

## Порядок работы

Challenge → Video Proof → Moderation → Exercise Catalog → Notifications →
сквозная сверка Identity, Accounts, Coins и Gateway. Для каждого сервиса
сначала сверяем принятые правила и существующие документы, затем проектируем
таблицы и контракты, после чего проверяем связанный пользовательский путь.
Расхождения и решения, требующие выбора продукта, остаются в
[открытых вопросах](05-open-questions.md); без них документация не считается
готовой к генерации кода.
