# Identity: вход и сессии — рабочий контракт

Документ новой системы Java / Spring. Это проект, не описание реализованного API.
[Регистрация и модель данных](30-identity-registration.md) определяют создание
пользователя, профиля, кошелька и первой сессии.

## Сверка с работающим монолитом и решение для новой системы

В Python-монолите access JWT содержит `sub` (пользователь), `sid` (сессия),
роли, сроки, issuer и audience; код проверяет подпись и обязательные поля.
`logout` отзывает запись `auth_sessions` в PostgreSQL, refresh также учитывает
её состояние. Но `GetCurrentIdentityService.authenticate` после проверки JWT
загружает по `sub` только пользователя и его статус: существование и отзыв
сессии по `sid` он не проверяет. Роли берутся из claims токена. Поэтому нельзя
утверждать, что в текущем монолите logout сразу запрещает уже выданный access
token: обычная проверка может принимать его до истечения срока при активном
пользователе. Это статический вывод из кода, не результат нового теста.

Источники — исторические пути монолита, не перенесённые в этот репозиторий:
`backend/app/core/security/tokens.py`,
`backend/app/modules/identity/application/current_identity.py`,
`backend/app/modules/identity/infrastructure/repository.py` и
`backend/app/modules/identity/application/logout.py`.

Для Java / Spring сохраняем идею JWT с `sub` и `sid` и отзыв сессии в БД,
но добавляем обязательную проверку сессии при защищённом запросе. Вызывающий
компонент проверяет подпись и claims токена и обращается к Identity по gRPC
`CheckSession`; Identity читает primary PostgreSQL и сверяет пользователя,
принадлежность и отзыв сессии. Доступ к действиям проверяется отдельно.
Уже описанный [межсервисный контракт](../../interactions/59-identity-accounts-internal-api.md#проверка-сессии-сервис--identity)
содержит запрос, ответ, ошибки и границу полномочий. JWT и секреты в этот
вызов не передаются. Это проект, а не готовая реализация.

## Вход

Предлагаемый внешний API: `POST /api/v1/auth/login`, JSON с `email` и `password`.
Identity нормализует email той же политикой, что при регистрации, проверяет
пароль и состояние пользователя. `PENDING` не может войти; обычное ограничение
новых вступлений не равнозначно полной блокировке входа. При успехе Identity
создаёт сессию и возвращает access token на 15 минут и refresh token на 30 дней.
Ответ содержит `token_type`, сроки действия в секундах и не кешируется;
токены и пароль не записываются в журналы.

При неверном email или пароле предлагается один безопасный ответ `401` с кодом
`invalid_credentials`, без указания, какая часть неверна. При лимите — `429`;
начальный лимит login — 10 попыток в минуту с IP. Для `PENDING` после проверки
пароля согласован `503 registration_pending`; политика полного ограничения
доступа уточняется в общей модели Identity.

## Что уже делает существующее приложение

Сверено статически с `backend/app/modules/identity/api/router.py`,
`api/schemas.py`, `application/login.py`, `application/refresh_session.py`,
`application/logout.py` и `infrastructure/models.py`:

| Запрос | Тело | Текущий результат |
| --- | --- | --- |
| `POST /api/v1/auth/login` | `email`, `password` | `200` и пара токенов; неверные данные `401 invalid_credentials`; недоступный аккаунт `403 account_unavailable`. |
| `POST /api/v1/auth/refresh` | `refresh_token` | `200` и новая пара; старый refresh помечается использованным. Недействительный токен — `401 invalid_refresh_token`. |
| `POST /api/v1/auth/logout` | `refresh_token` | `204`; отзывает связанную сессию. Некорректный или неизвестный токен тоже получает `204`. |
| `POST /api/v1/auth/logout-all` | Bearer access token | `204`; отзывает все активные сессии текущего пользователя. |

Текущий ответ токенов содержит `access_token`, `refresh_token`, `token_type`,
`expires_in`, `refresh_expires_in`; ответы с токенами имеют `Cache-Control:
no-store`. В текущей БД есть `auth_sessions` и отдельная `refresh_tokens`;
секрет refresh хранится как хеш. При повторном использовании уже применённого
refresh текущая реализация отзывает сессию. Это означает, что потерянный ответ
после успешного refresh может потребовать повторного входа; тесты здесь не
запускались. Срок сессии в текущем коде фиксирован при login: rotation не
продлевает его автоматически.

## Предлагаемый контракт новой системы

Сохраняем четыре понятных пути и форму token response выше. Данные входа:

```json
{"email":"anna@example.com","password":"a"}
```

Внешний ответ ошибки использует согласованный конверт `error.code`,
`error.message`, опциональный `error.details`, `error.request_id`; старый
FastAPI использует другой формат и автоматически не становится совместимым.
Ошибки login: `400 invalid_request` для некорректного JSON,
`422 validation_error` для недопустимого формата, `401 invalid_credentials`
для неверной пары, `429 rate_limited`, `503 identity_unavailable` для
временного сбоя и `500 internal_error` без внутренних подробностей.

Refresh и logout принимают `{"refresh_token":"<token>"}`; logout-all требует
access token. При успехе logout / logout-all возвращают `204` без тела. Refresh
вращает токен в той же сессии; TTL access — 15 минут, длительность сессии —
30 дней. Потерянный ответ refresh требует нового входа при повторе старого
токена; конкретный механизм срочной проверки отзыва описан ниже. Клиент хранит
токены в защищённом хранилище ОС, не в логах.

## Данные и тесты

У Identity — `users`, `user_credentials`, `auth_sessions` и данные refresh
tokens; в текущем Python варианте отдельная таблица `refresh_tokens` позволяет
зафиксировать использование и замену. Для Java-системы это кандидат, а не уже
утверждённая миграция. Сессия и новый refresh при login сохраняются атомарно;
rotation должна сериализоваться для одного токена. Проверяются успешный вход,
неверный пароль, неактивный пользователь, ограничение частоты, rotation, два
одновременных refresh, потерянный ответ, logout и logout-all, отзыв сессии,
отсутствие секретов в логах и PostgreSQL rollback.

## Дальнейшие сценарии

- Refresh: одноразовая смена refresh token; повтор и параллельные запросы нужно
  подробно спроектировать, учитывая потерянный ответ и защиту от повторного
  использования украденного токена.
- Logout: отзыв текущей сессии; logout-all: отзыв всех сессий пользователя.
  Повтор отзыва не должен создавать ошибочный доступ или вторую операцию.
- Отзыв сессии и уже выданные access token: выбран проект проверки актуальной
  сессии через `CheckSession`, описанный ниже и в межсервисном контракте.
- Должны быть реализованы и проверены хранение токенов на телефоне, схемы
  запросов, rate limit, rotation, миграции и интеграционные тесты.

## Согласованные правила login, refresh и logout

1. После успешного refresh старый refresh token использован. Повторное его
   применение приводит к отзыву сессии; если ответ потерян, пользователь
   входит заново. Клиент не отправляет параллельные refresh для одной сессии.
2. После подтверждённого logout отозванная сессия не допускает новые защищённые
   запросы даже с ещё не истёкшим access token. Проверка актуальности сессии
   обязательна; кэш допустим лишь если обеспечивает эту гарантию, включая
   сбои и задержки отзыва. Проект проверки через `CheckSession` указан ниже.
3. Ошибки: `401 invalid_refresh_token`, `429 rate_limited`, `503
   identity_unavailable`; logout с уже отозванным или неизвестным refresh —
   `204`. Начальный лимит login — 10 попыток в минуту с IP, подробности и
   настройка общей защиты ещё определяются.
4. В Identity используются `auth_sessions` и `refresh_tokens`. В refresh
   хранится хеш секрета, связь с сессией, сроки, использование и ссылка на
   замену; открытый refresh в базе не хранится. Точные DDL и индексы ещё нужны.
5. Одновременное применение одного refresh сериализуется; после замены повтор
   старого токена отзывает сессию. Это намеренный компромисс надёжности при
   потере ответа и защиты от повторного использования.
6. Незавершённую регистрацию продолжают после проверки email и пароля; сессия
   запрещена до готовности профиля и кошелька. Пока аккаунт `PENDING`, login
   возвращает `503 registration_pending` и инициирует продолжение операции.
   Старый ключ регистрации для login не нужен. Подробности и фоновые повторы —
   в [регистрации](30-identity-registration.md#продолжение-регистрации-и-вход-после-перезапуска-приложения).

## Проект API и ответы

Все запросы — JSON по HTTPS. Ошибки используют конверт из
[регистрации](30-identity-registration.md#рабочее-решение-для-первой-реализации):
стабильный `error.code`, безопасный `message`, необязательный `details` и
`request_id`. Токены в логи и сообщения не попадают.

| Запрос | Успех | Ошибки |
| --- | --- | --- |
| `POST /api/v1/auth/login` — email, password | `200` token response | `400 invalid_request`, `422 validation_error`, `401 invalid_credentials`, `403 account_unavailable`, `429 rate_limited`, `503 registration_pending`, `503 identity_unavailable`, `500 internal_error` |
| `POST /api/v1/auth/refresh` — refresh_token | `200` новая token response | `400 invalid_request`, `422 validation_error`, `401 invalid_refresh_token`, `403 account_unavailable`, `429 rate_limited`, `503 identity_unavailable`, `500 internal_error` |
| `POST /api/v1/auth/logout` — refresh_token | `204` без тела; повтор, неизвестный или уже отозванный токен тоже `204` | `400 invalid_request` для некорректного JSON, `429 rate_limited`, `503 identity_unavailable`, `500 internal_error` |
| `POST /api/v1/auth/logout-all` — Bearer access | `204` без тела, включая повтор при ещё действующей авторизации | `401 invalid_access_token` при отсутствии, истечении или отзыве токена, `429 rate_limited`, `503 identity_unavailable`, `500 internal_error` |

После успешного logout-all текущий access отозван, поэтому повтор с ним
получит `401`; `204` для повтора не означает обход авторизации. `PENDING`
после проверки пароля получает `503 registration_pending`; вход не создаёт
сессию и побуждает продолжить регистрацию. Публичную политику раскрытия состояний
аккаунта ещё нужно оценить. Ответ с токенами имеет `Cache-Control: no-store`:

```json
{"access_token":"<token>","refresh_token":"<token>","token_type":"Bearer",
 "expires_in":900,"refresh_expires_in":2592000}
```

Значения — секунды; при refresh `refresh_expires_in` показывает оставшееся
время сессии, абсолютный 30-дневный срок не продлевается. Ограничения TTL JWT
вблизи окончания сессии: access выдаётся не дольше оставшегося срока сессии.

## Проверка отзыва сессии: рекомендуемый первый вариант

Access token содержит `user_id`, `session_id`, срок и подпись. На каждом
защищённом запросе проверяются подпись, срок, назначение и актуальные состояние
сессии и пользователя через доверенную внутреннюю проверку Identity. Identity
читает актуальное состояние из основной БД; результат не считается валидным
на основании просроченного кэша. После подтверждённого logout новые проверки
отклоняют сессию; запрос, уже прошедший проверку до logout, может завершиться.
При недоступности Identity проверка не выдаёт доступ и возвращает `503`; не
нужно превращать такой сбой в ложное `401`. Оптимизация кэшем возможна позже
только при доказуемом сохранении гарантии отзыва. Проект gRPC, service identity,
аудитории токена, разрешения и ошибок — в [межсервисном контракте](../../interactions/59-identity-accounts-internal-api.md#проверка-сессии-сервис--identity).
Проект выдачи и ротации сервисных credentials определён в
[контракте регистрации](30-identity-registration.md#сервисные-credentials-и-разблокировка-обработки);
развёртывание issuer и secret store ещё нужно спроектировать. Дополнительная
задержка и зависимость доступности — осознанная цена требования.

## Данные Identity: `refresh_tokens`

Это дополнение к [auth_sessions](30-identity-registration.md#identity-auth_sessions),
а не отдельная таблица сессий. Предлагаемые столбцы:

| Поле | Тип | Ограничение |
| --- | --- | --- |
| `id` | UUID | Первичный ключ; публичный идентификатор части токена, не секрет. |
| `session_id` | UUID | NOT NULL, FK на `auth_sessions.id`; индекс для отзыва. |
| `secret_hash` | bytes | NOT NULL, уникален; открытый секрет не хранится. Алгоритм и безопасное сравнение требуют конкретизации. |
| `created_at`, `expires_at` | timestamptz | NOT NULL; `expires_at > created_at`, не позднее окончания сессии. |
| `used_at`, `revoked_at` | timestamptz NULL | Фиксация использования и отзыва. |
| `replaced_by_token_id` | UUID NULL | Локальный FK на `refresh_tokens.id`, уникальный при наличии; один заменяющий токен для одной операции. |

Индекс `expires_at` помогает очистке. Проверка срока относительно сессии между
таблицами обеспечивается прикладной транзакцией и тестами, не обычным CHECK.
Точную политику очистки токенов и необходимый срок хранения следов повторного
применения определить до миграции.

## Транзакции и повторы

- Login: проверка статуса и сохранение сессии и первого refresh атомарны в
  Identity; наружу токены возвращаются только после успешного commit.
- Refresh: блокируются сессия и предъявленный refresh, проверяется хеш и сроки;
  старый токен помечается использованным, новый сохраняется в той же транзакции.
  Повтор использованного токена после проверки секрета отзывает сессию. Если
  два запроса соревнуются, даже успешный первый ответ может стать недействителен
  после второго; клиент обязан делать single-flight.
- Logout и logout-all: отзыв фиксируется транзакционно до `204`. Потерянный
  ответ logout можно повторить; logout-all с уже отозванным access потребует
  новую авторизацию, при этом предыдущий отзыв остаётся выполненным.

## Rate limit и необходимые тесты

Согласован login: 10 попыток в минуту на IP. Для refresh / logout согласован
начальный предел 30 запросов в минуту на IP; отдельно защитить попытки для одного
аккаунта / сессии; окончательные пороги, доверенные proxy и доступность общего
хранилища лимитов определить до развёртывания. Не использовать исходные токены
или email в ключах логов лимитера. Это техническое предложение, не измеренная
производственная настройка. `429` сопровождается `Retry-After`.

Проверки: верный и неверный вход, `PENDING`, блокировка, срок сессии и подпись
токена; параллельный refresh и потерянный ответ; один и все logout, повторный
logout-all с отозванным access, состояние уже начатого запроса; недоступность
Identity при проверке отзыва; PostgreSQL-ограничения, транзакционный rollback,
параллельные запросы, ошибки и absence секретов в ответах / логах. Тесты ещё
не реализованы и не запускались.

## Техническая спецификация первой реализации

Ниже инженерное решение для проектируемой системы Java / Spring; действующий
Python backend или сервер оно не меняет. Значения конфигурации и миграции должны
быть проверены на совместимость до запуска нового проекта.

### Access token и проверка

- JWT подписывается Identity асимметричным `ES256`; заголовок содержит `kid`.
  Только Identity владеет закрытым ключом, проверяющие получают открытые ключи
  через доверенный конфигурируемый JWKS; ключи не хранятся в репозитории.
- Обязательны `iss`, `aud`, `sub` (user UUID), `sid` (session UUID), `iat`,
  `exp`, `jti` (UUID). Проверяющая сторона принимает только ожидаемый алгоритм,
  доверенный issuer, audience и корректную подпись; срок не более 15 минут и
  не дольше сессии. Секретов и персональных данных кроме необходимого ID в JWT
  нет. Точные `iss` / `aud`, публикация ключей и ротация — конфигурация среды.
- Gateway проверяет подпись и срок, затем для каждого защищённого запроса
  обращается к Identity с `sid` и `sub` по доверенному внутреннему каналу.
  Сервисы должны отклонять непроверенный контекст и прямой обход Gateway.
  Проверка свежести сессии в Identity читает основную БД; сбой проверки — `503`,
  а не разрешение доступа. Отозванная сессия — `401 invalid_access_token`.
  Бизнес-сервис дополнительно проверяет полномочия и доступ к своей сущности.
- Внутренний контракт `CheckSession`: вход `session_id`, `user_id`, выход
  `ACTIVE` или `INVALID`; доступен только аутентифицированным доверенным
  сервисам. Выбранный проект gRPC, полномочий и ошибок:
  [внутренние API Identity](../../interactions/59-identity-accounts-internal-api.md#проверка-сессии-сервис--identity).

### Refresh token

- Opaque-токен: идентификатор UUID и случайный секрет не менее 32 байт из
  криптографического генератора. Значение передаётся по TLS, хранится на клиенте
  в защищённом хранилище ОС. В БД сохраняется SHA-256 от случайного секрета;
  сравнение — constant time. Это высокоэнтропийный токен, а не пароль.
- В `refresh_tokens`: `id UUID PRIMARY KEY`, `session_id UUID NOT NULL` FK на
  `auth_sessions`, `secret_hash BYTEA NOT NULL UNIQUE` длиной 32 байта,
  `created_at`, `expires_at` как `timestamptz NOT NULL`, `used_at`, `revoked_at`
  как nullable `timestamptz`, `replaced_by_token_id UUID NULL` self-FK с UNIQUE
  для ненулевых значений. CHECK `expires_at > created_at`, индексы по
  `session_id` и `expires_at`; сроки проверяются относительно сессии в коде.
- Использованные токены сохраняются не менее времени жизни сессии, чтобы
  обнаруживать повтор. Очистка начинается после окончания / отзыва сессии и
  принятого срока аудита; точное время хранения аудита — отдельное решение.

### Порядок транзакций и блокировок

- Для каждой операции сперва блокируется строка `auth_sessions`, затем
  соответствующий `refresh_tokens` в едином порядке. Login создаёт обе строки
  и фиксирует их до отправки ответа; активен только пользователь `ACTIVE`.
- Refresh проверяет секрет и состояние под блокировкой, атомарно помечает
  старый использованным, сохраняет замену и связь. Если использованный токен
  предъявлен повторно с правильным секретом, сессия отзывается и commit делается
  до ответа `401`. Неверный секрет не должен позволять отзывать чужую сессию.
- Logout проверяет предъявленный секрет и идемпотентно отзывает его сессию.
  Logout-all авторизован текущей сессией и отзывает все сессии пользователя;
  одновременное создание новой сессии требует сериализации на строке пользователя
  при определении момента logout-all. Порядок блокировок пользователя, сессии и
  токена для всех операций должен быть единым во избежание deadlock и проверен.

### Пределы и тесты

- Начальные лимиты по согласованию: login — 10 запросов/мин/IP, refresh и logout —
  30 запросов/мин/IP; регистрация описана отдельно. Порог для дополнительной
  защиты аккаунта не утверждён. Доверять заголовкам IP только от настроенного
  proxy; `429` с `Retry-After`. Требуется общий лимитер для нескольких экземпляров
  и отдельное решение о его недоступности до развёртывания.
- PostgreSQL: уникальность и FK, rollback login и rotation, проверка секретов,
  два refresh одновременно, повтор после потерянного ответа, logout вместе с
  refresh и logout-all вместе с login, атомарность отзыва, ошибки БД.
- API / интеграция: `200`, `204`, `400`, `401`, `403`, `422`, `429`, `503`,
  ошибки подписи / issuer / audience / expiry, `PENDING`, отзыв и уже начатые
  запросы, недоступность Identity, запрет обхода Gateway, истечение сессии.
  Проверка отсутствия паролей, токенов и URL в ответах ошибок и логах.
- Проверка выполняется на реальном PostgreSQL и тестовых сервисах; это перечень
  будущих тестов, не отчёт об их запуске. Вопросы реализации и запуска нового
  проекта пока не закрыты одним документом.
