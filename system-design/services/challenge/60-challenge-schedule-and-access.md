# Challenge: расписание, публикация и приватный доступ — проект v1

Проект будущего сервиса Java / Spring. Он дополняет [API Challenge](39-challenge-api.md)
и использует единые определения таблиц из [модели Challenge](38-challenge-data-model.md).
Коды и пути ниже проектные; миграции, приложение и интеграционные тесты не созданы.

## Черновик и публикация

Черновик принадлежит создателю и допускает неполные поля. Просмотр и изменение
черновика доступны только ему. Перед публикацией Challenge проверяет право
пользователя, обязательную положительную ставку, режим, состав участников,
расписание и упражнения через Catalog, затем резервирует ставку через Coins.
При недостатке доступных монет публикации нет, черновик сохраняется. После
подтверждения участия создателя условия опубликованного challenge неизменяемы;
если нужно изменить условия, разрешённая отмена и новое создание выполняются
по ранее согласованным правилам. Потерянный ответ Coins не означает отказа.

## Состав запроса изменения черновика

`PATCH /api/v1/challenges/{id}/draft`, `Idempotency-Key` и JSON `version`:

```json
{"version":1,"title":"7 days","description":"Push-ups",
 "mode":"HEAD_TO_HEAD","stake_amount":10,"visibility":"PUBLIC",
 "participants":{"min":2,"max":2},
 "start":{"mode":"WHEN_FULL","scheduled_at":null,
          "extension":{"max_count":0,"interval_seconds":null}},
 "days":[{"day_number":1,"tasks":[{"position":1,"exercise_id":1,
 "variation_id":1,"target_value":10}]}]}
```

Частичный PATCH меняет только переданные корневые поля; `days` при наличии
полностью заменяет расписание черновика в одной локальной транзакции. Явный
`null` очищает только nullable поле; неизвестное поле — `422 validation_error`.
Отсутствие поля не меняет его. Собственные ID Challenge проверяются как UUID,
а `exercise_id` и `variation_id` — как числа `1`–`32767`; они не считаются
доказательством активности каталога. Полное расписание может состоять из
нескольких дней; пример показывает только один элемент. При сохранении
неполного черновика частичные условия допускаются, но при публикации они
обязательны и повторно валидируются.

Для PRIVATE черновик дополнительно принимает `private_password` строкой либо
NULL для удаления пароля до публикации; отсутствие поля не меняет пароль.
Сервер сразу хеширует пароль и сохраняет только хеш в `challenge_access_settings`.
GET и PATCH-ответы возвращают только `has_password: true|false`, не хеш и не
пароль. Тело и секреты запрещено включать в HTTP access log; идемпотентность
использует защищённый отпечаток согласно разделу приватного доступа.

`200 {"id":"<uuid>","status":"DRAFT","version":2}`. `409
version_conflict` — версия не совпадает; `409 challenge_not_editable` — уже
опубликовано; `422 validation_error` — недопустимый формат, число или массив;
`409 idempotency_key_conflict` — повтор ключа с другим телом. Одновременный
PATCH / publish сериализуется по строке challenge; повтор уже успешного ключа
возвращает первоначальный ответ, не создавая ложный conflict версии.

## Правила расписания и старта

- Длительность опубликованного challenge — 1–30 последовательных дней, без
  выходных; номера идут от 1 без пропусков. Каждый день содержит 1–10
  обязательных заданий, позиции уникальны в пределах дня. Одна запись — одно
  задание. Точная верхняя граница упражнения проверяется по варианту Catalog.
- `HEAD_TO_HEAD`: min и max равны 2, создатель занимает одно место. `GROUP`:
  min не меньше 2, max либо NULL, либо не меньше min. Состав и ограничения
  остальных режимов описываются до их включения; неподдержанный код — `422`.
- `WHEN_FULL`: задан конечный max; запуск после подтверждения всех мест и
  необходимых резервов. Это режим немедленного старта после заполнения.
- `AT_SCHEDULE`: `scheduled_at` — будущий UTC timestamp; запуск в это время,
  если подтверждённых участников не меньше min. Max может быть NULL. Чтобы
  начать в назначенное время только после заполнения, min и max равны.
- Создатель указывает `max_count` переносов >= 0 и положительный
  `interval_seconds`, если переносы включены; ноль переносов — interval NULL.
  Числовые верхние пределы этих двух значений требуют продуктового решения;
  сервер обязан проверять BIGINT-переполнение и допустимость timestamp.
- При нехватке участников в `AT_SCHEDULE` система переносит время на выбранный
  интервал, пока не исчерпаны переносы; затем отменяет и запускает возврат
  ставок. `WHEN_FULL` не имеет назначенной даты, поэтому временной перенос
  для него не применяется. Уведомления не доказывают возврат монет.
- Для учебного проекта день — интервал в 24 часа от фактического старта и
  последующих кратных суток UTC; вся группа имеет общий срок. Если нужные
  решения/апелляции предыдущего дня не готовы, следующие дни идут по расписанию
  согласно согласованным правилам; окончательный итог ждёт необходимых решений.

Расписание snapshot создаётся Challenge из валидированных условий и ответа
Catalog. `target_value` — int64 > 0 и в допустимом диапазоне конкретной
вариации; метрика и единица приходят от каталога. UI может заранее построить
одинаковые значения, удвоение или рост на 50% с округлением вверх, но backend
сохраняет и проверяет готовые значения каждого задания, а не доверяет формуле
или округлению телефона.

## Просмотр и сортировка

Единые DTO чтения деталей, расписания, участников и результата находятся в
[контракте HTTP API](39-challenge-api.md#6-прочитать-challenge-и-расписание).
Приватное описание видно без права вступления; чужие черновики скрыты `404`.
Пароль и приватный токен в ответ не входят. Для будущих дней время может быть
NULL до фактического старта; доступ к видео проверяется отдельно.

`GET /api/v1/challenges?min_stake=1&max_stake=100&exercise_id=1&sort=start_at&limit=20&cursor=...`
— проект поиска; min/max и exercise_id опциональны, sort: `start_at`, `stake`,
`participants`; limit 1–100, default 20. `200 {"items":[{...}],"next_cursor":null}`.
Каждый sort имеет вторичный стабильный ключ ID; cursor привязан к фильтрам.
При одинаковом времени/ставке ID определяет порядок. Формат cursor, полная
схема карточки и поведение NULL scheduled_at ещё необходимо определить до
реализации; список при изменении данных не обещает неизменяемый snapshot.

## Приватный доступ

Предлагаемые значения `PUBLIC`, `PRIVATE`. Приватный challenge отображается с
замком; описание и число участников видны, но вступление требует действующую
пригласительную ссылку или верный пароль, если он задан создателем. Наличие
ссылки позволяет вступить без пароля; пароль — альтернативный способ.
Ни ссылка, ни пароль не заменяют проверку мест, состояния, доступных монет и
ограничений Identity. Не показывать секреты в карточке, ошибках или логах.

### Создание и чтение ссылки

Проект v1: пароль задаётся при подготовке приватного challenge опционально;
если указан, применяется Argon2id с солью и стартовыми параметрами 64 MiB,
3 прохода, 1 поток. Лимит — 1–128 Unicode code points и максимум 512 UTF-8
байт, без молчаливого обрезания или изменения Unicode. Параметры проверяются
под нагрузкой; локальный алгоритм регистрации Identity не подразумевается тем
же. В БД хранится только хеш согласно [модели](38-challenge-data-model.md#challenge_access_settings).

Для приглашения используется `base64url(HMAC-SHA256(key, UTF8("challenge.invite.v1|"
 + canonical-lowercase-challenge-uuid)))` без padding. Ключ не менее 32
случайных байт из секретного хранилища; `invite_key_id` выбирает версию.
Авторизованный создатель вызывает `GET /api/v1/challenges/{id}/invitation` и
получает `200 {"invitation_url":"https://<app-host>/challenge/<uuid>#invite=<token>"}`
с `Cache-Control: no-store`. Ссылка формируется заново, токен не хранится в
открытом виде. URL чувствителен: не логировать, не включать в аналитику или
события. Клиент извлекает fragment и отправляет токен через TLS в теле POST;
App Links/deep links и защиту от утечки нужно проверить на целевых платформах.

Ссылка действует только пока challenge опубликован и открыт для вступления.
Ротация/индивидуальный отзыв ссылки в v1 не поддерживаются; если ключ
скомпрометирован, процедура аварийной ротации и сохранение старых key_id
проектируется отдельно. Нельзя удалять ключ, необходимый активной ссылке,
без обработки последствий. Создатель не может менять пароль опубликованного
challenge в обычном API; редактирование условий остаётся запрещено.

### Проверка при вступлении

`POST /api/v1/challenges/{id}/joins`, `Idempotency-Key`, для публичного тела
`{}`, для приватного ровно один вариант: `{"invitation_token":"<token>"}`
или `{"password":"<password>"}`. Оба поля, неизвестные поля или неверная
форма — `422 validation_error`. Сервер сравнивает HMAC токенов в constant time
или проверяет Argon2id; неуспех — `403 private_access_denied` с общим текстом.
Доступ не означает успешного вступления: далее выполняется резервирование и
проверка места по [контракту вступления](20-join-service-contract-draft.md).

Защита от перебора: стартовый лимит 10 неудачных проверок за 15 минут по паре
`(user_id,challenge_id)` и дополнительный по IP на доверенном Gateway; после
лимита `429 rate_limited` с `Retry-After`. Временные счётчики хранятся в Redis,
при его недоступности приватную проверку не выполнять: `503
private_access_unavailable`. Порог и IP-политика проверяются под нагрузкой;
прокси-заголовки принимаются только от доверенного Gateway. Токены, пароли и
payload не логируются. Отпечаток идемпотентности для чувствительного тела —
HMAC-SHA256 с отдельным серверным ключом и версией ключа, а не сохранённый
пароль или простой хеш пароля. Период хранения и ротация этого ключа должны
перекрывать незавершённые операции. Повтор той же операции не резервирует
монеты второй раз; при другом теле с тем же ключом — `409
idempotency_key_conflict`.

## Критерии проверки

Проверить параллельные PATCH и publish, два последних места, отмену и вступление,
отказ Coins до и после его commit, повтор ключа, каждый режим старта и число
переносов, все дни/задания, округление и переполнение, приватный доступ с
паролем и ссылкой, отзыв права, смену времени зоны клиента и чтение UTC,
потерю событий и перезапуск scheduler. Нужны реальные PostgreSQL сервисов;
описание не означает, что они уже проверены.
