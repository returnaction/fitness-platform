# Coins: резервирование ставки и распределение банка

Проект контракта новой системы на Java / Spring; не утверждение о работающем
gRPC API. Challenge и Coins — отдельные контексты со своими базами. Монеты
виртуальные; ставка обязательна и больше нуля. Связанные документы:
[кошелёк](33-coins-wallet-and-reward.md), [вступление](../challenge/20-join-service-contract-draft.md),
[отмена](../challenge/21-challenge-cancellation-draft.md).

## Сверка с действующим кодом

В `backend/app/modules/challenges/application/outcomes.py` текущий монолит
рассчитывает итоги и меняет удержания, кошельки и ledger в общей базе. Для
группы победителям возвращаются их ставки, а проигранные ставки делятся между
победителями. Остаточные монеты сейчас распределяются по фиксированному порядку
(создатель, время вступления, ID), а не случайно. В новой модели согласовано
случайное распределение остатка; результат выбора сохраняется. Это статическое
чтение кода, не проверка тестами.

В новой модели Challenge определяет итог, Coins владеет резервами и ledger;
общего commit между сервисами нет. Результат Challenge доставляется событием,
Coins выполняет расчёт в своей БД. При расхождении не угадываем и не выплачиваем
деньги: операция удерживается для разбора.

## gRPC: протокол v1

Рабочая спецификация, не сгенерированный код и не окончательные настройки
TLS / авторизации. Все UUID в proto ниже — канонические строки; сервер проверяет
формат и диапазон `amount`. Идентификаторы не являются секретом. Только
авторизованный Challenge имеет право выполнять команды и читать их состояние.

**Приоритет:** проектные контракты собраны в [coins-stake-v1.proto](../../contracts/coins-stake-v1.proto)
и [challenge-results-v1.proto](../../contracts/challenge-results-v1.proto). Для закрытия больших наборов одиночный `SealStakeSet` заменён
методами `BeginStakeSet` / `PutStakeBatch` / `FinalizeStakeSet`. Сообщения
этих методов описаны в разделе «Закрытие набора частями», а DTO отмены — в
[контракте отмены](../challenge/21-challenge-cancellation-draft.md). Старые фрагменты в этом
документе показывают историю; использовать отдельные файлы контрактов.

Примеры ниже — JSON-представление protobuf для чтения человеком; настоящий
gRPC передаёт protobuf. Внутренний ID пользователя никогда не принимается от
телефона как доказательство права: Challenge формирует данные на сервере, а
Coins проверяет полномочия вызывающего сервиса.

Единственное описание методов и DTO — [coins-stake-v1.proto](../../contracts/coins-stake-v1.proto).


`hold_id` присутствует только при `RESERVED`. Отказ из-за недостатка монет и
конфликт активного резерва — сохранённые бизнес-исходы, а не временный отказ.
Для новой попытки после окончательного отказа Challenge использует новый ID.
Повтор той же команды с тем же ID и параметрами возвращает сохранённый ответ;
повтор с другими параметрами — `ALREADY_EXISTS` и деталь
`operation_id_conflict`. `GetStakeOperation` без результата возвращает `NOT_FOUND`;
это не доказательство, что конкурентный запрос с тем же ID не завершится позже.
Если результат неизвестен, Challenge повторяет ту же команду или продолжает
сверку и не создаёт новую операцию до окончательного разрешения старой.

### gRPC ошибки

Внутри gRPC используем `google.rpc.Status`: `code` — стандартный числовой
gRPC-код, `message` — безопасный текст, `details` содержит
`google.rpc.ErrorInfo` с `reason`, `domain = "coins.fitness.internal"` и
необязательным `metadata.request_id`. Для межсервисного контракта `reason`
записывается в UPPER_SNAKE_CASE, например `OPERATION_ID_CONFLICT`; нижний
регистр в таблице ниже — исторические обозначения, не отдельный формат.
Клиенты ветвятся по gRPC code и `reason`, а не по тексту. Новые необязательные
metadata игнорируются, неизвестный reason обрабатывается как общая ошибка;
пароли, токены, данные кошелька и SQL в сообщениях не передаются. Наружный
HTTP API не отдаёт protobuf ошибки напрямую: он переводит их в согласованный
JSON `{"error":{"code":"...","message":"...","request_id":"..."}}`.

Пример gRPC rich error в JSON-представлении:

```json
{"code":6,"message":"Operation ID conflicts with previous request",
 "details":[{"@type":"type.googleapis.com/google.rpc.ErrorInfo",
 "reason":"OPERATION_ID_CONFLICT","domain":"coins.fitness.internal",
 "metadata":{"request_id":"<uuid>"}}]}
```

Это проект контракта зависимостей protobuf / gRPC; фактическая поддержка
`google.rpc.Status` в Java и сериализация трейлеров подлежат реализации и тесту.

| Код gRPC | Машинная причина | Смысл |
| --- | --- | --- |
| `INVALID_ARGUMENT` | `invalid_argument` | Неверный UUID, неуказанная причина или amount <= 0. |
| `UNAUTHENTICATED` | `service_unauthenticated` | Личность вызывающего сервиса не подтверждена. |
| `PERMISSION_DENIED` | `service_forbidden` | Нет разрешения на операцию. |
| `ALREADY_EXISTS` | `operation_id_conflict` | Тот же ID используется с другими параметрами. |
| `NOT_FOUND` | `hold_not_found`, `operation_not_found` | Резерв / операция не найдены; наличие запроса в пути исключается отдельно. |
| `FAILED_PRECONDITION` | `hold_not_releasable`, `hold_challenge_mismatch` | Резерв распределён либо не относится к указанному challenge. |
| `UNAVAILABLE` | `coins_unavailable` | Временная недоступность; результат после начала операции может быть неизвестен. |
| `DEADLINE_EXCEEDED` | — | Срок ожидания клиента истёк; результат может быть неизвестен. |
| `INTERNAL` | `internal_error` | Неожиданная ошибка без данных БД или секретов. |

Транспортный формат машинной причины и совместимость версий нужно закрепить в
общем gRPC error contract. Неверный секрет / права не должны раскрывать кошелёк.
При повторном `ReleaseStake` **с тем же operation ID** возвращается исход;
другой ID для уже освобождённого резерва не создаёт новую проводку и получает
`FAILED_PRECONDITION` с причиной `hold_not_releasable`. Единственный владелец
инициации возврата — Challenge: он создаёт одну долговечную операцию возврата
на hold независимо от того, обнаружили её отмена или процесс вступления.

### Примеры запросов и ответов

Резервирование:

```json
{"join_operation_id":"<uuid>","user_id":"<uuid>","challenge_id":"<uuid>","amount":"10"}
```

Protobuf JSON показывает `int64` строкой; в Java поле имеет тип `long`.
Ответ:

```json
{"join_operation_id":"<uuid>","outcome":"RESERVED","hold_id":"<uuid>"}
```

При недостатке средств `outcome` = `INSUFFICIENT_FUNDS`, `hold_id` отсутствует;
при уже активном другом резерве — `ACTIVE_HOLD_EXISTS`, без `hold_id`.
Оба бизнес-исхода возвращаются с gRPC `OK` и сохраняются по operation ID.

Возврат:

```json
{"release_operation_id":"<uuid>","hold_id":"<uuid>","challenge_id":"<uuid>","reason":"JOIN_NOT_CONFIRMED"}
```

Успех: `{"release_operation_id":"<uuid>","hold_id":"<uuid>","outcome":"RELEASED"}`.
Повтор с тем же ID и теми же данными возвращает исходный ответ, а не вторую
проводку. Другой ID для уже возвращённого hold — `FAILED_PRECONDITION`.

Получение исхода: `{"kind":"RESERVE","operation_id":"<uuid>"}`;
успешный ответ — `{"reserve":{"join_operation_id":"<uuid>","outcome":"RESERVED","hold_id":"<uuid>"}}`.
Для возврата передаётся `RELEASE`, ответ содержит `release`. `NOT_FOUND` не
доказывает отсутствие запроса в пути.

Исторический пример закрытия одним сообщением (не действующий API):

```json
{"seal_operation_id":"<uuid>","challenge_id":"<uuid>","set_version":"1",
 "stakes":[{"hold_id":"<uuid>","user_id":"<uuid>","amount":"10"}]}
```

Успех: `{"seal_operation_id":"<uuid>","challenge_id":"<uuid>","set_version":"1","set_digest":"<sha256-hex>"}`.
Несовпадение списка — `FAILED_PRECONDITION` / `STAKE_SET_MISMATCH`; изменённый
payload того же operation ID — `ALREADY_EXISTS` / `OPERATION_ID_CONFLICT`.
Действующий проект: пакеты по 500 строк, как описано в разделе ниже.

## Распределение банка

1. Challenge сохраняет окончательный `result_id`, `challenge_id`, список
   победителей и версию правил, только после завершения необходимых проверок и
   апелляций, затем отправляет факт через outbox / Kafka.
2. Coins проверяет авторизованный источник, единственность результата и полный
   состав действующих резервов, включая закрытие ранее начатых вступлений. При
   неизвестном составе или противоречии с отменой расчёт не выполняется.
3. Для одинаковых ставок, как в данной модели, банк — сумма всех активных
   резервов. Делим его на число победителей: `base = pool // n`,
   `remainder = pool % n`. Каждому — `base`, а по одной остаточной монете —
   случайно выбранным разным победителям. Выбор и его итог сохраняются как
   часть расчёта, после commit при повторе не выбираются заново.
4. Банк проводится по частям: отдельные транзакции с внутренним escrow,
   идемпотентными шагами и сохранённым прогрессом. Полный расчёт завершается
   только после выплаты всем победителям. Подробно: [большой банк](35-coins-large-settlement.md).
5. Сумма выплат равна сумме удержаний; остаточных / созданных монет нет.
   Согласование балансов и ledger при расхождении блокирует успех и создаёт
   сигнал для разбора. Повтор `event_id` и бизнес-дубликат с другим event ID не
   проводят расчёт дважды. Корректировка делается отдельной операцией и не
   перезаписывает первоначальный итог.

Пример: три участника поставили по 5, банк 15, победителей двое. Одному случайно
достаётся 8, другому 7; третий получает 0. У каждого из троих уменьшается
зарезервированный баланс на 5, а победителям увеличивается доступный на их
выплату. Ledger сохраняет отдельные изменения и идентификатор расчёта.
При ничьей один на один оба участника делят банк поровну; их личный результат
в статистике — ничья, а не победа. Внутренний набор `challenge_result_winners`
в этом случае содержит получателей долей.

## История и оставшиеся вопросы

История Coins отображает тип и изменения обоих балансов, время и связь с
challenge. Для стабильной пагинации используется порядок `(created_at, id)` и
непрозрачный курсор, проверяемый сервером и привязанный к авторизованному
пользователю. Для названия challenge выбрана локальная проекция ниже: пока она
не готова, название null, а монетные записи доступны. Прямая выборка из чужой
базы запрещена; восстановление проекции ещё требует конкретного контракта.

Административные корректировки остаются в backlog как отдельный контракт с
причиной, авторизацией и аудитом. Перед реализацией нужны конкретные protobuf
совместимости и безопасности, закрытие множества резервов, транзакции и тесты
PostgreSQL / брокера. Предложенная схема — не гарантия текущего приложения.

## План закрытия набора резервов и расчёта

Предлагаемый протокол; это инженерный проект, а не уже реализованная гарантия.

1. Challenge сохраняет все операции вступления до обращения к Coins. Закрытие
   набора, создание новых вступлений и переход к финализации сериализуются по
   одному challenge. После закрытия новые операции вступления не создаются;
   ранее начатые остаются отслеживаемыми.
2. Challenge доводит каждую ранее начатую операцию до известного результата.
   При неопределённости повторяет ту же команду; `NOT_FOUND` не доказывает, что
   запрос не находится в пути. Резервы без участия освобождаются.
3. После разрешения всех операций Challenge формирует неизменяемый список
   подтверждённых hold ID, участников, сумм и версию набора. Его отправляют
   в Coins частями через протокол `BeginStakeSet` / `PutStakeBatch` /
   `FinalizeStakeSet`, описанный ниже. Старый одиночный `SealStakeSet` отменён.
4. В Coins `ReserveStake` и `FinalizeStakeSet` для challenge сериализуются на общей
   строке состояния набора. Закрытие сверяет список с активными резервами;
   несовпадение не подтверждает закрытие. Повтор ранее выполненного резерва
   возвращает старый результат, ранее не выполненный резерв после закрытия
   запрещается. Сначала всё равно нужно разрешить ранее начатые операции.
5. После подтверждённого закрытия Challenge может передать окончательный result
   с версией набора; Coins проверяет версию и рассчитывает банк. При отмене
   Challenge вместо результата завершает возвраты и сверку.
6. При сбое состояние шагов хранится долговечно, повторы используют те же ID.
   При неопределённости финал не подтверждается; чужая БД не читается напрямую.

## Один возврат одного hold

Challenge — единственный инициатор освобождения. Отмена и неуспешное вступление
обращаются к одной локальной записи `release_intent` с UNIQUE (`hold_id`):
первая транзакция создаёт стабильный `release_operation_id` и фиксирует причину,
вторая получает существующую запись. Причина команды не меняется при повторе;
дополнительный факт отмены сохраняется отдельно. Потерянный ответ разрешается
повтором той же команды. Устойчивый порядок блокировок и конфликт с
распределением нужно проверить транзакционными тестами.

Событие отмены уведомляет другие сервисы, но Coins не создаёт второй независимый
процесс возвратов из события. Для подтверждённых участников Challenge также
создаёт intent на каждый hold. Завершение возвратов требует закрытого набора
и подтверждения Coins по каждому резерву.

## Название challenge в истории Coins

Предлагается локальная read-проекция: Challenge публикует доверенный факт
публикации с `challenge_id`, названием и версией; Coins идемпотентно сохраняет
снимок. Название после публикации не меняется. Если событие ещё не пришло,
история возвращает `challenge_title: null`, не задерживая монетную операцию;
после получения проекции название появляется. Coins не читает чужую базу и не
доверяет названию от клиента. Каждый запрос истории авторизуется по владельцу.
Порядок — `(created_at, id)` и непрозрачный keyset cursor; его точный формат и
восстановление проекции из авторитетных данных проектируются отдельно.

## Защита и хранение идемпотентности

- Внутренний gRPC: предлагаются TLS с взаимной аутентификацией сервисов и
  краткоживущий служебный токен с issuer, audience `coins`, идентичностью и
  отдельными полномочиями reserve / release / query. Coins проверяет оба слоя;
  пользовательский токен сам по себе не даёт этих прав. Выпуск и ротация
  сертификатов и токенов требуют инфраструктурной спецификации.
- Идентификаторы и результаты монетных операций хранятся вместе с ledger и
  settlement; короткого TTL, после которого старый повтор становится новой
  операцией, нет. Общая политика удаления данных пока не согласована. Если
  удаление вводится, нужна безопасная граница приёма старых операций и план
  архивирования: нельзя молча применить старый ID второй раз.

На первом этапе удаление аккаунтов не поддерживается; ledger и ID обработанных
операций сохраняются без автоматического срока удаления. Очистка или архив
позже допустимы только после отдельного проекта, который сохраняет защиту от
старых команд и восстановление вместе с журналом. Это не обещание бессрочного
физического хранения при катастрофе: резервное копирование требуется отдельно.

## Состояние, таблицы и границы транзакций: детальный проект

Это предлагаемая спецификация, не выполненная миграция. PostgreSQL является
отдельной локальной базой каждого сервиса: FK между сервисами отсутствуют.
UUID — PK, даты — `timestamptz`, суммы — положительные `BIGINT` с проверкой
переполнения; суммы банка суммируются в более широком типе и до записи
проверяются на допустимый диапазон. `created_at` / `updated_at` не NULL.

### Проверка закрытого набора

Закрытие делает `FinalizeStakeSet` по протоколу пакетной передачи ниже. Канонический digest и сверка набора обязательны.

- `seal_operation_id` — стабильный UUID, создаётся Challenge до первого вызова;
  `set_version > 0`; список не пустой, суммы > 0, hold ID и user ID уникальны.
  Пустой или некорректный список — `INVALID_ARGUMENT`.
- `set_digest` — lowercase hex SHA-256 от канонической последовательности:
  строки сортируются по canonical lowercase `hold_id`; для каждой используется
  `hold_id,user_id,amount` с разделителем `,`, строки разделяются `\n` без
  конечного перевода строки, UUID lowercase с дефисами, amount — десятичное
  целое без ведущих нулей. UTF-8; тестовые векторы обязательны.
- Coins под блокировкой набора повторно проверяет сохранённый результат по
  operation ID. Совпадающий запрос возвращает тот же ответ; другой payload с
  тем же ID — `ALREADY_EXISTS operation_id_conflict`. Незарегистрированные
  новые резервы после закрытия — `FAILED_PRECONDITION stake_set_sealed`.
- До записи `SEALED` Coins сверяет точный набор активных holds, user ID и суммы.
  Расхождение — `FAILED_PRECONDITION stake_set_mismatch`; закрытие не создаётся,
  причина передаётся на разбор без изменения балансов. `UNAVAILABLE` и
  `DEADLINE_EXCEEDED` не доказывают отказ: повторяется тот же seal ID и payload.
- После `SEALED` уже существующий reserve по тому же ID возвращает сохранённый
  исход без создания hold. Отдельный заключительный результат допускается лишь
  для сохранённых версии и digest. Смена набора после seal не допускается без
  отдельного, ещё не спроектированного протокола исправления.

### Событие окончательного результата v1: проект

Kafka, key = `challenge_id`, через Challenge outbox; JSON ниже — логическая
схема, регистрация и совместимость формата сообщений ещё требуют выбора:

```json
{
  "event_id":"<uuid>", "event_type":"challenge.finished", "schema_version":1,
  "occurred_at":"2026-11-05T12:00:00Z", "producer":"challenge",
  "correlation_id":"<uuid>",
  "data":{
    "challenge_id":"<uuid>", "result_id":"<uuid>", "set_version":1,
    "set_digest":"<sha256-hex>", "rule_version":"equal-pool-v1",
    "outcome":"SINGLE_WINNER", "winner_count":1,
    "winners_digest":"<sha256-hex>"
  }
}
```

Список победителей не помещается в событие: Coins читает неизменяемый список
страницами из Challenge по `result_id` и сверяет количество и digest. Список
непустой, ID уникальны и каждый победитель есть в сохранённом наборе.
`outcome` и версии правил проверяются; незнакомое значение не приводит
к выплате. Полный набор и суммы Coins получает из ранее закрытого снимка, не из
клиента; `set_digest` связывает событие с набором. Дубли `event_id` обрабатывает
inbox, дубли `result_id` и `challenge_id` — бизнес-уникальность. При наличии
другого итога или отмены применяется карантин / разбор, а не повторная выплата.
Допустимые исходы v1 и условия их проверки указаны в разделе «Исходы финального
события v1»; протокол постраничного чтения — в разделе ниже.

### Минимальные сценарии проверки

1. Поздний `ReserveStake` одновременно с `FinalizeStakeSet`; закрытый набор не
   пополняется, ранее начатая операция не теряется.
2. Потеря ответа любого из reserve / release / seal после commit: повтор того
   же ID и payload возвращает прежний результат, изменённый payload — конфликт.
3. Одновременные отмена и компенсация создают один release intent на hold;
   параллельные seal / release / settlement не создают двойной проводки.
4. Повтор события и другой event ID с тем же result: один settlement; другой
   result или конфликт отмены не меняют кошельки автоматически.
5. Чётное деление, случайный остаток, ничья, нулевые / отрицательные суммы,
   переполнение, несовпадающий список резервов, перезапуск до / после commit.
6. Проверка отказов авторизации, миграций, реального PostgreSQL, транспорта,
   брокера и восстановления без пропущенного outbox / inbox.

## Закрытие набора частями: выбранный проект v1

Не ограничиваем число участников одним gRPC-сообщением. Challenge сохраняет
снимок после закрытия набора и отправляет его пакетами максимум по 500 записей;
500 — технический размер пакета, не ограничение размера challenge. Протокол
заменяет `SealStakeSet` выше. До финализации временные данные не меняют банк.

Пакеты ограничивают размер gRPC-запроса. Сам банк распределяется отдельными
транзакционными шагами с escrow по [контракту большого банка](35-coins-large-settlement.md).
Пропускная способность и размеры batch требуют нагрузочных испытаний.

Единственное описание методов и DTO — [coins-stake-v1.proto](../../contracts/coins-stake-v1.proto).


- `Begin`: положительные версия и количество, 64 lowercase hex символа digest;
  сохраняет операцию и ожидаемые параметры. Повтор идентичен по ID и payload;
  другие параметры для того же ID — `ALREADY_EXISTS OPERATION_ID_CONFLICT`.
  Для одного challenge может быть только один незавершённый seal; конфликт
  другого ID — `FAILED_PRECONDITION STAKE_SET_SEAL_IN_PROGRESS`.
- `Put`: номер от 0; в пакете от 1 до 500 строк с корректными UUID и amount > 0.
  Повтор номера и данных возвращает предыдущий ответ; те же номер / ID с другими
  данными — конфликт. Дубли hold или user между пакетами отклоняются, а уже
  принятые пакеты не изменяются. Транспортная ошибка требует повтора того же
  пакета; никакие балансы на этом шаге не меняются.
- `Finalize`: под блокировкой строки `coin_stake_sets` сверяет число, digest,
  уникальные hold / user / суммы и точное совпадение активных резервов в БД.
  Ошибка количества / digest — `FAILED_PRECONDITION STAKE_SET_INCOMPLETE`,
  несовпадение с резервами — `STAKE_SET_MISMATCH`; состояние остаётся открытым,
  выпуск и расчёт не выполняются. При успехе локальная транзакция фиксирует
  SEALED, список и ответ; повтор возвращает тот же ответ. Ранее обработанный
  reserve возвращает сохранённый результат, новый после seal запрещается.
- Challenge не финализирует, пока хотя бы одна ранее начатая join / компенсация
  имеет неизвестный результат. `NOT_FOUND` не доказывает отсутствие команды в
  пути. Операция восстановления повторяет тот же reserve или release ID и не
  выдаёт новый. Без этого условия один только digest не защищает бизнес-логику.

### Порядок блокировок в пределах каждого сервиса

Единый порядок Coins для всех операций и исключения для короткого claim / lease:
[порядок блокировок](35-coins-large-settlement.md#порядок-блокировок-coins).
Операция, которой не нужна одна из перечисленных строк, пропускает её, но не
меняет относительный порядок остальных. Seal берёт stake set до фиксации набора;
внешних вызовов под блокировкой нет. Пересечение с проверкой идемпотентности и
создание новой строки набора требуют PostgreSQL-проверки. Challenge отдельно блокирует свой
challenge / stake set до join-операции и release intent; межбазовых блокировок
или общей транзакции нет.

### Отмена и итог

Challenge сериализует принятие окончательного `CANCELLED` и `FINISHED` на
строке challenge; одновременно оба решения не могут быть сохранены. До передачи
`FINISHED` закрытый набор подтверждён Coins. При отмене начатые join-операции
завершаются компенсацией; Challenge создаёт один release intent на hold и
повторяет его до подтверждения. Отменённый challenge не отправляет settlement.
Coins не выполняет новый reserve после подтверждённого закрытия набора; в
случае отмены допускает согласованные release по сохранённым hold до фиксации
`CANCELLED`. Поздние / противоречивые события ставятся на разбор без выплаты.
Способ подтверждения полного завершения отмены и защиты от отложенной доставки
команды после завершения — часть реализации протокола и интеграционных тестов,
а не автоматическое свойство Kafka.

### Исходы финального события v1

Для согласованной модели: `SINGLE_WINNER` — один победитель;
`MULTIPLE_WINNERS` — несколько победителей группового challenge;
`DRAW` — ничья один на один, оба участника в списке победителей. Остаток банка
делится случайно между разными победителями; результат сохраняется. Проверить,
что winner IDs уникальны и принадлежат закрытому набору, число соответствует
исходу и режиму, суммы и банк не переполняются. Старое рабочее значение
`WINNER_OR_TIE` не является допустимым кодом v1.

### Передача большого списка победителей

Challenge хранит количество, digest и список получателей в своих
[таблицах результата](../challenge/38-challenge-data-model.md#таблицы-challenge);
строки сохраняются вместе с итогом и outbox. `winners_digest`
— SHA-256 от user UUID в canonical lowercase с дефисами, отсортированных
лексикографически, через `\n` без конечного перевода строки, UTF-8. Список не
перезаписывается и сохраняется до подтверждённого получения результата Coins и
согласно общей политике хранения результатов.

Coins получает факт `challenge.finished`, затем запрашивает у Challenge
авторизованный внутренний gRPC `ListResultWinners(result_id, cursor, limit)`.
Список возвращается по возрастанию user UUID, пакет 1–500, по умолчанию 100.
Пустой cursor — начало, пустой next_cursor — конец. Курсор должен быть
непрозрачным, подписанным HMAC и привязанным к result_id; точная версия и
кодирование выбираются вместе с реализацией общего курсора, не копируются из
курсора отмены без учёта другого доменного префикса. На каждой странице
Challenge проверяет служебную авторизацию Coins. Вызов не делает внешняя
пользовательская сессия.

Coins сохраняет загруженные страницы в staging по `result_id`; повтор страницы
не изменяет уже сохранённые данные. До расчёта проверяются count, digest,
уникальность, наличие всех победителей в закрытом наборе и соответствие исходу.
Недоступность Challenge или потерянный ответ не завершают расчёт: запрос
повторяется с тем же result / cursor. После положительной сверки распределение
выполняется в локальной транзакции Coins. Если строка отсутствует, digest не
совпадает или другой результат уже принят, расчёт удерживается для разбора.
Такое чтение не делается под длительной блокировкой БД Coins; staging не
приравнивается к подтверждённому расчёту. Точные имена сообщений `.proto` и
таблиц staging должны быть определены перед генерацией кода.

### Совместимость события

Для учебной первой версии сообщение Kafka — UTF-8 JSON с `schema_version=1`,
обязательными полями из примера и строгой валидацией известных типов и outcome.
Новые необязательные поля потребители игнорируют; удалять обязательные поля,
менять их тип или смысл в v1 нельзя. Несовместимое изменение — новая версия с
отдельной проверкой потребителей и планом перехода; неизвестная версия идёт на
разбор, а не к выплате. Нельзя утверждать совместимость только потому, что
сообщение распарсилось. Реестр схем как инфраструктурный инструмент пока не
выбран; тесты контрактов publisher / consumer обязательны.

Приведённые таблицы и интерфейсы — спецификация для проверки, не SQL-миграция.
Для генерации финального кода остаются общие контракты аудита, служебной
авторизации и protobuf-ошибок, политика восстановления / эксплуатации и тесты
реальных PostgreSQL, Kafka и gRPC; запуск и надёжность не подтверждены.

Протокол заморозки набора при отмене, его DTO и тесты описаны отдельно:
[отмена и запоздавший ReserveStake](../challenge/21-challenge-cancellation-draft.md#протокол-отмены-при-запоздавшем-reservestake).
Там же определено, что резерв и заморозка блокируют одну строку набора.
