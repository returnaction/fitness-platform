# Coins: распределение большого банка по частям

Инженерный проект будущей системы; код и тесты ещё не созданы. Документ
заменяет предложение об одной транзакции для всех кошельков в [контракте ставок](34-coins-stake-and-settlement-contract.md).
Частичная обработка не означает полного завершения расчёта. Монеты виртуальные.

## Подготовка

1. Challenge сохраняет окончательный `result_id`, число победителей, digest и
   outbox после закрытия набора ставок и всех необходимых апелляций.
2. Coins обрабатывает `challenge.finished`: inbox и долговечная задача расчёта
   сохраняются одной транзакцией до подтверждения Kafka offset. Повтор события
   или результат с другим event ID не создаёт вторую задачу. Противоречивый
   payload / второй результат ставится на разбор.
3. Coins получает неизменяемый список победителей страницами по
   [challenge-results-v1.proto](../../contracts/challenge-results-v1.proto). Staging
   не меняет балансы. До расчёта проверяются число, digest, уникальность,
   принадлежность победителей закрытому набору и допустимость исхода.
4. Coins сохраняет allocations по формуле `pool // winner_count`, остаточные
   монеты назначает случайно разным победителям. Выбор фиксируется до выплат
   и при повторе не меняется. Проверяется, что сумма allocations равна банку.

### Выбор остаточных монет

После сверки полного списка Coins создаёт криптографическим генератором
случайный `random_seed` из 32 байтов и сохраняет его в settlement до построения
allocations. Для каждого победителя вычисляет `random_rank = HMAC-SHA256(seed,
UTF8("coins.remainder.v1|" + canonical-lowercase-user-uuid))`; записи сортируются
по `(random_rank, user_id)`. Первые `pool % winner_count` получают по одной
остаточной монете. Равенство rank разрешается порядком UUID. Повторы используют
сохранённый seed, поэтому выбор не меняется даже после сбоя; до фиксации seed
расчёт allocations не начинается. Seed и список победителей не задаются клиентом.
Это обеспечивает воспроизводимый случайный выбор внутри системы, но не является
криптографическим доказательством честности перед участниками. Необходимы
тестовые векторы и проверка конкурентной фиксации одного seed.

## Курсор победителей

`cursor` = `v1.<user-uuid>.<signature>`, UUID lowercase с дефисами. Подпись —
base64url без `=` от HMAC-SHA256 по UTF-8 строке
`challenge.result-winners.v1|<result_id>|<user-uuid>`. Ключ хранится в секретном
хранилище и общий для экземпляров Challenge. Курсор не является авторизацией:
Challenge проверяет права Coins на каждой странице. Пустой cursor — начало,
пустой next_cursor — конец; `limit=0` означает 100, явно допустимо 1–500.
Порядок — UUID, следующая страница `user_id > last_user_id`. Неверный cursor /
limit — gRPC `INVALID_ARGUMENT` с `INVALID_CURSOR` / `INVALID_LIMIT`.
Cursor и секреты не логируются; до ротации нужна поддержка версий HMAC-ключа.

## Проведение монет

1. В Coins создаётся внутренний **escrow расчёта** с балансом 0. Это не
   пользовательский кошелёк, напрямую тратить из него нельзя.
2. Небольшими транзакциями каждый hold переводится из `ACTIVE` в `SETTLED`:
   из locked баланса участника списывается сумма, escrow увеличивается на неё.
   Изменения кошелька, запись ledger, запись escrow и отметка hold фиксируются
   вместе. UNIQUE `(settlement_id, hold_id)` не даёт списать один hold дважды.
3. До выплат проверяются полный набор holds и равенство суммы escrow банку.
   При расхождении выплата не начинается, задача передаётся на разбор.
4. Пакетами каждая положительная allocation уменьшает escrow и зачисляет
   доступный баланс победителя. Кошелёк, ledger, escrow и статус allocation
   сохраняются одной транзакцией. Если allocation равна нулю, она помечается
   `PAID` без изменения кошелька, escrow и без нулевой проводки; это не
   начисление. PK `(settlement_id, user_id)` и проверка состояния исключают
   двойную выплату. После commit конкретный победитель может пользоваться
   начислением: итог challenge уже окончательный.
5. Только когда все allocations оплачены и escrow равен нулю, задача становится
   `COMPLETED`; событие завершения фиксируется в outbox в той же транзакции.
   До этого пользователь видит, что общий расчёт обрабатывается. Временный
   сбой восстанавливается повтором непроведённых шагов. Автоматически откатывать
   уже использованные выплаты нельзя; исключительные исправления требуют
   отдельного аудируемого процесса.

## Порядок блокировок Coins

Для бизнес-транзакции в Coins: `coin_stake_sets` по challenge →
`coin_settlements` → `coin_settlement_escrows` → `coin_holds` по возрастанию
UUID → `coin_wallets` по возрастанию user UUID → фиксация операций, ledger,
escrow entries и outbox. Отсутствующая или ненужная сущность пропускается без
изменения порядка остальных. Операция только кошелька, например ежедневная
награда, не берёт затем stake set. Индексы уникальности и конкурирующее первое
создание строк также должны учитываться в проекте транзакций.

Claim задачи и heartbeat могут взять только settlement в короткой отдельной
транзакции, которая не берёт stake set или кошельки. Проводка выполняется в
новой транзакции по полному порядку; settlement не удерживается из claim через
сетевой вызов. Resume блокирует stake set до settlement. Никаких внешних
вызовов под блокировкой БД. Порядок и сценарии first insert, конкурирующие
reserve, release, расчёт и восстановление необходимо проверить PostgreSQL-тестами
на deadlock и rollback. Размер batch по умолчанию 100, максимум 500 —
начальные параметры для измерений, не максимум участников.

## Обработчик расчёта: повторы и сбои

Источник работы — `coin_settlements` в PostgreSQL Coins. После фиксации inbox
и задачи обработчик опрашивает таблицу каждые 5 секунд. Claim в короткой
транзакции выбирает задачи с наступившим `next_attempt_at` и свободной или
истёкшей арендой через `FOR UPDATE SKIP LOCKED`; устанавливает `lease_owner`,
срок аренды 60 секунд по часам БД и увеличивает `lease_version`. Сетевые вызовы
Challenge выполняются после commit без удержания блокировок. Начальная
настройка — до четырёх задач одновременно на экземпляр.

Каждый шаг фиксируется отдельной транзакцией в указанном выше порядке
блокировок. Под блокировкой settlement проверяются фаза, `lease_owner`,
`lease_version` и неистёкшая аренда по времени БД до любых проводок. Старый
обработчик прекращает работу; его поздний ответ Challenge не применяется.
Проверка аренды, проводка, кошелёк, ledger, escrow и прогресс фиксируются одним
commit. При необходимости аренда продлевается отдельной короткой транзакцией
до истечения с проверкой владельца и версии. Внешний read-only запрос можно
повторить без изменения Challenge.

Срок аренды сравнивается с `clock_timestamp()` БД, считанным после получения
блокировки settlement; PostgreSQL `now()` отражает начало транзакции и может
устареть при ожидании блокировки. Проверка и изменения удерживают одну строку
до commit, чтобы новый claim не записал результат одновременно. Длинные
транзакции ограничиваются timeout и проверяются при нагрузочных испытаниях.

При временной недоступности Challenge, базы или сети сохраняются `attempt_count`,
безопасный `last_error_code` и `next_attempt_at`: задержка начинается с 5 секунд,
удваивается до 5 минут и дополняется случайным отклонением 0–20%. После успешного
шага счётчик сбрасывается. Если база недоступна и записать расписание нельзя,
аренда истечёт; после восстановления задача снова станет доступна. Продолжение
идёт с последнего commit; уникальные ключи hold и allocation и проверка состояния
защищают от повторного списания или начисления.

Несовпадение банка, digest, списка победителей, запрет доступа или несовместимая
версия контракта не исправляются бесконечными повторами: Coins сохраняет прежнюю
фазу в `blocked_from_phase`, переводит задачу в `BLOCKED`, очищает аренду и выдаёт операционный
сигнал. Автоматически менять банк или удалять проведённые записи запрещено.
Проверка и возобновление выполняются по операторскому контракту ниже; само
возобновление не доказывает устранение причины расхождения.

После переноса всех резервов сверяются количество и сумма с закрытым набором;
выплаты начинаются только при полном совпадении и достаточном escrow. При
каждой выплате сумма не может превышать остаток escrow. `COMPLETED` и событие
в outbox фиксируются одной транзакцией только после всех выплат и нулевого
escrow. Уникальность `challenge_id` / `result_id` и сверка данных защищают от
повторного расчёта; конфликт результата направляется на разбор. Это проект:
конкурентные транзакции, тайминги и восстановление ещё предстоит испытать.

### Разбор и возобновление остановленного расчёта

Только уполномоченный специалист с `coins.settlement.recover` может читать и
возобновлять остановленный расчёт. Перед возобновлением он устраняет причину
или передаёт расхождение владельцу данных; API не позволяет менять суммы,
список победителей, seed, проведённые операции или ledger. Если расхождение
требует исправления итогового результата после его фиксации, задача остаётся
`BLOCKED`: правила такого исправления отдельно отложены и `resume` не является
разрешением их обойти.

`GET /api/v1/admin/coins/settlements/{settlement_id}` возвращает `200`
`{"id":"<uuid>","phase":"BLOCKED","blockedFromPhase":"COLLECTING",
"lastErrorCode":"STAKE_SET_MISMATCH","version":3}`; данные доступны только
при `coins.settlement.recover`, отсутствующий ID — `404 settlement_not_found`.
Ответ не раскрывает токены и содержимое кошельков. Доступ к деталям отдельной
сверки определяется её собственным контрактом и полномочиями.

`POST /api/v1/admin/coins/settlements/{settlement_id}/resume` требует то же
право, `Idempotency-Key` UUID v4 и тело `{"expectedVersion":3,
"reason":"Исправлена недоступность источника"}`; причина 1–500 символов,
без секретов. В транзакции Coins по указанному ранее порядку блокируются stake
set и settlement; проверяются `BLOCKED`, версия и наличие допустимой сохранённой
фазы. После проверки сервер восстанавливает прежнюю фазу из `blocked_from_phase`,
обнуляет `blocked_from_phase`, очищает аренду и ошибку, увеличивает `lease_version` и `version`, назначает
`next_attempt_at` на время БД и сохраняет действие в
[`coin_settlement_recovery_actions`](36-coins-data-model.md#coin_settlement_recovery_actions)
одним commit. Ответ `200` содержит `id`, восстановленную `phase` и новую
`version`. Следующий шаг обработчика заново проверяет инварианты и при
расхождении снова блокирует расчёт; успешный resume не означает выплату.

Повтор того же ключа, оператора, объекта и тела после проверки прав возвращает
сохранённый результат; иной запрос с тем же ключом — `409
idempotency_key_conflict`. Неактуальная версия — `409 version_conflict`,
не `BLOCKED` — `409 settlement_not_blocked`, неверное состояние — `409
invalid_recovery_state`; `400` для неверного JSON/ключа, `422` для причины,
`401`/`403` для доступа, `404` для неизвестного объекта, `503` при временной
недоступности. Ответы используют общий формат ошибок, без SQL и секретов.
PostgreSQL-проверки должны включать одновременный resume, потерю ответа,
неизменность seed и проводок, повторную блокировку при неизменном расхождении,
отказ доступа и транзакционный rollback. Проект не реализован и не протестирован.

## Событие завершения расчёта

После сохранения всех выплат и нулевого escrow Coins в той же локальной
транзакции помечает settlement `COMPLETED` и сохраняет outbox-событие
`coins.settlement_completed` v1. Издатель — Coins, получатель — Challenge;
топик и key определены в [каталоге](../../architecture/messaging/19-kafka-topology.md).

```json
{"eventId":"<uuid>","eventType":"coins.settlement_completed","schemaVersion":1,
 "occurredAt":"2026-11-05T12:10:00Z","producer":"coins","correlationId":"<uuid>",
 "data":{"settlementId":"<uuid>","challengeId":"<uuid>","resultId":"<uuid>",
 "setVersion":1,"ruleVersion":"equal-pool-v1","completedAt":"2026-11-05T12:10:00Z"}}
```

Все поля обязательны; UUID, время и версия следуют общей оболочке. Событие
свидетельствует о завершении расчёта целиком, а не заменяет записи ledger или
уведомления об отдельных начислениях. Coins не публикует его при `BLOCKED` или
частичных выплатах. Challenge проверяет соответствие своему окончательному
результату и сохраняет inbox вместе с проекцией статуса расчёта. Дубликат с
тем же событием безопасен; тот же бизнес-ключ с другим `settlementId`, итогом
или данными не перезаписывает состояние и направляется на разбор. При отсутствии
результата событие хранится в ожидании, а не считается применённым.

## Восстановление проекции названий

Основной путь — событие публикации Challenge через outbox / Kafka и Inbox Coins.
Для полного восстановления уполномоченный worker читает challenge страницами
через внутренний API Challenge и сохраняет `(challenge_id, title, version)`,
применяя только новую версию. До начала обхода фиксируется позиция Kafka;
события с неё потребляются во время и после snapshot. Cursor и checkpoint
хранятся в Coins. Если retention уже не покрывает позицию, восстановление
начинается заново и не помечается успешным. Пока снимка нет, история возвращает
`challenge_title: null`, не блокируя операции. Точные API, согласованный
snapshot и проверка восстановления требуют реализации и интеграционных тестов.

## Проверки перед запуском

- PostgreSQL: параллельные jobs, unique hold / allocation, падение до и после
  каждого commit, отсутствие двойной выплаты, инвариант суммы, переполнение.
- Kafka / gRPC: дубликаты и конфликтные события, ошибки страниц / digest,
  deadline, недоступность Challenge и восстановление после перезапуска.
- Конкуренция: отмена и итог, резерв и seal, claim и расчёт, deadlock.
- Нагрузка: фактические batch, время блокировок и восстановление после сбоя.
  Реальные тесты и код на данный момент не выполнялись и не существуют.
