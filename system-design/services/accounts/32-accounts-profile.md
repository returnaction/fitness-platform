# Accounts: профиль пользователя

> Для нового Java API **своего** профиля актуальные согласованные требования
> находятся в [Spec 014](../../../specs/014-accounts-profile/spec.md): GET/PUT,
> восемь полей без public_profile_id, уточнённые дата рождения и ошибки.
> Контракт собственного профиля синхронизирован в T001; [OpenAPI](../../../contracts/openapi/accounts-profile-v1.yaml).
> Реализация runtime ещё не выполнена. Правила чужого профиля не меняются.

Рабочая модель для новой системы Java / Spring. Документ опирается на текущий
Python-код, но проектные предложения не считаются реализованным поведением.

## Граница

Accounts владеет данными профиля: ником, именем, часовым поясом и настройками
видимости. Identity владеет учётной записью, паролем, сессиями и ролями;
Coins — кошельком и монетами. Accounts ссылается на пользователя через `user_id`,
но не изменяет таблицы другого сервиса. Данные доступны только с учётом прав.

## Историческое Python-приложение: факты из кода

- `GET /api/v1/accounts/me` возвращает профиль текущего пользователя;
  `PATCH /api/v1/accounts/me` меняет только явно переданные поля.
- Поля: `nickname`, `first_name`, `last_name`, `date_of_birth`, `timezone`,
  `bio`, `visibility`. `timezone` по умолчанию UTC, `visibility` — PRIVATE.
- Ник — 3–30 символов: латинские буквы, цифры, `_` и `-`; уникальность не
  зависит от регистра. Занятый ник возвращает `409 nickname_already_taken`.
- Имена и фамилии — до 100 символов; текущая проверка запрещает цифры и пробелы.
  Описание — до 500 символов. Дата рождения не раньше 1900-01-01 и не в будущем;
  часовой пояс проверяется по IANA. Эти ограничения описывают нынешний код,
  не являются автоматически утверждёнными для новой модели.
- Текущая таблица `user_profiles` имеет `user_id` как PK и FK в общей БД,
  уникальный индекс на `lower(nickname)`. Значение генерируется как `Player_`
  и случайные шестнадцатеричные символы. Аватар в этой таблице и ответе нет.
- Источники: `backend/app/modules/accounts/api/router.py`, `api/schemas.py`,
  `infrastructure/models.py`, `infrastructure/repository.py`. Тесты и фактические
  настройки среды в этой сверке не запускались.

## Согласованные правила новой модели

- Внутренний идемпотентный вызов Identity `CreateProfileIfAbsent` описан в
  [контракте регистрации](../identity/30-identity-registration.md#внутренний-контракт-создания-профиля-и-кошелька).
- При регистрации Accounts создаёт ровно один профиль на `user_id` с ником
  `Player_<случайные цифры>`. При совпадении ника генерирует новый; повтор
  создания для существующего пользователя возвращает тот же профиль, а не
  перезаписывает данные. Отдельно предлагать пользователю указать имя не нужно.
- Профиль можно изменить позже. Регистрация и вход не считаются успешными,
  пока профиль и кошелёк не подтверждены; временный сбой восстанавливается по
  сценарию [регистрации](../identity/30-identity-registration.md).
- При разделённых базах `user_id` — идентификатор Identity без межбазового FK.
  Команду создания могут вызывать только доверенные компоненты; знание UUID не
  разрешает создать или изменить чужой профиль.

## Модель данных: проект

Проект таблицы `user_profiles` в базе Accounts:

| Поле | Тип | Правило |
| --- | --- | --- |
| `user_id` | UUID | PRIMARY KEY; ID пользователя Identity, без межбазового FK. |
| `public_profile_id` | UUID | NOT NULL UNIQUE; случайный публичный ID, отдельный от `user_id`, не меняется при смене ника. |
| `nickname` | VARCHAR(30) | NOT NULL; уникальный индекс без учёта регистра. |
| `first_name` | VARCHAR(100) | NULL; имя можно указать позднее, внутренние пробелы разрешены. |
| `last_name` | VARCHAR(100) | NULL; фамилию можно указать позднее, внутренние пробелы разрешены. |
| `date_of_birth` | DATE | NULL; дата рождения. |
| `timezone` | VARCHAR(64) | NOT NULL; IANA timezone, предлагается UTC по умолчанию. |
| `bio` | VARCHAR(500) | NULL; описание профиля. |
| `visibility` | VARCHAR(16) | NOT NULL; PRIVATE / PUBLIC, предлагается PRIVATE по умолчанию. |
| `version` | BIGINT | NOT NULL; номер версии для обнаружения параллельных изменений. |
| `created_at` | timestamptz | NOT NULL; время создания. |
| `updated_at` | timestamptz | NOT NULL; время последнего изменения. |

Согласованы значения по умолчанию `timezone=UTC` и `visibility=PRIVATE`.
Имена и фамилии допускают буквы разных языков, внутренние пробелы, дефис и
апостроф; внешние пробелы удаляются.
База защищает уникальность ника регистронезависимым индексом и допустимые
значения видимости. Точные правила сравнения, миграции и обработка Unicode
определяются вместе с правилами допустимых символов ника.

Доменный кандидат: `Profile` — entity с `user_id`; `Nickname` и `TimeZoneId` —
возможные value objects. Репозиторий — порт чтения / сохранения профиля; он не
раскрывает детали PostgreSQL в доменных правилах. Границы агрегата и классов —
предложение, не реализованный Java-код.

## Внешний API: проект v1

Собственный профиль определяется [Spec 014](../../../specs/014-accounts-profile/spec.md)
и [OpenAPI Accounts](../../../contracts/openapi/accounts-profile-v1.yaml).
Gateway проверяет JWT и активную сессию через CheckSession по gRPC mTLS.
Accounts использует UUID из sub; владелец не задаётся телом или клиентским заголовком.
Локальное доверие Bearer без повторной проверки подписи в Accounts не подтверждает
личность HTTP caller и не означает готовую защиту серверного развёртывания.

- `GET /api/v1/accounts/me` → `200` и свой профиль.
- `PUT /api/v1/accounts/me` → `200` и сохранённый профиль после commit.
  Все восемь полей обязательны к присутствию, включая nullable.
- Оба ответа содержат `Cache-Control: no-store`, общий `X-Request-Id`
  и явные null. Query string запрещён; PUT принимает `application/json`.
- Отсутствующий профиль не создаётся, ответ — `503 profile_unavailable`.

Пример ответа GET и полной формы PUT:

```json
{"nickname":"Player_482731","first_name":null,"last_name":null,
 "date_of_birth":null,"timezone":"UTC","bio":null,"visibility":"PRIVATE",
 "version":1}
```

`user_id`, `public_profile_id` и служебные даты в ответ своего профиля не входят.

### Версия при изменении профиля

Клиент передаёт version полученного профиля, а не If-Match. Короткая транзакция
READ COMMITTED выполняет UPDATE всех полей по user_id и ожидаемой version,
увеличивает version на один даже при прежних значениях, обновляет updated_at
и получает результат через RETURNING. Сетевых вызовов внутри нет.
Ноль обновлённых строк требует различить отсутствующий профиль (503)
и устаревшую версию (409 profile_version_conflict).
Конфликт именно индекса user_profiles_nickname_unique означает
409 nickname_already_taken после отката всей транзакции.
Свой ник и изменение регистра разрешены; старый ник после смены сразу свободен.

Idempotency-Key не требуется. Повтор после потерянного ответа со старой версией
может дать 409; клиент перечитывает профиль и сохраняет черновик отдельно.
Автоматическая подстановка новой версии запрещена. Техническая ошибка или
таймаут не доказывают отсутствие commit; HTTP timeout не означает отмену SQL.

### Просмотр другого пользователя

Адрес `GET /api/v1/accounts/by-nickname/{nickname}`, только для
вошедшего пользователя. Поиск ника регистронезависимый, как и его уникальность.
Сервер проверяет сессию и правила видимости; знание ника не заменяет проверку
прав. `user_id` остаётся внутренней связью и не возвращается в этом ответе.
После смены ник может занять другой пользователь; старая ссылка по никнейму не
гарантирует переход к прежнему владельцу.
Для постоянной ссылки выбран отдельный `public_profile_id`: проект пути и
правил — в [техническом решении](#предложения-по-оставшимся-вопросам).

Для `PRIVATE` пример ответа `200`:

```json
{"public_profile_id":"<public-uuid>","nickname":"Player_482731","visibility":"PRIVATE"}
```

Для `PUBLIC` пример ответа `200`:

```json
{"public_profile_id":"<public-uuid>","nickname":"Player_482731","visibility":"PUBLIC",
 "email":"anna@example.com","first_name":"Анна","last_name":"Иванова","bio":null}
```

### DTO ошибок Accounts

Предлагаемый общий формат соответствует
[формату ошибок Identity](../identity/30-identity-registration.md#рабочее-решение-для-первой-реализации).
Все ошибки — `Content-Type: application/json`:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Проверьте введённые данные",
    "details": [{"field": "nickname", "code": "invalid_format"}],
    "request_id": "<uuid>"
  }
}
```

`code` — стабильный код для логики клиента; `message` — безопасный текст,
который может меняться; `details` — массив деталей полей (для собственного профиля обязателен, без деталей — []);
`request_id` — идентификатор для поиска ошибки в логах. Необязательные новые
поля могут добавляться, клиент игнорирует неизвестные поля и коды обрабатывает
общим сообщением. Пароли, токены, email, SQL и stack trace не включаются.

| HTTP | `error.code` | Когда |
| --- | --- | --- |
| `400` | `invalid_request` | Некорректный JSON, пустое тело PUT, отсутствующее/неизвестное поле, неверный тип/enum или query string. |
| `401` | `invalid_access_token` | Нет действительной сессии или access token. |
| `403` | `access_denied` | Действие запрещено после проверки прав. |
| `404` | `profile_not_found` | Профиль по никнейму не найден. |
| `409` | `nickname_already_taken` | Ник уже занят, включая конкурентный запрос. |
| `409` | `profile_version_conflict` | PUT отправлен со старой версией профиля. |
| `415` | `unsupported_media_type` | Неподдерживаемый Content-Type PUT. |
| `422` | `validation_error` | Некорректное значение поля или null в обязательном поле. |
| `429` | `rate_limited` | Превышен лимит запросов; `Retry-After` при наличии. |
| `503` | `profile_unavailable` | Для /me: профиль отсутствует или недоступна БД; для чужого профиля — сбой необходимой зависимости. |
| `500` | `internal_error` | Непредвиденная ошибка без внутренних подробностей. |

Пример для занятого ника (`409`):

```json
{"error":{"code":"nickname_already_taken","message":"Этот никнейм уже занят",
 "details":[],"request_id":"<uuid>"}}
```

Пример для устаревшей версии (`409`):

```json
{"error":{"code":"profile_version_conflict",
 "message":"Профиль изменился. Обновите данные и попробуйте снова",
 "details":[],"request_id":"<uuid>"}}
```

### Согласованная валидация PUT

Сначала strip() для nickname, first_name, last_name и bio; внутренние пробелы
сохраняются, пустые необязательные строки становятся null. Затем собираются
все нарушения значений, без запросов к БД. Правила полей — в Spec 014 и OpenAPI:
имена допускают буквы разных языков и относящиеся к ним знаки, обычные внутренние
пробелы, дефис и апострофы U+0027/U+2019; хотя бы одна буква обязательна.
Длина имён до 100, bio до 500 Unicode code points, согласно VARCHAR PostgreSQL.
В bio разрешены emoji и переносы; HTML/Markdown не интерпретируются.
U+0000 отклоняется до БД с 422/invalid_format.

Дата рождения: от текущей даты UTC минус 150 лет до текущей даты UTC включительно.
Timezone — существующий IANA; visibility — PRIVATE/PUBLIC, пока только сохраняется.
Version — положительный Long. Отсутствующее поле, неверный тип, неизвестный
enum/регистр или непреобразуемая дата дают 400. Явный null в обязательном
значении, неверная длина/содержание или дата вне диапазона дают 422.
Коды деталей: required, invalid_length, invalid_format, invalid_value, out_of_range;
детали содержат только field/code, без текстов по полям.

### Дополнительные правила чужого профиля (вне Spec 014)

Дата рождения, timezone и другие неперечисленные личные поля не возвращаются.
Email принадлежит Identity, а не Accounts: серверный слой запрашивает его у
Identity через авторизованный внутренний интерфейс только для PUBLIC. Протокол,
права вызывающего сервиса и согласование видимости описаны как проект в
[межсервисном контракте](../../interactions/59-identity-accounts-internal-api.md); прямого чтения
чужой таблицы нет. До подтверждения актуальной
видимости и получения email нельзя отдавать устаревшие личные данные. При
недоступности зависимостей предлагается `503`, без возврата устаревших данных.
При отсутствии профиля — `404 profile_not_found`, без действительной сессии —
`401 invalid_access_token`. Изменяемый nickname может сделать старую ссылку
недействительной; повторное использование освобождённого ника может направить
старую ссылку к другому пользователю. Для закреплённых ссылок используется
согласованный `public_profile_id`; источники карточек должны получать его через
разрешённый контракт, а не подменять внутренним user_id. Проверка доступа и изменения PRIVATE
требуют отдельного контракта; URL и статусы — проект, не существующий endpoint.

Загрузка собственного аватара отложена в backlog; в первой версии достаточно
стандартной заглушки. API загрузки, хранение и модерация аватаров сейчас не
проектируются и не считаются реализованными.

## Сбои и тесты

Identity повторяет создание с тем же `user_id`, если ответ потерян; Accounts
возвращает ранее созданный профиль. Конфликт двух пользователей за ник должен
разрешаться уникальным индексом PostgreSQL; предварительная проверка одна не
устраняет гонку. Тесты: создание и повтор, конкурентная генерация и изменение
ника, валидация и null в PUT, недопустимый доступ к чужому профилю, timezone,
rollback при сбое БД и потерянный ответ в регистрации. Это план тестов, а не
утверждение, что они уже написаны или запущены.

### Оставшиеся задачи перед реализацией Accounts

- Описать `.proto` вызова Accounts → Identity за email, коды ошибок, deadline,
  сервисные полномочия, защиту канала и поведение при недоступности Identity.
- Реализовать и испытать [пакетный контракт публичных данных](../../interactions/59-identity-accounts-internal-api.md#получить-публичные-данные-участника-сервис--accounts)
  для карточек участников; он читает ник и публичный ID из основной БД без
  выдачи внутреннего `user_id` клиентам. Локальные проекции — отдельная задача.
- Подготовить миграцию Accounts: NOT NULL / UNIQUE для публичного ID, индекс
  уникальности nickname, ограничения полей и атомарную версию профиля;
  при редком совпадении случайного public ID повторить генерацию безопасно.
- Добавить PostgreSQL-интеграционные тесты ограничений, повторов и конкурентного
  PUT; API / межсервисные тесты PRIVATE / PUBLIC, сокрытия личных полей,
  получения email, изменения видимости и недоступности Identity. Проверить
  потерю ответа при создании профиля и восстановление регистрации.
- Собственный аватар отложен в [backlog](../../overview/05-open-questions.md#отложенные-возможности).

## Согласованные правила и открытые технические детали

1. Ник — 3–30 латинских букв, цифр, `_` или `-`; уникальность не зависит от
   регистра. Первоначальный ник можно изменить.
2. По умолчанию UTC. Приложение предлагает часовой пояс телефона при регистрации
   или первом открытии профиля; пользователь может его поменять. Сроки challenge
   хранятся в UTC и отображаются в выбранном поясе.
3. По нажатию на другого пользователя открывается его аккаунт. Профиль по
   умолчанию PRIVATE: другим доступен никнейм, но не email, имя, фамилия или
   описание. При PUBLIC доступны email, имя, фамилия и описание; дата рождения
   другим пользователям не показывается.
4. Имя, фамилия, дата рождения и описание необязательны и могут быть очищены;
   ник и часовой пояс не могут быть пустыми. Дата рождения пока не используется
   для ограничения доступа; возрастные правила отдельно не определены.
5. Для редактирования с нескольких устройств профиль имеет версию в JSON:
   устаревшее изменение возвращает конфликт, приложение предлагает обновить
   данные. Проверка и изменение атомарны; тесты ещё требуется реализовать.
6. Загрузка собственного аватара отложена: [backlog](../../overview/05-open-questions.md#отложенные-возможности).

Требуют технического уточнения согласование видимости и чтения email между
сервисами, детали конкурентных проверок и тесты.

## Техническое решение для реализации: просмотр и PUT

### Предложения по оставшимся вопросам

- Accounts → Identity: выбран внутренний gRPC-метод для получения текущего
  email по внутреннему user_id только при публичном просмотре, с явным правом
  вызывающего сервиса, deadline и TLS. Само наличие gRPC не подтверждает
  авторизацию. Identity не возвращает пароль, токены или посторонние поля;
  сбой — 503 без выдачи старого email. Формат Protobuf, доступ и защита канала
  требуют определения до реализации; это не готовый метод.
- Постоянные ссылки: выбран отдельный случайный `public_profile_id`,
  не равный внутреннему `user_id`, с уникальным индексом и неизменностью при
  смене nickname. Его можно использовать в URL `GET /api/v1/accounts/profiles/{public_profile_id}`;
  поиск по никнейму остаётся дополнительным. Идентификатор не секрет и не
  заменяет авторизацию. Поле включено в проектную таблицу; миграции пока нет.
- PostgreSQL / тесты: локальная миграция Accounts создаёт таблицу и ограничения,
  включая NOT NULL UNIQUE для публичного ID. Реальные
  PostgreSQL-тесты проверяют гонку nickname и версий, повтор создания и rollback;
  API / интеграционные тесты проверяют доступ PRIVATE / PUBLIC, сбои Identity,
  отсутствие лишних полей и состязание смены приватности с чтением.

### Публичный профиль и email

1. Accounts находит профиль по регистронезависимому нику, читая основную БД.
   Если профиль PRIVATE, возвращает публичный ID, ник и видимость, без обращения за
   email. При PUBLIC через внутренний доверенный интерфейс Identity запрашивает
   текущий email по внутреннему `user_id`. Внешний клиент этот ID не получает.
2. Доступ к внутреннему интерфейсу имеет только авторизованный Accounts;
   ответ, токены и email не записываются в логи. Таймаут или сбой Identity
   приводит к `503 profile_unavailable`, без ответа со старыми личными данными.
3. После получения email Accounts снова читает профиль из основной БД и сверяет
   видимость, версию и соответствие никнейму. Если данные изменились, повторяет
   чтение ограниченное число раз; при PRIVATE возвращает только публично
   допустимые ID, ник и видимость. При повторных изменениях возвращает временную
   ошибку, не раскрывая старые данные. Для `/by-nickname` нельзя использовать
   устаревшую реплику; gRPC-контракт — в
   [межсервисном описании](../../interactions/59-identity-accounts-internal-api.md).
4. У этой проверки есть предел: настройка может измениться сразу после финального
   чтения и до получения ответа клиентом. Поэтому это не гарантия мгновенного
   прекращения уже начатого просмотра. Гарантия для запросов, начатых после
   подтверждённого изменения PRIVATE, зависит от чтения с основной БД и проверки
   перед формированием ответа. Данные, ранее полученные другим человеком,
   забрать назад невозможно. Если понадобится более строгая гарантия, её надо
   отдельно определить вместе с механизмом координации.

### Проверки перед реализацией

- PostgreSQL: создание профиля дважды с одинаковым `user_id`, два участника с
  одинаковым ником с разным регистром, конкурентные PUT с одной версией,
  rollback при конфликте ника, отсутствие межбазового FK.
- API: `GET /me`, чужой PRIVATE / PUBLIC, получение email только для PUBLIC,
  отсутствие даты рождения, отказ без сессии, неизвестный ник, сбой Identity,
  PUT с `null`, пробелами, неизвестным полем, неверной датой и версией.
- Конкуренция: PRIVATE между первым чтением и ответом Identity; изменение ника;
  недоступность БД / Identity; уже начатые до переключения запросы проверяются
  в соответствии с пределом гарантии выше.
- Миграция и тесты пока не создавались и не запускались. Конкретные индексы,
  DTO и обработка ошибок согласуются с техническим стеком Java / Spring.
