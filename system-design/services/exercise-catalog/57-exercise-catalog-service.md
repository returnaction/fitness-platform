# Exercise Catalog — модель данных и контракты v1

Проект будущего сервиса Java / Spring, не действующий API и не миграция.
Единственный источник определений его таблиц — этот документ. Каталог владеет
категориями, упражнениями и вариациями. Challenge владеет опубликованными
снимками заданий; Moderation видит эти снимки. Каталог не меняет challenge.

## Сверка с монолитом

В текущем Python-приложении `exercise_catalog/api/router.py` предоставляет
чтение категорий, списка и деталей. В `exercise_catalog/infrastructure/models.py`
уже есть таблицы категорий, упражнений и вариаций, флаги активности и метрики
`REPETITIONS` / `DURATION`. Текущие ID — целые числа; проект ниже сохраняет
компактные `SMALLINT` ID для категорий, упражнений и вариаций. Это не
утверждает, что старый API уже реализует администрирование ниже.
Миграция данных и совместимость новой системы — отдельная задача.

### Что уже есть по инструкциям и проверке

- В исходных данных текущего приложения есть **12 записей вариаций с полем
  `instructions`** для шести упражнений: обычные приседания; пять вариантов
  отжиманий; три варианта бёрпи; обычные jumping jacks, скакалка и планка на
  предплечьях. Источник — исторический путь монолита
  `backend/migrations/versions/c9d2e5f8a1b4_add_exercise_catalog.py`, который
  не перенесён в этот репозиторий.
  Это состав исходной миграции, а не проверка содержимого конкретной базы.
- Эти инструкции кратко описывают движение, но не задают исчерпывающих и
  однозначных критериев для каждого спорного случая. Например, инструкция
  отжиманий говорит держать тело ровно и опускать грудь контролируемо, но не
  задаёт точную допустимую глубину. Не следует считать её полной методикой
  или автоматически выводить из неё новые причины отклонения.
- В будущей модели список упражнений и метрики выбран ниже. Инструкция
  вариации сохраняется в снимке задания при публикации challenge; участник и
  модератор видят зафиксированные условия. Последующая правка каталога не
  переписывает опубликованное задание. Контракт снимка и передачи:
  [формат задания](49-task-metric-contract.md), [передача в модерацию](../../interactions/44-video-moderation-handoff.md).
- Модератор выносит одно из четырёх решений по [согласованному контракту](../moderation/25-moderation-decisions.md#согласованные-коды-решений-и-состояние-задания).
  Наличие инструкции не означает, что автоматическая оценка или подсчёт уже
  существуют. Новые упражнения и вариации из списка ниже не объявляются
  имеющими готовые инструкции только потому, что у старого каталога они есть.

## Согласованный стартовый каталог

Это перечень для будущей системы, а не утверждение, что новые упражнения уже
добавлены в действующее приложение. Вариант по умолчанию — обычный (`STANDARD`).
Названия, описания техники и коды новых вариантов уточняются при подготовке
данных каталога. Упражнения и варианты не зашиваются в код: ими управляет каталог.

| Упражнение | Варианты | Как задаётся цель |
| --- | --- | --- |
| Приседания | Обычные, сумо, с прыжком, на одной ноге с опорой | Количество повторений |
| Отжимания | Обычные, ноги на возвышении, узкий хват, широкий хват, с хлопком, с колен | Количество повторений |
| Бёрпи | Обычные, с прыжком, с прыжком и поднятыми руками | Количество повторений |
| Прыжки с разведением рук и ног (jumping jacks) | Обычные | Количество повторений |
| Прыжки со скакалкой | Обычные | Количество повторений |
| Планка | Обычная, на прямых руках, боковая | Время в секундах |
| Подтягивания | Обычные, узкий хват, широкий хват, обратный хват | Количество повторений |
| Скручивания на пресс | Обычные, обратные, косые | Количество повторений |
| Выпады | На месте, вперёд, назад | Количество повторений |

Начальные ограничения для учебной версии (минимум и максимум включительно):

| Вариация | Цель |
| --- | --- |
| Приседания: обычные, сумо | 1–200 повторений |
| Приседания с прыжком | 1–100 повторений |
| Приседания на одной ноге с опорой | 2–100 повторений всего, поровну на каждую ногу; только чётные значения |
| Отжимания: обычные, с колен | 1–150 повторений |
| Отжимания: ноги на возвышении, узкий или широкий хват | 1–100 повторений |
| Отжимания с хлопком | 1–50 повторений |
| Бёрпи: обычные / с прыжком / с прыжком и поднятыми руками | 1–100 / 1–75 / 1–50 повторений соответственно |
| Jumping jacks | 1–300 повторений |
| Скакалка | 10–1000 повторений |
| Планка обычная или на прямых руках | 10–600 секунд |
| Планка боковая | 20–600 секунд всего, поровну на каждую сторону; только чётные значения |
| Подтягивания, любые вариации | 1–100 повторений |
| Скручивания обычные и обратные | 1–200 повторений |
| Скручивания косые | 2–200 повторений всего, поровну на каждую сторону; только чётные значения |
| Выпады, любые вариации | 2–200 повторений всего, поровну на каждую ногу; только чётные значения |

Согласованное правило: для симметричных заданий на две стороны указывается
общее чётное значение, чтобы поровну разделить его между сторонами. Для
приседаний на одной ноге с опорой и косых скручиваний также задаётся
общее чётное количество повторений, поровну на каждую сторону; минимальное
значение — 2. Например, 10 выпадов — пять на каждую ногу. Боковая планка на
60 секунд — 30 секунд на каждой стороне в одном задании и одном видео.
Чётность является дополнительным правилом проверки и не выводится только из
`min_target` и `max_target`. Данные пределы — стартовые настройки, а не
оценка возможностей пользователя; администратор может их менять. При изменении
предела существующие опубликованные задания сохраняют согласованные условия.

Для каждого упражнения каталог хранит одну основную метрику, все его вариации
используют её. Приложение показывает поле «повторения» для `REPETITIONS` и
«секунды» для `DURATION`. Сервер самостоятельно проверяет метрику и диапазон
выбранной вариации по каталогу; значение с другой единицей не принимается.
Например, 10 отжиманий — `10 REP`, а планка на минуту — `60 SECOND`. Снимок
задания вместе с метрикой и значением получает модератор: [единый формат](49-task-metric-contract.md).

Точные инструкции и критерии выполнения для новых вариантов ещё нужно заполнить
при подготовке стартовых данных. Для вариантов на разные стороны правило
подсчёта обязательно явно указывается в инструкции.

## Правила v1

- Для нового задания доступны только активные категория, упражнение и
  вариация. Каталог деактивирует записи, физическое удаление не предусмотрено.
- У упражнения один активный вариант по умолчанию `STANDARD`; клиент может
  выбрать другой активный вариант. Если `STANDARD` отсутствует или неактивен,
  упражнение нельзя опубликовать/выбрать как активное.
- Метрики v1: `REPETITIONS` / `REP`, `DURATION` / `SECOND`. Цель — целое
  положительное значение в диапазоне вариации. Другие метрики — будущая работа.
- Challenge при публикации получает данные каталога по доверенному сервисному
  вызову, проверяет цель и сохраняет свой неизменяемый снимок. Каталог не
  доверяет произвольному названию или метрике телефона. Изменение каталога не
  переписывает опубликованное задание: [формат](49-task-metric-contract.md).
- Проверка каталога и публикация Challenge не имеют общей транзакции. Рабочее
  правило v1: Challenge сохраняет данные и версию, полученные при успешной
  проверке; деактивация сразу после неё не переписывает принятый снимок. Для
  более строгого запрета публикации после деактивации нужен отдельный протокол.

## Единые таблицы PostgreSQL

ID категорий, упражнений и вариаций — `SMALLINT` в диапазоне `1`–`32767`;
они создаются через `GENERATED BY DEFAULT AS IDENTITY`. Их достаточно для
малого управляемого справочника, а Challenge хранит их как внешние числа без
межбазовых FK. Технические ID запросов, аудита и событий остаются UUID. Даты —
`timestamptz` UTC; `created_at`, `updated_at` имеют `NOT NULL DEFAULT
CURRENT_TIMESTAMP`, а изменение записи обновляет `updated_at` в той же локальной
транзакции. Данные каталога находятся только в его БД. `version BIGINT NOT NULL CHECK > 0` увеличивается
при каждом изменении. Код — `VARCHAR(64)`, regex
`^[A-Z][A-Z0-9_]{0,63}$`, значение после создания неизменно.

### `catalog_categories`

| Колонка | PostgreSQL-тип | Null | Правило |
| --- | --- | --- | --- |
| `id` | `SMALLINT` | Нет | `GENERATED BY DEFAULT AS IDENTITY`, primary key, `CHECK (id BETWEEN 1 AND 32767)`. |
| `code` | `VARCHAR(64)` | Нет | Unique, неизменяемый, regex общего правила. |
| `name` | `VARCHAR(120)` | Нет | После trim не пустое. |
| `is_active` | `BOOLEAN` | Нет | Активность категории. |
| `sort_order` | `INTEGER` | Нет | `CHECK (sort_order >= 0)`. |
| `version` | `BIGINT` | Нет | `CHECK (version > 0)`. |
| `created_at` | `TIMESTAMPTZ` | Нет | `DEFAULT CURRENT_TIMESTAMP`, UTC. |
| `updated_at` | `TIMESTAMPTZ` | Нет | `DEFAULT CURRENT_TIMESTAMP`, UTC; обновляется при изменении записи. |

Индекс: `(is_active, sort_order, id)`.

### `catalog_exercises`

| Колонка | PostgreSQL-тип | Null | Правило |
| --- | --- | --- | --- |
| `id` | `SMALLINT` | Нет | `GENERATED BY DEFAULT AS IDENTITY`, primary key, `CHECK (id BETWEEN 1 AND 32767)`. |
| `category_id` | `SMALLINT` | Нет | Локальный FK → `catalog_categories.id ON DELETE RESTRICT`. |
| `code` | `VARCHAR(64)` | Нет | Unique, неизменяемый, regex общего правила. |
| `name` | `VARCHAR(120)` | Нет | После trim не пустое. |
| `description` | `VARCHAR(1000)` | Нет | После trim не пустое. |
| `primary_metric` | `VARCHAR(16)` | Нет | `CHECK IN ('REPETITIONS', 'DURATION')`. |
| `is_active` | `BOOLEAN` | Нет | Активность упражнения. |
| `sort_order` | `INTEGER` | Нет | `CHECK (sort_order >= 0)`. |
| `version` | `BIGINT` | Нет | `CHECK (version > 0)`. |
| `created_at` | `TIMESTAMPTZ` | Нет | `DEFAULT CURRENT_TIMESTAMP`, UTC. |
| `updated_at` | `TIMESTAMPTZ` | Нет | `DEFAULT CURRENT_TIMESTAMP`, UTC; обновляется при изменении записи. |

Индекс: `(category_id, is_active, sort_order, id)`. Упражнение не активно для
выбора, если его категория неактивна. Изменение метрики опубликованного
упражнения в v1 запрещено: создаётся новое определение с новым кодом, иначе
диапазоны вариантов могут потерять смысл.

### `catalog_variations`

| Колонка | PostgreSQL-тип | Null | Правило |
| --- | --- | --- | --- |
| `id` | `SMALLINT` | Нет | `GENERATED BY DEFAULT AS IDENTITY`, primary key, `CHECK (id BETWEEN 1 AND 32767)`. |
| `exercise_id` | `SMALLINT` | Нет | Локальный FK → `catalog_exercises.id ON DELETE RESTRICT`. |
| `code` | `VARCHAR(64)` | Нет | Unique вместе с `exercise_id`, regex общего правила. |
| `name` | `VARCHAR(120)` | Нет | После trim не пустое. |
| `description` | `VARCHAR(1000)` | Нет | После trim не пустое. |
| `instructions` | `VARCHAR(2000)` | Нет | После trim не пустое. |
| `min_target` | `BIGINT` | Нет | `CHECK (min_target > 0)`. |
| `max_target` | `BIGINT` | Нет | `CHECK (max_target >= min_target)`. |
| `target_step` | `BIGINT` | Нет | `DEFAULT 1`, `CHECK (target_step > 0)`. |
| `is_active` | `BOOLEAN` | Нет | Активность вариации. |
| `sort_order` | `INTEGER` | Нет | `CHECK (sort_order >= 0)`. |
| `version` | `BIGINT` | Нет | `CHECK (version > 0)`. |
| `created_at` | `TIMESTAMPTZ` | Нет | `DEFAULT CURRENT_TIMESTAMP`, UTC. |
| `updated_at` | `TIMESTAMPTZ` | Нет | `DEFAULT CURRENT_TIMESTAMP`, UTC; обновляется при изменении записи. |

Ограничение: `UNIQUE (exercise_id, code)`. Индекс:
`(exercise_id, is_active, sort_order, id)`. `STANDARD` создаётся при
создании упражнения в той же транзакции. Запрет деактивации `STANDARD` для
активного упражнения обеспечивается блокировкой строки упражнения и проверкой
при изменениях; уникальный код сам по себе не гарантирует наличие варианта.
Допустимая цель находится в диапазоне и кратна `target_step` относительно
нуля; для симметричных вариаций выше это 2, иначе 1. При изменении диапазона
должно существовать хотя бы одно допустимое значение; `target_step` передаётся
клиенту вместе с диапазоном. Приложение показывает допустимые значения и
объясняет правило; сервер независимо проверяет шаг при публикации challenge.

### `catalog_admin_requests`, `catalog_audit`, `catalog_outbox`

`catalog_admin_requests`: `actor_user_id UUID NOT NULL`, `operation
VARCHAR(96) NOT NULL`, `key_digest BYTEA NOT NULL`, `request_digest BYTEA NOT
NULL`, `response_status INTEGER NOT NULL`, `response_body JSONB NOT NULL`,
`created_at timestamptz NOT NULL`, PK `(actor_user_id,operation,key_digest)`;
дижесты 32 байта. Результат и изменение фиксируются одним commit. Хранение
ключей — минимум 90 суток; бизнес-уникальность кодов остаётся после очистки.

`catalog_audit`: `id UUID PK`, `actor_user_id UUID NOT NULL`, `action
VARCHAR(96) NOT NULL`, `entity_type VARCHAR(32) NOT NULL`, `entity_id SMALLINT NOT
NULL`, `request_id UUID NOT NULL`, `old_version BIGINT NULL`, `new_version
BIGINT NOT NULL`, `occurred_at timestamptz NOT NULL`; индекс `(entity_type,
entity_id,occurred_at)`. Админ-действие и audit — один commit; история не
изменяется обычным API. Срок хранения административного аудита — отдельная
политика, не приравнивать молча к сроку модерации.

`catalog_outbox`: `event_id UUID PK`, `event_type VARCHAR(128) NOT NULL`,
`schema_version INTEGER NOT NULL CHECK > 0`, `aggregate_id SMALLINT NOT NULL`,
`payload JSONB NOT NULL`, `created_at timestamptz NOT NULL`, `published_at
timestamptz NULL`; индекс неопубликованных записей. Если событие используется,
оно фиксируется вместе с действием и audit; потребители идемпотентны. Каталог
использует асинхронную репликацию PostgreSQL, поэтому подтверждённая правка при
аварии основной базы может быть потеряна — это согласованное допущение.

## Внешний REST API

Чтение доступно авторизованному пользователю; админ-методы требуют актуальной
сессии и разрешения `catalog.manage`. Даты UTC; ID категорий, упражнений и
вариаций — числа `1`–`32767`, а технический `request_id` — UUID. Ошибка:
`{"error":{"code":"validation_error","message":"Проверьте данные","request_id":"<uuid>"}}`.
Общие `400 invalid_request`, `401 unauthenticated`, `403 forbidden`,
`404 not_found`, `422 validation_error`, `429 rate_limited`,
`503 catalog_unavailable`, `500 internal_error`; секреты не выдаются.

| Метод | Назначение | Ответ |
| --- | --- | --- |
| `GET /api/v1/exercise-categories` | Активные категории. | `200 {"items":[{"id":1,"code":"BODYWEIGHT","name":"Bodyweight"}]}` |
| `GET /api/v1/exercises?category_id=1&limit=20&cursor=...` | Активные упражнения с активным STANDARD; категория опциональна, limit 1–100. | `200 {"items":[{"id":1,"code":"PUSH_UP","name":"Push-up","primary_metric":"REPETITIONS"}],"next_cursor":null}` |
| `GET /api/v1/exercises/{exercise_id}` | Упражнение и активные вариации. | `200` DTO ниже; неактивное — `404`. |

Пример деталей:

```json
{"id":1,"code":"PUSH_UP","name":"Push-up","description":"...",
 "category":{"id":1,"code":"BODYWEIGHT","name":"Bodyweight"},
 "primary_metric":"REPETITIONS","unit":"REP",
 "variations":[{"id":1,"code":"STANDARD","name":"Standard",
 "description":"...","instructions":"...","min_target":1,"max_target":1000,"target_step":1}],
 "version":1}
```

Телефон загружает активный каталог с сервера и хранит локальную копию для
выбора; при открытии экрана обновляет данные при доступной сети. Поиск и фильтр
выполняются по загруженному каталогу на телефоне. Серверная проверка перед
публикацией обязательна: старая локальная копия не даёт права опубликовать
отключённую вариацию. При недоступности каталога опубликование не выполняется,
черновик сохраняется, пользователь может повторить запрос.

Порядок — `(sort_order,id)`, cursor — непрозрачный кодированный последний ключ,
привязанный к фильтру; не считать его разрешением. Изменения каталога между
страницами могут изменить список. Конкретный подписанный формат курсора и
лимит запросов ещё нужно согласовать с общим механизмом пагинации.

## Администрирование

POST/PATCH требуют `Idempotency-Key` UUID; повтор того же ключа и payload
возвращает сохранённый исход, другой payload — `409 idempotency_key_conflict`.
Доступ проверяется и при повторе. PATCH содержит `version`: при устаревшей
версии `409 version_conflict`. Успешный commit включает изменение, результат
повтора и audit; outbox — если требуется событие.
В запросах создания вариации или STANDARD можно передать `target_step`; по
умолчанию он равен 1. При PATCH вариации можно изменить `min_target`,
`max_target` и `target_step` вместе или по отдельности: сервер проверяет итоговое
сочетание и отвечает `422 validation_error`, если допустимых значений нет.

| Метод | Тело | Успешный ответ |
| --- | --- | --- |
| `POST /api/v1/admin/exercise-categories` | `{"code":"BODYWEIGHT","name":"Bodyweight","sort_order":0}` | `201 {"id":"...","version":1}` |
| `PATCH /api/v1/admin/exercise-categories/{id}` | `{"version":1,"name":"Bodyweight exercises","is_active":true}` | `200 {"id":"...","version":2}` |
| `POST /api/v1/admin/exercises` | `{"category_id":"...","code":"PUSH_UP","name":"Push-up","description":"...","primary_metric":"REPETITIONS","standard":{"name":"Standard","description":"...","instructions":"...","min_target":1,"max_target":1000}}` | `201 {"id":"...","standard_variation_id":"...","version":1}` |
| `PATCH /api/v1/admin/exercises/{id}` | `{"version":1,"name":"Push-up","description":"...","is_active":false}` | `200 {"id":"...","version":2}` |
| `POST /api/v1/admin/exercises/{id}/variations` | `{"code":"NARROW","name":"Narrow grip","description":"...","instructions":"...","min_target":1,"max_target":1000}` | `201 {"id":"...","version":1}` |
| `PATCH /api/v1/admin/exercises/{id}/variations/{variation_id}` | `{"version":1,"is_active":false}` | `200 {"id":"...","version":2}` |

`409 code_conflict` для занятого кода; `409 standard_required`, если операция
оставляет активное упражнение без STANDARD; `409 metric_immutable` при попытке
сменить метрику; неверный диапазон — `422 validation_error`. Неактивную запись
администратор может прочитать отдельным admin GET, определённым ниже. DELETE нет. При отключении категории её записи
остаются, но пользователи не выбирают их для новых заданий.

`GET /api/v1/admin/exercises?active=all&limit=20&cursor=...` требует
`catalog.manage`; `active` — `all`, `true`, `false`, default `all`;
limit 1–100, сортировка `(sort_order,id)`, cursor привязан к фильтрам.
`200 {"items":[{"id":"...","code":"PUSH_UP","name":"Push-up",
"is_active":true,"version":1}],"next_cursor":null}`.
`GET /api/v1/admin/exercises/{id}` возвращает `200` с полным DTO публичных
деталей и дополнительными `is_active`, `version` у упражнения и каждого
варианта, включая неактивные. Неизвестный ID — `404 not_found`. Аналогично
`GET /api/v1/admin/exercise-categories` возвращает все категории с `is_active`
и `version`. Объекты вариаций редактируются через родительский exercise ID;
чужая пара exercise/variation возвращает `404`.

## Межсервисный контракт

Предлагаемый gRPC `GetVariationForChallenge` от Challenge к Catalog: в Protobuf
`exercise_id` и `variation_id` передаются как `int32`, но Catalog принимает
только значения `1`–`32767`. Запрос
`{exercise_id, variation_id, target_value, request_id}`, значение —
положительный int64; ответ `{exercise_id, exercise_version, exercise_name,
variation_id, variation_version, variation_name, description, metric, unit,
target_value, instructions}`. `instructions` — инструкция выбранной вариации;
Challenge фиксирует её в снимке и передаёт Moderation, а не берёт с телефона.
Доступ только service identity Challenge; Catalog проверяет
активность всей цепочки и диапазон на primary. `NOT_FOUND` — неизвестный ID,
`FAILED_PRECONDITION INACTIVE`, `INVALID_ARGUMENT TARGET_OUT_OF_RANGE`,
`UNAVAILABLE` / `DEADLINE_EXCEEDED` — временная неопределённость. Таймаут не
считается отрицательной бизнес-проверкой; Challenge повторяет до публикации.
Проверка не блокирует изменения в двух базах: действует правило фиксации
снимка выше.

`GetVariationsForChallenge` — пакетный gRPC-вызов Challenge → Catalog:
`{request_id, items:[{task_ref,exercise_id,variation_id,target_value}]}`;
1–100 элементов, `task_ref` — уникальный UUID задачи в запросе. Ответ
`{items:[{task_ref,status,snapshot,error_code}]}` в порядке запроса. При
`status=OK` snapshot содержит поля одиночного вызова; при `status=INVALID`
snapshot отсутствует, `error_code` — `NOT_FOUND`, `INACTIVE` или
`TARGET_OUT_OF_RANGE`. Нарушение шага передаётся как `INVALID_ARGUMENT
TARGET_STEP_INVALID` в одиночном вызове и как `status=INVALID`,
`error_code=TARGET_STEP_INVALID` в пакетном. Весь запрос с повторяющимся task_ref —
`INVALID_ARGUMENT DUPLICATE_TASK_REF`; отказ БД — `UNAVAILABLE`, частичного
успеха в таком случае нет. Вызов читает primary и получает один согласованный
снимок БД каталога на пакет; несколько пакетов не образуют глобальную
транзакцию. Challenge не публикует challenge, если хотя бы один item INVALID
или пакет не получил достоверного ответа. Повтор read-only вызова не создаёт
изменений; результат может отличаться после правки каталога, поэтому Challenge
фиксирует только результаты окончательной успешной проверки перед своей
транзакцией публикации с учётом оговорённой гонки деактивации.

## Проверки перед разработкой

PostgreSQL: одновременные изменения STANDARD и упражнения, код-дубликат,
устаревшая версия, повтор ключа и потерянный ответ, атомарный audit и rollback.
Интеграционно: недоступный каталог при публикации, деактивация одновременно с
публикацией, неизменность старого снимка, проверка метрик/диапазонов,
авторизация админа и сервиса, пагинация. Тесты не запускались.
