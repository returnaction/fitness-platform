# Выкладка сервисов на dev-сервер

Это инструкция для разработчиков и помощника: как обновить работающий сервис
и подключить новый. Она описывает текущие скрипты, а не будущую архитектуру.
При изменении механизма выкладки обновляйте эту инструкцию вместе с кодом.

Перед работой проверьте текущую ветку, выбранную задачу и разрешённый объём.
Подготовка файлов не разрешает автоматически commit, push, merge, deploy
или миграции пользовательской БД — для них нужно явное поручение владельца.
Реальные адреса доступа, пароли, токены и ключи сюда не записываются.

## Как устроен выпуск

```text
Повышение собственной версии сервиса в pom.xml
  → согласованный merge в main
  → GitHub Actions определяет изменённые версии
  → тесты Maven → сборка образа → публикация в GHCR
  → SSH на сервер → скачивание образа → запуск → health-check
```

Workflow запускается при push в `main`. Если повышенных версий нет,
сборка образов и выкладка пропускаются; проверка логики release всё равно идёт.
Кандидаты собираются параллельно, но серверная выкладка ждёт успеха всех сборок
и выполняется последовательно. Текущий порядок:
Accounts → Coins → Identity → Exercise Catalog → Gateway.

Используется точный числовой tag из POM, например `0.1.2`, без `latest`.
Образы согласовано оставлять публичными; настоящие env и ключи в них не входят.
Java runtime находится в образе. PostgreSQL установлен в ОС отдельно от Docker.
Наружу опубликован Gateway, остальные приложения общаются во внутренней сети.

## Где что находится

| Файл | Назначение |
| --- | --- |
| [release.yml](../.github/workflows/release.yml) | Запуск Actions, тесты, сборка, GHCR и SSH-доставка |
| [release-candidates.py](scripts/release-candidates.py) | Список выпускаемых сервисов `SERVICES` и сравнение версий POM |
| [deploy-release.sh](scripts/deploy-release.sh) | Порядок, зависимости, обновление точного образа, health-check и очистка |
| [test_release.py](scripts/test_release.py) | Тесты выбора версий и сценариев выкладки без настоящего Docker/SSH |
| [compose.yaml](compose.yaml) | Контейнеры, сеть, mounts, dev-профиль, health-check и логи |
| [compose.env.example](compose.env.example) | Шаблон переменных `*_IMAGE` с точными адресами образов |
| [env/README.md](env/README.md) и `env/*.env.example` | Шаблоны настроек, из которых создаются настоящие файлы на сервере |
| [generate-dev-crypto.sh](scripts/generate-dev-crypto.sh) | Первоначальное создание серверных mTLS/JWT-материалов |

Python-скрипты release запускаются на GitHub runner. На сервере выкладкой
занимается Bash; исходники Java там не собираются.

## Что должно быть готово на сервере

До разрешённого выпуска проверяются Docker/Compose, существующая внешняя
Docker-сеть из Compose, SSH-доступ Actions и доступ к GHCR. Базы, роли, env,
сертификаты и каталоги dumps готовятся заранее. Скрипт deploy их не создаёт.

В Actions используются Secrets `VPS_HOST`, `VPS_SSH_USER`,
`VPS_SSH_PRIVATE_KEY`, `VPS_SSH_KNOWN_HOSTS` и variable
`VPS_DEPLOY_ENABLED=true`. Для публикации workflow использует `GITHUB_TOKEN`.
Значения секретов не печатаются в диагностике.

Шаблон `compose.env.example` не является рабочим файлом сервера. Настоящий
`compose.env` лежит в каталоге приложения, заданном `VPS_APP_DIR` в workflow.
Он хранит версии образов, а не пароли БД. При выпуске скрипт обновляет нужную
строку `*_IMAGE` в серверном файле; шаблон не нужно переписывать при каждом релизе.
Не заменяйте рабочий файл целиком стартовым шаблоном: это потеряет текущие версии.

Перед первым выпуском Catalog подготовьте базу и роль по
[инструкции PostgreSQL](../docs/database-setup.md), файл
`/opt/fitness-platform/secrets/exercise-catalog.env` по
[шаблону](env/exercise-catalog.env.example) и каталог
`/opt/fitness-platform/runtime/exercise-catalog/dumps` с правом записи для UID 10001.
Добавьте строку `EXERCISE_CATALOG_IMAGE` из [compose.env.example](compose.env.example)
в серверный `compose.env` и укажите в серверном `gateway.env`
`EXERCISE_CATALOG_HTTP_BASE_URL=http://exercise-catalog-service:8086`.
Gateway запускается после готовности Identity и Catalog.

Для первого выпуска по спецификации 007 подготовлены Catalog `0.1.2` и Gateway `0.1.4`.
Подготовка VPS подтверждена оператором. На момент закрытия реализации публикация
образов и запуск на VPS ещё предстояли. [Журнал проверок 007](../specs/007-exercise-catalog-readonly-mvp/verification.md)

## Обновление существующего сервиса

1. Подготовьте изменение и проверьте совместимость API, gRPC и миграций
   с уже работающими сервисами. Если нужны новые переменные или файлы,
   обновите шаблон и заранее подготовьте серверную конфигурацию.
2. Повысьте собственную `<version>` в `services/<service>/pom.xml`,
   например `0.1.1` → `0.1.2`. Версию родительского POM для этого не меняют.
   Изменения кода, Dockerfile, Compose или документации без повышения
   версии сервиса сами по себе не запускают его выкладку.
3. Если изменились gRPC-контракты, повысьте версию `grpc-contracts`, явно
   обновите зависимости нужных потребителей и версии выпускаемых сервисов.
   Сам модуль контрактов не выкатывается отдельным контейнером.
4. Выполните проверки из раздела ниже. После явного разрешения владельца
   изменения проходят commit/push/PR и merge в `main`.
5. Проверьте Actions, опубликованный tag, состояние контейнера, миграции
   и нужный HTTP-сценарий через Gateway. Зелёная сборка не заменяет проверку
   server job: при `VPS_DEPLOY_ENABLED != true` выкладка пропускается.

Нельзя незаметно заменять код уже выпущенного tag. Для исправленного кода
нужна следующая версия. Повторная попытка того же run предназначена для
исправленной причины сбоя окружения, а не для выпуска нового кода под старым tag.

## Добавление нового сервиса в выкладку

Наличие папки сервиса и env-шаблона не включает его в выпуск автоматически.
Подготовьте все пункты до merge, иначе Actions попытается запустить
ещё не подготовленный контейнер.

1. **Модуль и образ.** Проверьте регистрацию модуля в root POM, собственную
   release-версию, Dockerfile, `application-dev.yaml`, readiness endpoint
   и пользователя контейнера. Сборка Docker идёт с контекстом корня репозитория.
   Проверьте COPY модулей в Dockerfile: после добавления Maven-модуля сборка
   существующих сервисов тоже должна видеть необходимые POM.
2. **Версия первого выпуска.** Если POM появился только в этом изменении,
   числовая версия считается первым выпуском. Если сервис уже был в `main`,
   но раньше не входил в deployment, повысьте его версию: скрипт сравнивает
   POM с `github.event.before`, а не проверяет наличие образа в GHCR.
3. **Настройки.** Добавьте или актуализируйте `env/<service>.env.example`,
   затем подготовьте настоящий файл на сервере по [инструкции env](env/README.md).
   Имена, переменные и пути должны совпадать с dev-профилем и Compose.
   Не копируйте локальные адреса и пароли в серверный шаблон.
4. **База, если нужна.** По [database-setup.md](../docs/database-setup.md)
   создайте отдельную роль, БД и права на сервере. Пароль запишите только
   в серверный env. Проверьте разрешение новой пары БД/роль в `pg_hba.conf`
   для Docker-сети: существующие правила могут быть перечислены по сервисам.
   PostgreSQL наружу не открывается. Таблицы создаст Liquibase при запуске.
5. **mTLS, если нужен.** Подготовьте сертификат с правильными DNS SAN и
   назначением client/server, доверие существующему CA и необходимые mounts.
   Текущий генератор рассчитан на первый набор сервисов: дополните его для
   будущей установки и отдельно подготовьте безопасное добавление материалов
   на уже работающем сервере. Не запускайте `--force` ради нового сервиса:
   он заменяет общий CA и существующие mTLS/JWT-ключи.
6. **Compose.** Добавьте сервис в [compose.yaml](compose.yaml): переменную
   образа, сеть, `SPRING_PROFILES_ACTIVE=dev`, read-only env/crypto mounts,
   каталог dumps, health-check, restart и ротацию логов. Подготовьте источники
   bind mounts и права под UID приложения; `create_host_path: false` не создаст
   их автоматически. Порты внутреннего сервиса наружу не публикуются.
   Если нужны лимиты, контейнерный лимит задаётся в Compose, JVM — параметрами
   запуска Java; значения подбираются отдельно, не в application-dev.yaml.
7. **Ссылка на образ.** Добавьте новую `*_IMAGE` в `compose.env.example`
   и заранее ровно одну такую строку в рабочий `compose.env` сервера.
   Адрес должен соответствовать формуле workflow: `ghcr.io/<owner>/fitness-<service>:<version>`.
   Текущий owner закреплён в workflow и deploy-скрипте, не берётся из POM.
8. **Выбор и порядок.** Добавьте сервис в `SERVICES` в
   [release-candidates.py](scripts/release-candidates.py). В
   [deploy-release.sh](scripts/deploy-release.sh) обновите **оба** `case`:
   первый задаёт допустимые имена и `rank`, второй — `image_variable`
   и `dependencies`. Порядок `SERVICES`, ranks и зависимости должны совпадать;
   зависимости запускаются раньше потребителей. Скрипт использует `--no-deps`
   и сам не поднимает пропущенные зависимости.
9. **Потребители и тесты.** Если Gateway или другой сервис должен обращаться
   к новому, обновите его настройки/маршруты, серверный env и версию для выпуска.
   Дополните [test_release.py](scripts/test_release.py): список, порядок,
   переменную образа и проверки зависимостей/отказа. Workflow строит matrix
   из кандидатов — отдельная job для каждого нового сервиса обычно не нужна.
10. **Выпуск.** После проверок и разрешённого merge дождитесь всех jobs,
    проверьте tag, доступность образа серверу, healthy, Liquibase и запрос
    через Gateway. Видимость нового GHCR-пакета проверьте отдельно:
    workflow не устанавливает её автоматически в public.

## Проверки до merge

Команды запускаются из корня репозитория. Ниже Bash (Linux/WSL/Git Bash);
`<service>` заменяется на имя каталога, например `accounts-service`.

```bash
bash ./mvnw --batch-mode --no-transfer-progress -pl services/<service> -am verify
bash -n deployment/scripts/deploy-release.sh
bash -n deployment/scripts/generate-dev-crypto.sh
python3 deployment/scripts/test_release.py
docker compose --env-file deployment/compose.env.example -f deployment/compose.yaml config --quiet
```

Для полной проверки shell-тестов нужны Bash и `flock`; предпочтителен Linux/WSL
или GitHub runner. Пропущенные тесты не считаются успешной проверкой выкладки.
`compose config` проверяет конфигурацию, но не наличие серверных файлов, сети,
паролей, доступности БД или готовности приложения. При изменении Dockerfile
проверьте сборку образа отдельно; при изменении состава файлов — отсутствие
секретов в конечном образе, слоях, metadata и JAR. `.dockerignore` — только
одна из защит, не замена этой проверки.

## Проверки после выпуска и разбор ошибок

1. В Actions откройте «Выпуск сервисов»: тесты, публикация и server job
   должны завершиться успешно. Сверьте опубликованный tag с версией POM.
2. По SSH из каталога приложения проверьте состояние и логи:

   ```bash
   docker compose --env-file compose.env -f compose.yaml ps
   docker compose --env-file compose.env -f compose.yaml logs --tail=200 <service>
   ```

3. У сервиса должен быть `healthy`. Для сервиса с БД сверьте
   `databasechangelog` с миграциями выпущенного JAR, а
   `databasechangeloglock.locked` должен быть `false` после завершения старта.
4. Проверьте нужный HTTP-сценарий через Gateway. Проверку с телефона,
   если она требуется задачей, отмечайте отдельно.
5. Запишите версию, ссылку на run и результаты в журнал текущей задачи,
   не публикуя пароли, токены, личные данные и полный вывод секретных настроек.

При ошибке скрипт останавливает дальнейшую выкладку и показывает состояние
Compose и последние 200 строк логов. Автоматического rollback нет. Ранее
успешно обновлённые сервисы остаются обновлёнными; после ошибки cleanup
провалившегося сервиса не выполняется. Строка image в `compose.env` меняется
**до** pull/up, поэтому сама по себе не доказывает успешный запуск версии.

Сначала выясните причину по Actions и логам: отсутствующий env/ключ,
неверные права, недоступная БД, миграция или health-check. Не удаляйте БД,
не сбрасывайте checksum/lock Liquibase и не запускайте полный crypto-generator
как универсальное исправление. Исправление кода требует новой версии;
повторный запуск после исправления окружения — отдельного разрешения.
